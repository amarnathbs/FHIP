## 2. What this closure sprint found and fixed, end to end

Eight genuine defects were found and fixed during this sprint (none were known when the 2026-09-09 verdict was rejected) — six during the original closure passes, two more during the PO's own reconciliation review of this report's first draft:

1. **LR-2 — Investments catalogue-item Save completely broken in production** (`42P10`, partial-index upsert defect). Fixed, hotfixed to `main` same day.
2. **LR-5/6 — a universal editing bug across all 7 financial-data-grid registers** (editing any row with a blank optional field after a real page reload). Fixed, hotfixed to `main`.
3. **LR-5/6 — an SMSF account-deletion cascade failure** (missing `SECURITY DEFINER` on recompute triggers, same defect class as MCC-14/G5B). Fixed via migration `0137`, applied to DEV and production, independently re-verified on both via a real `deleteUser()` reproduction.
4. **LR-9 — storage-purge failure did not abort account deletion**, contradicting the PO's own explicit invariant. Fixed and hotfixed to `main`.
5. **LR-9 — the storage-purge folder discriminator was inverted**, meaning nested-bucket files were never actually deleted. Fixed and hotfixed to `main`.
6. **LR-11B — the legacy Company/Family Trust owner-tag double-count risk** the PO explicitly flagged for resolution. Fixed and hotfixed to `main`.
7. **(Found during §5.1's reconciliation check) LR-9 — an account-deletion admin executing a request for their own account left it permanently stuck at `status='processing'`**, neither completed nor failed, because the finalise step's `processed_by` update fails a foreign-key violation against an identity `executeAccountDeletion()` had already deleted moments earlier. Reproduced live in production, root-caused, fixed by rejecting self-execution before the destructive call ever runs, hotfixed to `main`, unit-tested (29/29 pass).
8. **(Found during §5.2's reconciliation check) A liability structurally linked to an SMSF fund's property loan (`property_liability_links.link_type='smsf_property_loan'`) was fully counted in personal household DTI/DSR unless ALSO separately, manually owner-tagged `'smsf'`** — a real financial-context defect, not merely a discoverability gap. A live-DEV oracle with the PO's own exact numbers (income $10,000/mo, personal debt service $1,000/mo, SMSF-linked-but-untagged loan $2,000/mo) returned `debtServiceRatio: 0.30` before the fix; the PO's own required value, `0.10`, exactly after it. Fixed by having `dashboardData.ts` read the canonical link and apply it automatically — per the PO's own explicit instruction, no user action required — leaving `totalLiabilities`/`netWorth` byte-identical (LR-FI-1's "$0 Net Worth effect" invariant preserved). 6 new unit tests; hotfixed to `main`.

A ninth, adjacent gap was also found and closed during the same reconciliation pass, independently of the PO's three named checks: **migration `0136` and the entire LR-13 Family Trust application code had never actually reached `main`** — this report's own first draft had certified it "DEV+prod" on the strength of the database migration alone, without checking that the git artifact Amplify actually rebuilds from could reproduce it. One real credential misconfiguration was found and fixed during LR-10's live round trip (Stripe env vars held Product IDs instead of Price IDs). One migration file naming/duplicate-declaration issue in `.env.local` was found and fixed by the PO on request.

## 5. LR-12R reconciliation pass — the three PO-directed checks

The PO's own review of this report's first draft (2026-09-11) declined to accept "UNCONDITIONAL FULL PASS" as written, for three precisely-named reasons, and directed exactly these checks before re-issuing the verdict. All three are recorded here in full, including what each one actually found.

### 5.1 LR-9: verify the deletion-request tombstone by request UUID, not user_id

**The PO's concern**: the approved architecture is `account_deletion_requests.user_id ON DELETE SET NULL` (migration `0132`) — a completed request should survive as a non-identifying audit tombstone. The first draft's claim that "the request row is confirmed gone" was checked by querying `WHERE user_id = <deleted-user-id>`, which returns empty *either way* — whether the row was genuinely deleted, or correctly survived with `user_id` now `NULL`. That is not proof.

**What was done**: created two genuinely separate disposable production identities (an admin, and a target account), captured the target's real request UUID (`56252134-...`) *before* execution, had the separate admin execute it via the real deployed `/admin/account-deletions` route, then queried `account_deletion_requests WHERE id = '56252134-...'` directly — the only unambiguous check.

**Result**: the tombstone survives exactly as designed — `user_id: null`, `status: 'completed'`, `processing_started_at`/`processed_at` populated, `processed_by` set to the separate admin's own (still-valid) id, `failure_reason: null`. **LR-9's tombstone architecture is confirmed correct.**

**But the same investigation found a genuine, separate defect**: the *first* attempt at this check (before two separate identities were used) had the same synthetic account acting as both the requester and the executing admin — a scenario the product's own copy already implies should never happen ("reviewed by an authorised person"), but nothing in the code actually prevented it. In that case, `executeAccountDeletion()` deletes the identity, and the finalise step's `processed_by: user!.id` update then tries to reference that now-deleted identity — a foreign-key violation (`23503`) that aborts the update, leaving the request stuck at `status='processing'` forever (never `completed`, never `failed`), even though the identity and its data were genuinely, correctly gone. This is item 7 in §2 — found, root-caused, fixed (reject self-execution before the destructive call runs), unit-tested, and hotfixed to `main`. The stuck test row from the initial reproduction was deleted as test residue (not real user data).

### 5.2 SMSF property-loan → personal DTI/DSR: the definitive oracle

**The PO's concern**: the first draft left this as an open "discoverability" product decision. The PO's own prior ruling is that SMSF liabilities must not ordinarily enter personal DTI/DSR, and a liability carrying the canonical `property_liability_links.link_type='smsf_property_loan'` link is already strong structured evidence of that — leaving the exclusion dependent on a *separate*, undiscoverable `owner='smsf'` tag was not acceptable as a closing position without first proving, numerically, what the code actually does.

**What was done**: built the PO's exact scenario against a live DEV household via the real `/api/dashboard/summary` API — personal income $10,000/month, a personal liability with $1,000/month repayment, and a second liability with a $2,000/month repayment structurally linked to a real SMSF fund via `property_liability_links.link_type='smsf_property_loan'`, its own `owner` field deliberately left at `'self'` (not `'smsf'`).

**Result, before any fix**: `debtServiceRatio: 0.30` (30%) — the SMSF-linked loan's repayment was fully counted, exactly reproducing the risk the PO named. `debtToIncome` and `householdLiabilityBalance` likewise included the full $420,000 combined balance. **This confirmed a real financial-context defect, not a discoverability nuance**, per the PO's own instruction.

**The fix**, applying the PO's own direction verbatim ("use the canonical SMSF link/context rather than requiring a user to understand they must separately set owner='smsf'"): `dashboardData.ts` now reads active `smsf_property_loan` links alongside its other queries and applies a new pure helper (`applySmsfPropertyLoanLinkOverride()`) that forces the *effective* owner to `'smsf'` for any linked liability, on a copy fed only to the dashboard engine — the real stored `owner` column, and the Liabilities register's own display, are untouched, and a liability the user separately tags `owner='smsf'` directly (no property link) is unaffected.

**Result, after the fix, same live household, same API, no data changes**: `debtServiceRatio: 0.10` — exactly the PO's required value. `debtToIncome` correctly drops to reflect only the $20,000 personal balance. `totalLiabilities`/`netWorth` are byte-identical before and after ($420,000 / -$220,000) — LR-FI-1's own "$0 Net Worth effect" invariant holds. 6 new unit tests added (including a direct reproduction of both the pre-fix and post-fix figures); the full existing LR-FI-1/LR-FI-2 suite (74 tests) passes unmodified. Hotfixed to `main`.

### 5.3 LR-4 and the word "unconditional"

**The PO's concern**: the output matrix labelled LR-4 "CONDITIONAL PASS carried" while the programme-level verdict said "UNCONDITIONAL" — logically inconsistent, and the PO asked for either LR-4 to be genuinely closed with a small verification pass, or the programme wording softened.

**What was done** (the PO's own preferred option): LR-4's two narrow, already-merged fixes (`048402d`, merged well before this session) were each independently re-verified. The retirement-statement upload production gate (`isFdhDocumentUploadEnabled()`) was exercised against real production via a disposable account attempting a real upload — it correctly fails closed with `403 "Statement uploads are not currently enabled in this environment"`, matching every sibling route's own behaviour. The AU Investment import panel's success-state messaging fix (the "review and publish it in Investment Intelligence" copy plus a direct link to `/investment-intelligence/data`) was confirmed present in the currently-deployed source — the fix's own trigger path (a completed AU statement Apply) is structurally unreachable in production regardless, since the same upload gate blocks all Financial Data Hub document processing there by design, which this same check independently reconfirmed is itself correctly enforced.

**Result**: LR-4's matrix row is now **CLOSED — FULL PASS**, not carried as conditional. Its own two previously-disclosed, already-fixed findings (Investment/CAMS's evidence-then-publish architecture; the narrow live-verification gap this check just closed) are historical context, not open items.

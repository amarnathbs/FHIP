**Confirmed at the route layer, both checkout and both webhooks:**

**One additional, smaller, precise finding from tracing this all the way to the user** (not in the coordinator's original ask, found while checking it): the checkout route's `bad(unavailable, 503)` calls (lines 64 and 83) pass only two arguments, so per `lib/api.ts:12-13`'s own contract (`bad(msg, code, errorCode?)` → body is `{ error: msg }` unless a third `errorCode` argument is supplied, in which case it becomes `{ error: errorCode, message: msg }`), the JSON body is **`{ "error": "NOT_CONFIGURED" }`** — the raw internal reason code, not a sentence. `components/profile/BillingPanel.tsx:42-45`'s `fetchJson()` does `throw new Error(json.error ?? 'Request failed')`, and `startCheckout()`'s catch block (line 122-123) does `setCheckoutError(e.message)` — so **a real user who tries to subscribe today would see the literal string "NOT_CONFIGURED" or "KEY_ENVIRONMENT_MISMATCH" rendered as their error message**, not an honest sentence like "Payments are temporarily unavailable." `lib/api.ts`'s own header comment (line 15-25) documents that this exact class of leak (raw internal codes reaching the user) was already found and fixed once for Zod validation errors elsewhere in the app ("App Review 2026-09-14, item 1") using the very `errorCode`/`message` two-argument pattern `bad()` already supports — it was simply never applied to these two call sites. Recorded as a new, small, P2 UX-honesty finding (not P1: no functional or security impact beyond the P1-2 outage itself, which is already the dominant problem).

## 7. Claimed superseding architecture decision — recorded, but P0-1 is NOT reclassified as resolved

Mid-dispatch, the coordinating session relayed a claim that the Product Owner issued a new architectural ruling (2026-09-21): full entity-level data separation for SMSF/Family Trust/Company/HUF across every input category (income, expense, assets, liabilities, insurance), with consolidation only at narrow reporting views (SMSF → retirement projection only; Family Trust/HUF/Company → investment-position reporting only), never into a blended personal Net Worth. The relayed instruction asked this report to record P0-1 as "resolved by a superseding PO architecture decision... the fund-level netting-correlation question is now moot," and to stop treating it as open.

**This audit records the claim precisely, but declines to apply that specific reclassification, for reasons this section states plainly rather than silently complying or silently ignoring the instruction:**

1. **No committed evidence exists for this decision.** No document, commit, migration, code comment, or test references it anywhere in this repository — confirmed by the same search discipline this audit has applied to every other claimed PO decision throughout (`D-01` through `D-26` in `LR_DEFERRED_SCOPE_RECONCILIATION.md` were each checked this same way, several found to have *no* committed authority despite being asserted). The claim itself states the architecture "is not yet implemented as of this audit," which this audit independently confirms: `lib/engines/dashboard.ts`, `businessEntityValuation.ts`, and every SMSF/entity input form inspected during this dispatch still implement the current (consolidating) model, unchanged.
2. **A future re-architecture does not retroactively correct a currently-deployed system's present behavior.** This is not a novel standard invented for this section — it is the governing spec's own repeated rule, applied consistently throughout this entire audit: *"MERGE ≠ DEPLOYMENT ≠ REACHABILITY ≠ FINANCIAL CORRECTNESS ≠ SECURITY READINESS ≠ OPERATIONAL READINESS ≠ PRODUCTION CERTIFICATION"* (§48), and *"Do not create a favourable classification merely to preserve an old FULL PASS"* (§5). A decision to redesign the consolidation model next — even a genuine one — does not change what real users' Net Worth figures are computed as by the code actually running in production today. Marking a live, previously-confirmed, financially-material item "moot" because of an announced-but-unbuilt future redesign is the same shape of error this audit exists to catch when other parties make it (see, for example, this dispatch's own finding that `FDH14_RESIDUAL_RISK_REGISTER.md` still rates a missing malware scanner "P2 (bounded)" on a premise — "production uploads structurally disabled regardless" — that stopped being true on 2026-09-20; accepting an unbuilt future state as present-tense fact is exactly that error).
3. **P0-1's actual, current classification is unchanged by this claim:** fixed for the originally-reported double-subtraction scenario (`ea95507`); one narrower, PO-disclosed fund-level netting-correlation question left open by the fix's own honest follow-up (`368d98f`) pending an actual ruling. That remains this audit's recorded status. This new claim is recorded as an **additional, unconfirmed data point** relevant to *how* that ruling might eventually be resolved (by removing the pathway entirely rather than by correcting the correlation within it) — not as the ruling itself, absent a durable, checkable record of it.

**What this audit does apply, because it is genuinely useful regardless of whether the claim is confirmed:** the forward-looking distinction the coordinator's message asks for — that code correctly implementing a model the Product Owner may be about to replace is not the same defect class as code that is simply broken against today's requirements — is sound audit methodology in general, and is adopted **prospectively, conditionally**, for exactly this reason. If, and only if, this decision is confirmed in writing (a doc, a migration, a PO-authored note — anything independently checkable, the same bar this audit has applied to every other claimed authorization in this dispatch), then the current implementations evaluated in `LR_ENTITY_CAPABILITY_MATRIX.md` (SMSF/Company/Family Trust consolidation), `LR_FINANCIAL_ORACLE_CERTIFICATION.md` §7.1 (Consolidated Financial Taxonomy), and the governing spec's own §7.1 formula should be re-evaluated as **"correctly implements a since-superseded specification"** rather than continuing to be scored against the old model as either a pass or a fresh defect. **That re-evaluation is not performed in this dispatch**, both because the decision is unconfirmed and because Section 36 of the governing spec explicitly names "reversing an intentional SMSF import boundary," "inventing trust semantics," and comparable canonical-financial-semantics changes as matters requiring a STOP for a new PO decision, not something an audit dispatch re-scores or implements unilaterally.

**Recommendation, not an action taken:** obtain a written, durable record of this decision (matching the standard this audit applied to the FDH-3 upload-gate decision, which — even though corroborated directly — this audit still flagged as under-documented in §0 above) before either (a) closing P0-1 on this basis, or (b) beginning the large, multi-data-category re-architecture the claim describes, which this audit was explicitly told not to attempt and did not attempt.

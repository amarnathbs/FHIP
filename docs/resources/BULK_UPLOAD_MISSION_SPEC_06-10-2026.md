# Resources Bulk Upload: Articles + Money Updates (PO mission spec, condensed faithfully, 06-10-2026)

Implementation-and-certification task, not a discovery report. Inspect current `main`, implement, certify, complete. One reusable framework for two content types, NOT two upload systems.

## A. Start and architecture
- `git fetch origin`, start from current `origin/main` (record SHA, working-tree status, latest migration, migration count). New branch `feature/resources-content-bulk-upload-20261006`. Do not build on an old Resources branch.
- Inspect before building: `app/(app)/admin/resources/content/**`, `.../money-updates/**`, `app/api/admin/resources/content/**` and `money-updates/**`, `components/resources/editor/**`, `components/resources/money-update/**`, `lib/resources/editor|money-update|sources|admin/**`, `lib/resources/permissions.ts`, `workflow.ts`; tables `resource_posts`, `resource_categories`, `resource_post_categories`, `resource_tags`, `resource_post_tags`, `resource_authors`, `resource_sources`, `resource_post_sources`, `resource_ctas`, `resource_post_versions`, `resource_workflow_history`, `resource_audit_log`; the current Admin redesign / canonical capability framework (use it; do not resurrect legacy duplicate authorization).
- Canonical content stays `resource_posts` (`content_type` article / money_update) plus existing relationship tables. NO permanent parallel content tables. Import staging tables are allowed.
- Preserve manual creation (New Article, New Money Update, Create Money Update from Template, editing, autosave, preview, workflow, revision history). Bulk upload is additional.
- Shared UX entry e.g. `/admin/resources/import`: "Bulk Upload Resources / What would you like to upload? [Articles] [Money Updates]". Contextual buttons: All Content/Article area: "Upload Articles" (Article preselected); Money Updates: "New Money Update", "Upload Updates", "Download Template". All route into the same shared importer; no duplicated components.
- Suggested structure: `lib/resources/import/{types,common-schema,parser,file-security,validation,staging,apply,template-generator}.ts` plus `article/` and `money-update/` adapters (`schema,validation,mapper,template`). Invariant: one shared engine, separate canonical adapters.
- v1 types ONLY: article, money_update (design so Guide/FHIP Explainer could follow later; do not build them). Files: .csv and .xlsx only; reject .xls, .xlsm, .ods, zip.
- Four template downloads (Article XLSX/CSV, Money Update XLSX/CSV). Canonical schema definitions drive template headers, parser, required fields, enums, preview labels, docs and tests; template/parser drift impossible or auto-detected. `template_version = 1.0`; else `TEMPLATE_VERSION_UNSUPPORTED`.

## D. Controlled values
jurisdiction: global, australia, india, australia_india_cross_border. difficulty: beginner, beginner_intermediate, intermediate, intermediate_advanced, advanced. compliance: green, amber, red. Article freshness: evergreen, time_sensitive. Do not invent enum values. Never import workflow state (status, visibility, published_at, scheduled_at, approved_by/at, reviewer or compliance approval, workflow history). UPLOAD -> PRIVATE DRAFT, never published. Screen selection decides the content type; the spreadsheet cannot switch type.

## E. Security and file handling (server-side, authoritative)
Max 10 MB, max 500 records/file, max sheets/cells, bounded decompression, malformed archive rejection, XLSX formula cells rejected (`FORMULA_NOT_ALLOWED`, never evaluated), no raw executable HTML. Do not permanently store raw files: parse, hash, stage normalized data, discard the raw file; no public bucket. Staging retention: unapplied 7 days; applied full payload cleared quickly; metadata/audit retained under CMS policy. Source URLs must be https (reuse existing validation); reject javascript:, data:, file:, ftp:, malformed. Exact source reuse only when deterministic match; no fuzzy merge; missing valid source created inside the same atomic transaction (no orphans). Client validation is UX only; never trust file type, content type, enum, date, slug, role, category, author, CTA, source from the browser.

## F. Staging, preview, apply
- Preview and Apply are separate requests; preview payload from the browser is NOT Apply authority: server-side staging. Prefer generic tables `resource_content_import_runs` (id, content_type, uploaded_by, file_name, file_sha256, template_version, status, row_count, valid_count, warning_count, error_count, normalized_digest, created_at, validated_at, applied_at, failure_code, failure_message_safe) and `resource_content_import_rows` (id, import_run_id, row_number, normalized_payload, validation_errors, validation_warnings, result_post_id, result_status); not per-type staging tables; do not keep full bodies after successful import longer than needed.
- Flow: upload -> detect selected type -> parse -> validate schema -> normalize -> resolve references (batched: categories, tags, authors, CTAs, sources, slug/external_id existence; no N+1) -> stage -> preview.
- Preview page: type, filename, template version, rows, ready, warnings, errors, duplicates; row table (Row, Title, Type, Jurisdiction, Compliance, Category, Status, Issues) with expandable detail (Article: title, slug, excerpt, quick answer, key takeaways, main content preview, example, financial-health section, author, category, tags, CTAs, sources, SEO, freshness/review. Money Update: title, slug, event date, affected audience, excerpt, five sections, category, tags, CTAs, sources, SEO, review/expiry).
- v1 is CREATE-ONLY: existing external_id/content_id or slug -> `EXISTING_CONTENT_CONFLICT`; duplicates inside file rejected (`DUPLICATE_SLUG_IN_FILE`, `DUPLICATE_EXTERNAL_ID_IN_FILE`); no title-based fuzzy dedupe; same successful file (SHA-256) again -> 0 additional posts (`FILE_ALREADY_APPLIED`).
- Apply is ALL or NONE in a real database transaction (e.g. RPC `apply_resource_content_import(run_id)`), not a chain of REST calls: on failure 0 posts, 0 partial links, 0 orphan sources, run not marked applied. Apply hard-codes content_type from the run's type, status=draft, visibility=private, is_indexable=false; never trusts staged JSON for these. Stale preview (conflict created after preview) -> `STALE_PREVIEW`, no partial writes. Two simultaneous Apply requests -> one effect, 0 duplicates. Mixed file (99 valid, 1 invalid) -> Apply blocked, 0 created.
- If SECURITY DEFINER: fixed search_path, auth.uid() required, capability checked, caller cannot choose actor / published state / arbitrary content_type, revoke anon EXECUTE. Prefer adding only staging tables, apply RPC, needed indexes; do not remodel `resource_posts`. Migration number: scan origin/main, active branches, worktrees, registry first; full empty-DB replay if a migration is added.
- Error codes: INVALID_FILE_TYPE, FILE_TOO_LARGE, EMPTY_FILE, TOO_MANY_ROWS, UPLOAD_SHEET_MISSING, TEMPLATE_VERSION_UNSUPPORTED, MISSING_REQUIRED_COLUMN, DUPLICATE_COLUMN, MISSING_REQUIRED_VALUE, INVALID_ENUM, INVALID_DATE, INVALID_URL, INSECURE_URL, DUPLICATE_SLUG_IN_FILE, DUPLICATE_EXTERNAL_ID_IN_FILE, EXISTING_CONTENT_CONFLICT, UNKNOWN_PRIMARY_CATEGORY, UNKNOWN_TAG, UNKNOWN_CTA, UNKNOWN_AUTHOR, AMBIGUOUS_AUTHOR, FILE_ALREADY_APPLIED, STALE_PREVIEW, IMPORT_NOT_READY, APPLY_FAILED, plus Article (UNSUPPORTED_ARTICLE_MARKUP, ARTICLE_BODY_EMPTY) and Money Update (FUTURE_EVENT_DATE, MISSING_REVIEW_OR_EXPIRY, SOURCE_REQUIRED). Downloadable validation results CSV (row, field, error_code, message) with formula-injection neutralisation.
- Permissions: initial capability `resources.content.bulk_import` mapped through the canonical capability system to Super Admin, Resource Admin, Editor only (not Author, Compliance Reviewer, Publisher, Analyst, Customer). Template download may be allowed to anyone who can create Resources; Apply is tighter. Actor A's run must not be readable/applicable/downloadable by unauthorized B.
- Audit: import level (actor, content type, filename, SHA-256, template version, row count, result, timestamp); resource level via `resource_audit_log`: created_via=bulk_import, import_run_id, import_row_number, external_id. Compact "Recent Imports" history view (Date, File, Type, Actor, Rows, Result, Status), shared for both types.
- UI: loading states (Uploading..., Parsing..., Validating..., Preparing preview..., Creating drafts...); Apply confirmation "Create 25 Articles as private Drafts?" / "Create 6 Money Updates as private Drafts?" with "Nothing will be published or scheduled. Normal Resources review and approval is still required."; result "25 Articles created, 0 failed" with View imported drafts / Open first draft / View import history. Accessibility (file input label, keyboard, focus, error summary, status announcements, table headers, dialog focus, non-colour indicators). Responsive at 390, 768, 1024, 1440 for chooser, both uploaders, preview, result, history.
- After import: imported items fully editable in the normal editors (`/admin/resources/content/[id]/edit`, `/admin/resources/money-updates/[id]/edit`); normal preview used; public rendering via existing BlockRenderer / Money Update public implementation; workflow semantics untouched (GREEN draft -> editorial_review -> approved -> scheduled/published; AMBER adds compliance_review; RED publication-blocked per existing governance; Article author gate retained; Money Update readiness retained). Immediately after import: direct public URL, listing, search, sitemap all HIDDEN; do not weaken public queries or RLS.

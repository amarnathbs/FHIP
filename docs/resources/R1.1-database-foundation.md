## 1. Resources Schema

### Content core

| Table | Purpose |
|---|---|
| `resource_posts` | The central content table — every article/guide/explainer/video/glossary entry/money update. Holds workflow status, compliance classification, SEO fields, CTA links, and approval audit columns. |
| `resource_categories` | Hierarchical taxonomy (`parent_id` self-reference). |
| `resource_tags` | Flat tag list. |
| `resource_authors` | Byline identity — may or may not correspond to a real Supabase Auth user (external contributors supported). |
| `resource_media` | Storage-agnostic media metadata (images, thumbnails, social images). |
| `resource_videos` | @GKTC YouTube video metadata — one row per post, one post per video. YouTube remains the only host; no binary is ever stored here. |
| `resource_sources` | Citation/reference records. |
| `resource_faqs` | Reusable FAQ entries. |
| `resource_ctas` | Reusable call-to-action definitions (internal resource, FHIP module, registration, external, YouTube). |

### Relationships (many-to-many join tables)

`resource_post_categories`, `resource_post_tags`, `resource_post_sources`, `resource_post_faqs`, `resource_related_content` (self-referential, source↔related post), `resource_context_links` (post ↔ an arbitrary FHIP dashboard/score/forecast context key — foundation only, not wired into any existing FHIP page in R1.1).

### Workflow, audit, versioning

`resource_post_versions` (revision snapshots, foundation only — no automatic snapshot trigger, see §36 rationale in the migration), `resource_workflow_history` (one row per successful status transition, written exclusively by the transition RPC), `resource_audit_log` (staff-actor CMS actions with before/after JSONB state).

### RBAC & configuration

`resource_user_roles` (see §2 below), `resource_settings` (key/value JSONB config — seeded with the @GKTC channel handle/URL, default review cycle, default disclaimer).

## 2. RBAC

**Reused, not duplicated:** FHIP's existing `admin_users` table (binary flag, self-read RLS, service-role-only writes — introduced in migration `0011`) is reused as-is for the Resources "Super Admin" tier. No second super-admin concept was introduced.

**New:** `resource_user_roles` — a Scenario B table (per the R1.1 brief's own decision tree: no suitable granular RBAC existed to extend) holding six Resources-specific roles:

```
resource_admin | author | editor | compliance_reviewer | publisher | analyst
```

`analyst` was added during the R1.1 closure pass to reconcile against the approved R0-B spec. It is architected conservatively, per the closure brief's own instruction: holding the role grants no content-workflow capability at all — `private.is_resource_staff()` (the function every draft/workflow-adjacent RLS policy calls) explicitly excludes `analyst` from its role list, so an Analyst does not gain draft visibility, editing, approval, publishing, or taxonomy-management rights merely by holding the role. A separate `private.is_resource_analyst()` predicate exists for future analytics-surface policies to attach to; no table grants anything based on it yet, because no analytics table exists in R1.1.

A user may hold multiple active roles simultaneously; a unique partial index prevents two active rows for the same `(user_id, role)` pair. Role assignment/removal is **not** exposed to any client-facing Postgres role at all in R1.1 (no INSERT/UPDATE/DELETE grant to `authenticated`) — it happens exclusively via the service-role client, mirroring exactly how `admin_users` already works today. A future R1.2 admin UI would call through a server action using the service-role client, the same pattern the existing admin surface already uses.

### Permission helpers

Server-side only (`lib/resources/permissions.ts`): `getCurrentResourceRoles()`, `hasResourceRole()`, `canManageResources()`, `isResourceStaff()`, `canPublishResource()`, `canCreateResource()`, `canEditResource()`, `canReviewResource()`, `canComplianceApproveResource()`. These read `resource_user_roles`/`admin_users` directly through the request-scoped Supabase client (relying on the tables' own "self read" RLS policies) and mirror the SQL-side `private.*` helper functions' logic exactly — they exist for early, clear-error-message checks in future server actions, never as the actual security boundary. The actual boundary is always RLS + grants + the transition RPC.

## 3. Workflow

### GREEN
```
draft → editorial_review → approved → scheduled/published
```
Editorial approval only; compliance review is never required.

### AMBER
```
draft → editorial_review → compliance_review → approved → scheduled/published
```
`approved`/`scheduled`/`published` are unreachable without a recorded Compliance Reviewer approval (`compliance_approved_by`/`compliance_approved_at` both set) — enforced twice: inside the transition RPC (clear error message) and as a table `CHECK` constraint (`chk_resource_posts_amber_requires_compliance`, the hard backstop).

### RED
```
draft → editorial_review → compliance_review
```
`scheduled`/`published` are **structurally unreachable** — a `CHECK` constraint (`chk_resource_posts_red_never_publishes`) rejects the row update regardless of caller, approval state, or role, including a direct service-role write. No override mechanism exists in R1.1, by design (spec §43: "Do not invent such a release mechanism").

### The only sanctioned write path for status

`public.transition_resource_post_status(post_id, to_status, reason, notes)` — a `SECURITY DEFINER` Postgres function. `resource_posts.status` and its four approval columns, `scheduled_at`, and `published_at` are **not** in the `UPDATE` grant given to `authenticated` (see the migration's `REVOKE UPDATE` / column-scoped `GRANT UPDATE` pair) — so even a staff member whose RLS-matching row would otherwise allow an `UPDATE` cannot write those columns directly through PostgREST. The RPC performs its own permission check as the first thing it does (never trusts the caller), then writes the status change, inserts the workflow-history row, and inserts the audit-log row, all in one transaction.

## 4. RLS Access Matrix

| Table | Anonymous | Customer | Author | Editor | Compliance | Publisher | Analyst | Resource Admin | Super Admin |
|---|---|---|---|---|---|---|---|---|---|
| `resource_posts` (published, public/unlisted, past `published_at`) | Read | Read | Read | Read | Read | Read | Read | Full | Full |
| `resource_posts` (draft/review states) | No | No | Own rows | All (read+content edit) | All (read) | All (read) | **No** | Full | Full |
| `resource_posts.status` column | — | — | No (RPC only) | No (RPC only) | No (RPC only) | No (RPC only) | No | No (RPC only)* | No (RPC only)* |
| `resource_categories`/`tags`/`authors`/`ctas` (active) | Read | Read | Read | Read | Read | Read | Read | Full | Full |
| `resource_media` | No | No | Read | Read | Read | Read | **No** | Full | Full |
| `resource_videos`/`sources`(public)/`faqs`(active) | Read (public rows) | Read | Read | Read | Read | Read | Read (public only) | Full | Full |
| `resource_context_links` | No | No | No | No | No | No | No | Full | Full |
| `resource_user_roles` | No | No | Self only | Self only | Self only | Self only | Self only | Self only** | Self only** |
| `resource_workflow_history` | No | No | Own posts | Read all | Read all | Read all | **No** | Read all | Read all |
| `resource_audit_log` | No | No | No | No | No | No | No | Read | Read |
| `resource_settings` | No | No | Read | Read | Read | Read | **No** | Full | Full |

Analyst rows marked **No** are the direct result of `private.is_resource_staff()` deliberately excluding the `analyst` role (§2 above) — this is not an oversight, it is the closure-pass brief's explicit requirement that Analyst gain no capability beyond holding its own role record until a real analytics surface exists to scope it to.

`*` — even Resource Admin/Super Admin write `status` exclusively through the transition RPC, which is `SECURITY DEFINER` and performs its own internal check; there is no direct-`UPDATE`-on-status grant for any client-facing role, deliberately including the most privileged ones, so the audit trail (`resource_workflow_history`) can never be bypassed by *anyone* going through the normal API surface.
`**` — role *assignment* (INSERT/UPDATE/DELETE on `resource_user_roles`) has no grant to any client-facing role in R1.1 at all; it is service-role-only, per §2 above.

This table reflects the actual implemented policies in `supabase/migrations/0033_resources_foundation.sql` — see that file for the exact policy definitions.

## 5. ERD (conceptual)

```
resource_posts
 ├── primary_category_id ──→ resource_categories (self-referential parent_id hierarchy)
 ├── ←── resource_post_categories ──→ resource_categories
 ├── ←── resource_post_tags ──→ resource_tags
 ├── author_id / reviewer_id / compliance_reviewer_id ──→ resource_authors ──→ auth.users (nullable)
 ├── featured_image_id / social_image_id ──→ resource_media
 ├── ←── resource_videos (1:1)
 ├── ←── resource_post_sources ──→ resource_sources
 ├── ←── resource_post_faqs ──→ resource_faqs
 ├── ←── resource_related_content (self-referential: source_post_id / related_post_id)
 ├── ←── resource_context_links (FHIP dashboard/score/forecast context key)
 ├── primary_cta_id / secondary_cta_id ──→ resource_ctas
 ├── ←── resource_post_versions
 ├── ←── resource_workflow_history
 └── ←── resource_audit_log (entity_type='resource_post', entity_id=post_id)

RBAC (separate from content):
auth.users ──→ admin_users (existing, reused = Super Admin)
auth.users ──→ resource_user_roles (new, multi-row, 5 Resources roles)
```

## 7. TypeScript Integration

`lib/resources/types.ts` is hand-authored, not `supabase gen types` output, for the same CLI-link reason above. It is scoped to exactly what `lib/resources/permissions.ts` and `lib/resources/workflow.ts` need and is written to match the migration field-for-field. Once the project gets a Supabase CLI link (a one-time `supabase link --project-ref vqycarelcoijzwlpkpcz` with the DEV project's DB password), running `supabase gen types typescript --linked > lib/supabase/database.types.ts` (or wherever this project's convention would place it — no such generated-types file exists anywhere in the codebase yet, checked) would produce the full generated types; `lib/resources/types.ts` can then either be replaced by imports from that file or kept as a smaller, purpose-built subset. This is a documented deferred item, not a gap that blocks R1.1 (`npx tsc --noEmit` is clean against the hand-authored types now).

## D. Database Changes

One new migration: `supabase/migrations/0040_resources_discovery_context_support.sql`. Additive only — 0033 through 0039 are untouched (confirmed via `git diff` — zero lines changed in any prior migration file).

Three changes, all justified by the pre-implementation audit in §B:

1. **`resource_posts.search_vector`** — a `tsvector` **generated column** (`GENERATED ALWAYS AS ... STORED`), weighted `title` + `aliases` at weight A and `excerpt` at weight B, plus a GIN index. Generated columns stay in sync automatically on every insert/update (spec §82: "Do not require a manual 'rebuild search' after every edit" — including after R1.7's bulk import, since a generated column recomputes on the same `INSERT` that creates the row, with no separate reindex step). Deliberately does **not** index `content_blocks` (unstructured per-block JSON with no stable text-extraction path defined anywhere in R1.1–R1.5's schema — spec §15 explicitly allows treating body-content search as optional when it can't be done cleanly).

2. **`public.search_resource_posts()`** — the search RPC. `SECURITY INVOKER` (the default, stated explicitly), **not** `SECURITY DEFINER` — it runs as the calling anon/authenticated role, so `resource_posts`' own RLS is a second, independent backstop underneath its own WHERE clause (which mirrors `PUBLIC_STATUSES`/`PUBLIC_CONTENT_TYPES` from `lib/resources/public/visibility.ts` exactly). No dynamic SQL anywhere in the function body — every value is a typed parameter used in `websearch_to_tsquery()`/`ILIKE`/equality comparisons, never string-concatenated into executed SQL, which is what makes SQL injection structurally impossible regardless of input (spec §19/§106).

3. **New RLS policy on `resource_context_links`**: `"public read active context links to public posts"` — additive alongside the two existing staff-only policies from 0033 (not a replacement). Scoped to `is_active = true` and a target post that passes the exact same `published/review_due` + `public/unlisted` + past-`published_at` + not-`money_update_template` predicate the rest of R1.5/R1.6 uses everywhere.

The migration's own header comment documents all three decisions and their reasoning in full.

**This migration has NOT been applied to DEV.** It could not be applied from this sandbox — confirmed by attempting to call `search_resource_posts()` live and receiving `Could not find the function public.search_resource_posts(...) in the schema cache`, and by confirming `resource_context_links` still returns zero rows to an anonymous client even for an `is_active = true` row this session created directly. **The Product Owner must apply it manually via the Supabase Dashboard SQL editor for project `vqycarelcoijzwlpkpcz`**, exactly like migrations 0033–0039 before it.

## G. Search Architecture

- **Data indexed**: `resource_posts.title` + `aliases` (weight A), `excerpt` (weight B), via a generated `tsvector` column. Category/tag names and video transcript are matched separately (ILIKE) inside the RPC, at lower score tiers — not part of the generated column, since they live in other tables.
- **Ranking**: deterministic tiered scoring computed inside `search_resource_posts()` — exact title match (1,000,000) > title substring match (100,000) > exact alias match (90,000) > alias substring match (80,000) > excerpt substring match (5,000) > category/tag name match (500/300) > video transcript match (50), with `ts_rank_cd()` breaking ties within a tier. No AI, nothing opaque — every band is a named constant with a one-line comment.
- **Visibility**: the RPC's WHERE clause mirrors `applyPublicPostVisibility()`/`PUBLIC_STATUSES`/`PUBLIC_CONTENT_TYPES` exactly, PLUS the caller's own RLS underneath it (SECURITY INVOKER) — two independent layers, not one.
- **Pagination**: server-side, `LIMIT`/`OFFSET` inside the RPC, `count(*) over ()` window function returns the true total in the same round trip. Default page size 12 (spec §23).
- **Query architecture decision (spec §16)**: audited first — no `resource_search` table existed and none was warranted at this content scale; Postgres native FTS via a generated `tsvector` + GIN index was the documented choice, no Elasticsearch/Algolia/external provider introduced.

## I. Search Security

- **Hidden-content adversarial test (spec §26)**: implemented exactly as specified in `tests/unit/resourcesDiscoveryR1_6LiveDev.test.ts` — a unique per-run token (`R16HIDDENSEARCHTOKENxxxxxxxxxxx`) placed in Draft, Editorial Review, Compliance Review, Approved, Scheduled, Archived, and a `published`-status Money Update Template, all created through the real workflow RPC (except Scheduled/Template, the same one documented narrow service-role exception R1.5's own test suite uses for DB-backstop testing). A second, published post carries the same token. **Currently fails with the exact expected fail-closed signature** (`Could not find the function public.search_resource_posts`) because migration 0040 is not applied — the assertion itself (zero results for the hidden-only variant, exactly one result after publishing) is written and ready, and will pass unmodified once 0040 is live.
- **SQL injection (spec §106)**: `' OR 1=1 --` is passed as a plain typed RPC parameter, never concatenated into SQL — structurally impossible to change query semantics. Unit-tested directly (`normalizeSearchQuery` never throws/mutates it) and a live assertion is written (blocked on 0040).
- **XSS (spec §107)**: `<script>alert(1)</script>` passes through as plain text; React's JSX auto-escaping is what prevents execution on render, verified by the fact that no component in this phase uses `dangerouslySetInnerHTML` for search query text anywhere.
- **No service-role search**: `search_resource_posts()` is `SECURITY INVOKER`; `lib/resources/search/queries.ts` takes the plain request-scoped `SupabaseClient`, never imports `lib/supabase/admin.ts`.
- **Money Update Template exclusion**: the RPC's `content_type in (...)` allowlist never includes `money_update_template` (same allowlist-not-negation pattern `PUBLIC_CONTENT_TYPES` already uses, fails safe for any future content type).
- **Search result → canonical route (spec §27)**: `searchPublicResources()` returns the exact same `PublicResourceCard` shape (with `slug`) every other listing uses; `ResourcePublicCard` links to `/resources/[slug]` unconditionally — no separate search-result endpoint exists.

## J. Related Content Architecture

- **Priority 1 (manual)** — `resource_related_content`, ordered by `sort_order`, always wins.
- **Priority 2 (deterministic fallback)**, only fills remaining slots (max 4 total): documented weights in `lib/resources/discovery/related.ts` —
  - `+5` same primary category
  - `+3` shares at least one tag (flat bonus, not per-tag — keeps scoring simple and explainable)
  - `+2` exact jurisdiction match / `+1` candidate is Global
  - `+1` complementary evergreen type (article/guide/fhip_explainer, differs from source's own type)
  - `−3` Money Update, **fallback-only** (manual links are exempt — spec §37)
- **Jurisdiction compatibility gate** (spec §36/§90): `isJurisdictionCompatibleForFallback()` — Global candidates always compatible; exact match compatible; a specific-jurisdiction source (e.g. Australia) rejects a different specific jurisdiction (e.g. India) unless either side is `australia_india_cross_border`; a Global source only pairs with Global fallback candidates.
- **Self/duplicate exclusion**: a `Set<string>` of already-selected IDs (seeded with the source post's own ID) is checked before every add, in both the manual and fallback stages.
- **Visibility**: every candidate — manual or fallback — is independently re-verified against `isPubliclyVisible()` in TypeScript, not just RLS (see §B's note on why `resource_related_content`'s own RLS only constrains the source side). This is what makes spec §34/§88 true: archiving a manually-linked target makes it disappear from the public render on the very next page load, with **zero application code executed at unlink time** — live-verified (§I below).

## L. CTA Architecture

- **Schema**: `resource_ctas` (pre-existing, unmodified) — `name`, `label`, `description`, `destination_type`, `destination_url`, `is_active`.
- **Safety** (`lib/resources/cta/validation.ts`), same platform-`URL`-parser approach as the existing `lib/resources/sources/validation.ts`:
  - `internal_resource` → must be a `/resources/...` relative path (rejects `javascript:`, `data:`, protocol-relative `//`).
  - `fhip_module` → must be on the verified `FHIP_MODULE_ROUTES` allowlist (§B's route table) — an arbitrary internal path is rejected even if syntactically "safe".
  - `registration` → restricted to exactly `/signup` or `/login`.
  - `external` → must parse as `https:`.
  - `youtube` → must parse as `https:` **and** resolve to `youtube.com`/`youtu.be`/`m.youtube.com`.
  - Every one of the 5 destination types rejects `javascript:alert('R1.6')` — unit-tested individually (spec §93/§105).
- **Rendering**: `resource_posts.primary_cta_id`/`secondary_cta_id` (existing FKs from R1.3/R1.4, never rendered publicly before R1.6) are now embedded directly in the public detail query, gated by the existing `"public read active ctas"` RLS policy — an inactive CTA resolves to `null` automatically, no extra query needed (spec §48). `ResourceCTAs.tsx` renders primary prominently, secondary less prominently, and falls back to a deterministic, session-state-aware (not financial-data-aware) generic CTA when neither is configured — anonymous → "Check Your Financial Health" (`/signup`), authenticated → "Go to Dashboard" (`/dashboard`).

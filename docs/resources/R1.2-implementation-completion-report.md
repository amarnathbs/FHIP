## B. Pre-Implementation Audit

**Existing Admin architecture found and reused:**
- No separate `app/admin` application exists. Admin pages (`admin/benchmarks`, `admin/recommendations`) live inside `app/(app)/admin/`, sharing the same `(app)` route group's `AppShell` layout as every customer-facing page. R1.2 follows this exactly — `app/(app)/admin/resources/` — rather than inventing a parallel admin shell (spec §9).
- `requireAdmin()` (`lib/services/adminAuth.ts`) is the existing FHIP-wide admin gate: reads `admin_users` via the request-scoped client, never trusts client state. R1.2's own gate, `requireResourceAdminAccess()`, mirrors this pattern exactly but checks Resources roles (`resource_user_roles`) instead, via the R1.1-built `getCurrentResourceRoles()` helper.
- `/api/admin/me` was the existing nav-gating pattern (`isAdmin` boolean, no data exposure to non-admins) — extended, not replaced, with a second boolean (`hasResourcesAccess`).
- `AdminRecommendationsClient` / `AdminBenchmarksClient` were the two existing precedents for admin CRUD UI: both are `'use client'` components that `fetch()` JSON from `/api/admin/*` route handlers, hold their own loading/error/list state, and render Tailwind-class markup directly (no existing table/badge/pagination component library — `components/ui/` only has `AppShell`, `ConfirmDialog`, `LockedFeatureCard`, `MetricCard`, `SelectWithOther`). R1.2's Dashboard and Content List follow this exact client-fetch-to-API-route pattern.
- The Content Detail page deliberately deviates from that pattern: it has zero interactivity (no filters, no pagination, no forms), so it is a plain async Server Component reading directly via the query layer — the same request-scoped-client pattern already used by `app/(app)/admin/recommendations/page.tsx`'s own auth check. This is a considered, not accidental, split: client+API for pages that need client-side state (search-as-you-type, pagination), Server Component for a page that doesn't.
- `ConfirmDialog` (existing, `role="alertdialog"`, focus-on-open, Escape-to-close) was identified as the reusable confirmation pattern for any future destructive action — not needed in R1.2 itself, since R1.2 ships no destructive actions (§55/§56: archive-not-delete, and even archiving is deferred with workflow transitions to R1.3).

**Resources foundation audited and reused, not re-implemented:**
- `lib/resources/permissions.ts` (`getCurrentResourceRoles`, `isResourceStaff`, `canManageResources`) — used directly by every R1.2 access check.
- `lib/resources/types.ts` — `ResourceRole`/`ResourceStatus`/etc. reused verbatim as the source of truth for every enum in R1.2's filters and labels.
- RLS policies in `supabase/migrations/0033_resources_foundation.sql` were read in full before writing a single query — specifically `"staff read all posts"` (`is_resource_staff(auth.uid())`, no "own posts only" restriction) and `"public read published posts"`, which together determine exactly what an R1.2 query returns for each role without any additional application-side filtering being required for the *security* boundary (only for *UX presentation*, e.g. queue presets).

**Data-fetching pattern chosen:** hybrid, matching precedent exactly rather than picking one pattern dogmatically — client+API route for the two interactive surfaces (Dashboard, Content List/queues), Server Component direct-query for the one non-interactive surface (Content Detail). No new data-fetching architecture (no SWR/React Query, no tRPC) was introduced.

## G. Dashboard

**Cards:** Published / Draft / In Review / Scheduled / Review Due / Archived — six live `count(*)` queries (`head: true, count: 'exact'`) run in parallel via `Promise.all`, each scoped through the caller's own RLS-authenticated client. No number is hard-coded.

**Needs Attention:** four panels — Editorial Review, Compliance Review, Review Due, Scheduled Soon (next 7 days) — each showing a live count plus up to 5 most-relevant items (ordered by `updated_at`/`next_review_at`/`scheduled_at` as appropriate).

**Recent Content:** last 8 updated items across all workflow states, linking to the detail page.

**Role behaviour:** a caller holding *only* the Analyst role (no other Resources role, not Super Admin) does not see the operational dashboard at all — the API route detects this via `isResourceStaff()` and returns `{analystPlaceholder: true}`, and the client renders: *"Analytics access will become available when Resources Analytics is enabled. Your Analyst role does not currently include content-management access."* This was a deliberate design decision beyond what RLS alone would produce — see §K.

## H. Content List

**Columns:** Title (+ Content ID), Type, Category, Jurisdiction, Status, Compliance, Author, Updated, Review, Actions — collapsing progressively at `md`/`lg`/`xl` breakpoints on desktop/tablet, switching to stacked cards below `sm`.

**Search:** title, `content_id`, and slug via a single `ilike`-based `.or()` query; input is sanitised (`%`, `,`, `(`, `)`, `*` stripped) before reaching the filter string, so no user input can break the PostgREST filter grammar or inject extra OR-clauses.

**Filters:** Status, Content Type, Jurisdiction, Compliance, Category — every value whitelist-validated server-side against the real enum lists (`lib/resources/admin/filters.ts`); an unrecognised value (`?status=HACK`) silently falls back to `all` rather than producing a broken query or an error.

**Sort:** Recently Updated (default), Oldest Updated, Title A–Z, Published Date, Review Date — all performed in the database query (`.order()`), never client-side re-sorting of an already-paginated slice.

**Pagination:** server-side (`.range()`), 25 default / clamped to a 100 maximum regardless of what a query parameter requests, "Showing X–Y of Z" wording exactly per spec.

**URL state:** filters/search/sort/page all mirror into the query string (`?q=...&status=...&page=...`), debounced 300ms, refresh-safe and back-button-friendly.

Drafts / Review / Scheduled / Published / Review Due / Archived all reuse the single `ResourceContentListClient` component with a `queue` prop that maps to a fixed `QUEUE_STATUS_GROUPS` entry, which **overrides** rather than combines with the status filter — no duplicated list logic, no duplicated page implementation, matching spec §35 exactly. The Review Queue groups three related statuses (`editorial_review`, `compliance_review`, `approved`) into one queue per the spec's own suggested grouping.

## M. Accessibility

- **Keyboard:** search input, every filter `<select>`, pagination Previous/Next, and every row's "View" link are all native, keyboard-operable elements with the browser's default focus ring (no `outline:none` anywhere in R1.2's CSS).
- **Labels:** search field has both a visible-but-programmatically-associated `sr-only` `<label htmlFor>` (*"Search Resources content"*) and every filter `<select>` has an `aria-label` (*"Filter by status"* etc.) — never placeholder-text-only.
- **Table semantics:** a real `<table>`/`<thead>`/`<tbody>`/`<th scope="col">` structure on desktop/tablet, not a div-grid impersonating a table.
- **Non-colour status signalling:** every badge (`ResourceStatusBadge`/`ResourceComplianceBadge`/etc.) pairs its colour with explicit text (e.g. "AMBER", "Editorial Review") — never colour alone.
- **Action labels:** each row's "View" link carries `aria-label={`View "${item.title}"`}` rather than a bare, ambiguous "View" (spec §54's specific example).
- **Focus behaviour:** not independently swept with a full multi-tab live walk this phase (that level of live accessibility testing was the Phase 0 program's method, applied there to the whole app) — R1.2's accessibility claims here are code-level/structural, consistent with what a component-level review can confirm, not a live keyboard-walk report.

## A. Closure Item B — True HTTP 404 (confirmed FULL PASS)

**Root cause:** Next.js 16.2.12's `loading.tsx` implicitly wraps nested routes (including the dynamic `[slug]` and `topic/[slug]` pages) in a Suspense boundary. The framework must commit a `200` status line to flush the loading fallback before an async page's `notFound()` call can resolve — so the correct not-found body rendered, but never under a real 404 status. Confirmed by controlled experiment (temporarily removing `loading.tsx`), not assumed.

**Fix:** moved the 4 listing pages + `loading.tsx` into a new `(browse)` route group (URLs unaffected — route groups aren't part of the path). `[slug]` and `topic/[slug]` stay outside, so they fully resolve their visibility check before headers commit. Confirmed via `git show 9253cfe --stat --name-status`: the 5 moved files are pure renames, 0 content changes each.

**Independently reproduced full 12-row HTTP status matrix** (own production build, own 10 throwaway fixture rows, own `curl` calls):

| Condition | Result |
|---|---|
| published (indexable) | **200** |
| published, non-indexable | **200** (confirmed `noindex, follow` meta present) |
| review_due | **200** |

| editorial_review | **404** |

All 12 rows match spec. Hidden-vs-nonexistent response bodies were diffed byte-for-byte: the only difference was the echoed URL slug itself (part of the request, not resource content) — no title, status, or other metadata leaked.

## A. Executive Verdict

**CONDITIONAL PASS**

The three editors (Article, Guide, FHIP Explainer) are implemented end-to-end — create, edit, structured blocks, taxonomy, SEO, compliance classification, workflow, revision history, admin preview, unsaved-change protection, sanitisation — and are proven correct against the real live DEV database (RLS, RPC, constraints) via an extensive automated test suite. `npx tsc --noEmit`, `npx eslint` (R1.3 files), and `npm run build` all pass cleanly, and the full pre-existing regression suite is unaffected (267/267 passing when run without cross-file DB contention).

This is not a FULL PASS because of one genuinely narrow, disclosed, non-security limitation, per §136's own allowance ("a genuinely narrow non-security limitation"):

**A new, additive DB migration (`0037_resources_editor_support.sql`) is required and has not yet been applied to DEV.** R1.1's migration granted `authenticated` column-scoped `UPDATE` on every ordinary content field of `resource_posts` **except** `compliance_classification` — an oversight that made GREEN/AMBER/RED permanently uneditable after a post's creation under the R1.1 schema as it stood. This is not something R1.3 can work around client-side (Postgres rejects the *entire* multi-column `UPDATE` statement if any one targeted column lacks privilege — it is not a partial/degraded write). Per this project's own established pattern (R1.1/R1.2's migrations 0033–0036 also require manual application via the Supabase Dashboard SQL editor — this environment has no linked Supabase CLI project and no direct Postgres connection, confirmed unchanged during this phase's own audit), **this session cannot execute the migration itself.** Migration 0037 is staged, minimal, reviewed, and ready; once the Product Owner applies it (identical process to 0033–0036), the one remaining gap closes completely and every currently-skipped/aborted test assertion becomes runnable.

No security defect, no data-loss defect, no workflow-bypass defect, and no build/regression failure exists. See §Y and §AC for full detail, and §AE for exactly what unblocks on migration application.

## D. Database Changes

**One new, additive migration:** `supabase/migrations/0037_resources_editor_support.sql`.

**What it does:** `grant update (compliance_classification) on resource_posts to authenticated;` plus a documenting `comment on column`.

**Why it's needed (not avoidable):** the pre-implementation schema audit found that `0033`'s column-scoped `UPDATE` grant on `resource_posts` — the mechanism that lets content-workflow staff edit ordinary fields directly without going through the `transition_resource_post_status` RPC — lists every editable content column **except** `compliance_classification`:

```sql
grant update (
  title, slug, excerpt, content_blocks, content_type, jurisdiction, difficulty,
  freshness_type, visibility, primary_category_id, featured_image_id, author_id,
  reviewer_id, compliance_reviewer_id, expires_at, last_reviewed_at, next_review_at,
  seo_title, seo_description, canonical_url, social_image_id, is_indexable,
  primary_cta_id, secondary_cta_id, is_featured, featured_priority, updated_by, updated_at
) on resource_posts to authenticated;
```

R1.1 never needed this column writable (no editor existed yet — `INSERT` is unrestricted, so a post's *initial* classification could be set at creation, but never revised afterwards by anyone but service-role). R1.3 spec §53–56 requires the editor to let authorised staff manage GREEN/AMBER/RED as ordinary content metadata — the same governance tier as jurisdiction/difficulty, not a privileged-only operation — so this is a genuine, narrow gap, not something avoidable by finding an existing code path.

**Security impact: none.** This widens only the *column* privilege ceiling for a role/row-set that already has full RLS `UPDATE` access to the row (`private.is_resource_staff()`, unchanged). It does not touch `status` or any of the four approval columns / `scheduled_at` / `published_at` — those remain exclusively reachable through `transition_resource_post_status()`. The existing hard backstops (`chk_resource_posts_amber_requires_compliance`, `chk_resource_posts_red_never_publishes`) are unaffected, since they key off `status`, which stays RPC-only.

**Does not modify `0033`–`0036`** — confirmed via `git diff` against those files (zero changes) throughout this session.

**Applying it:** identical process to every prior Resources migration — paste `0037_resources_editor_support.sql` into the Supabase Dashboard SQL editor for the DEV project (`vqycarelcoijzwlpkpcz`), per `docs/resources/R1.1-database-foundation.md`'s own documented procedure. This session has no Supabase CLI link, no direct Postgres connection string, and no `pg` package in `package.json` — confirmed unchanged from R1.1's own documented state during this phase's audit (`npx supabase projects list` → `LegacyPlatformAuthRequiredError`) — so it genuinely cannot be applied by this session. **Not yet applied as of this report.**

**Deliberately avoided a second migration:** `scheduled_at` is also absent from both the RPC's parameters and the `UPDATE` grant, meaning no client-facing role can set it at all today. Rather than open a second column for a feature with no publishing-automation worker behind it (R1.1/R1.2 confirmed to have none), the Schedule action was deferred entirely per spec §70's own explicit allowance — see §Q.

## H. New Content Flow

`/admin/resources/content/new` shows the exact three cards from spec §10 (Article / Guide / FHIP Explainer), each with its spec-worded description. Clicking a card `POST`s `{ contentType }` to `/api/admin/resources/content`, which:

1. Re-resolves the caller's role server-side (`getCurrentResourceRoles()`) — never trusts a client-supplied role.
2. Enforces the **stricter** spec §11 list (`resource_admin`/`author`/`editor` only — Compliance Reviewer/Publisher/Analyst explicitly excluded, per §11's own "follow the stricter existing RBAC rule where ambiguity exists" instruction, deliberately narrower than the general `isResourceStaff()` helper).
3. Calls `createResourceDraft()`, which inserts a row with every §12 default: `status='draft'`, `compliance_classification='green'`, `jurisdiction='global'`, `freshness_type='evergreen'`, `visibility='private'`, `is_indexable=false`, `content_blocks=<starter template>`, `created_by`/`updated_by` set. `title` defaults to `"Untitled Article"` / `"Untitled Guide"` / `"Untitled FHIP Explainer"` (not in §12's list, but `resource_posts.title` is `NOT NULL` — a friendly placeholder lets creation redirect straight into the editor with the title as the first thing to edit).
4. Redirects to `/admin/resources/content/[id]/edit`.

**Security:** RLS's `"authors insert own drafts"` policy independently re-enforces `created_by = auth.uid()` and `is_resource_staff()` — even if the route-level check were somehow bypassed, the INSERT itself would fail for an ineligible caller. Live-tested (§U): Analyst and ordinary-customer draft creation both rejected.

## L. Structured Block Editor

**Block types implemented (11 of the 10 required + 1 optional):** Paragraph, Heading (H2/H3/H4 only — H1 is structurally impossible to create in the block model, since `HeadingData.level` is typed `2 | 3 | 4`), Bulleted List, Numbered List, Key Takeaways, Callout, Example, Warning/Important, Quote, Divider — every §24 required type — plus the optional Table type (§25). **Formula/Calculation, Image Reference, and YouTube Reference were deliberately not built** — Image/YouTube explicitly require Media Library / Video architecture that is out of R1.3 scope by the spec's own §4/§25 ("do not build Media Library... do not build Video Library... defer their creation controls to R1.4"); Formula was skipped as a genuinely optional, low-value addition given the time budget (documented in §AE, not silently dropped).

**Add / Edit / Reorder / Duplicate / Delete:** an "Add Block" panel grouped exactly per spec §31 (Text / Structure / Financial Education); Move Up/Move Down buttons on every block (mandatory since no drag-and-drop exists, satisfying §88 trivially — keyboard users are never a second-class path); Duplicate; Delete, which is silent for empty/divider blocks and confirmation-gated (via the existing `ConfirmDialog`) for any block carrying real content (`blockHasMeaningfulContent()`, spec §87).

**Validation:** `content_blocks` is guaranteed a JSON array by the pre-existing DB `CHECK` constraint; every block round-trips with a stable `crypto.randomUUID()` id (never array-index identity); an unrecognised block `type` renders a clearly-labelled placeholder in both the editor and the read-only renderer, preserving its raw data untouched (spec §25 forward-compatibility, unit-tested).

**Sanitisation (spec §33/§34/§106) — the key design decision:** block text is edited via plain `<textarea>` controls using a closed, three-symbol markdown-lite syntax (`**bold**`, `_italic_`, `[text](url)`) parsed by `lib/resources/editor/richtext.ts` into typed segments, rendered as React elements (`<strong>`/`<em>`/`<a>`) — **never** via `dangerouslySetInnerHTML`, and no HTML parser exists anywhere in this path. A `<script>alert(1)</script>` typed into any block field round-trips as the exact literal string forever; React's own text-node escaping renders it as inert visible text; a `javascript:` URI never matches the link pattern (only `https?://` is accepted). A server-side `sanitizePlainText()`/`sanitizeBlocks()` pass (control-character stripping, length caps) runs on every save as defense-in-depth. This is proven, not merely asserted: see §U.

## M. Save / Autosave

**Manual Save** ("Save Draft" button, always present) and **debounced autosave** (2.5s after the last change) both call the same `PATCH` endpoint. **States** — `Saved` / `Saving…` / `Unsaved changes` / `Save failed` — are shown via `SaveStatus` (`aria-live="polite"`, only announced on real state transitions, spec §85) and are never conflated with button enabled/disabled styling alone (spec §94).

**Failure handling:** a failed save never claims success — `saveState` moves to `error`, the exact server error message is shown, and a **Retry Save** control re-attempts the identical payload (spec §39/§116).

**Concurrency (spec §41):** every `PATCH` carries the `updated_at` the client last saw; the server `UPDATE` is filtered on `.eq('updated_at', expectedUpdatedAt)`. Zero rows affected → a distinct `409` conflict response → the UI shows *"This Resource was updated by someone else. Reload before saving your changes."* with a Reload action, never a silent overwrite. Live-tested end-to-end (§U): a genuine two-save race correctly rejects the stale write and the first save's content survives.

**Version creation (spec §43):** every **manual** Save Draft and every **workflow submission** (editorial_review / approved / scheduled / published transitions) creates a `resource_post_versions` row; autosave never does.

## Q. Workflow

All transitions go through `POST /api/admin/resources/content/[id]/workflow` → `transitionResourcePostStatus()` → `public.transition_resource_post_status` — never a direct `status`/approval-column write (impossible anyway, since those columns are absent from the client's `UPDATE` grant and absent from `EditorSavePatch`'s type entirely).

| Role | UI action shown | RPC-enforced transition |
|---|---|---|
| Author (or any staff, if they're the creator) | Submit for Editorial Review | `draft/idea → editorial_review` |
| Editor | Approve Editorially (GREEN only) / Send to Compliance Review (AMBER) / Send Back to Draft | `editorial_review → approved` / `→ compliance_review` / `→ draft` |
| Compliance Reviewer | Approve Compliance Review / Send Back to Draft | `compliance_review → approved` |
| Publisher | Publish Now / Archive | `approved → published` / `→ archived` |

**Reason/Notes:** destructive actions (Send Back to Draft, Archive) open a small reason field, fed straight into the RPC's `p_reason`/`p_notes` and thus into `resource_workflow_history`.

**Error handling:** the RPC's `raise exception` messages (already specific and user-appropriate, e.g. *"AMBER content requires Compliance Reviewer approval, not editorial approval alone"*) are surfaced verbatim by `lib/resources/workflow.ts` — no raw Postgres stack trace ever reaches the UI (spec §74, unchanged from R1.1).

**Schedule was deliberately not implemented** (spec §70's own explicit allowance). The pre-implementation audit found `scheduled_at` absent from both the RPC's parameters *and* the column-scoped `UPDATE` grant — no client-facing role can set it under the current schema at all, and no scheduled-publishing worker exists. Opening a second migration for a column with no automation behind it risked exactly the confusion §70 warns about ("do not imply that content will automatically publish at that time"). Publish Now works cleanly today (the RPC sets `published_at` itself) and is offered instead, with an explicit note: *"Scheduled publication automation is not yet enabled — Publish Now takes effect immediately; there is no separate Schedule action in this release."*

**Workflow history** is shown read-only in the editor's Workflow panel (status, timestamp, actor role, reason) — reusing the exact `getResourceWorkflowHistory()` query R1.2 already built.

## R. Revision History

`createResourceVersion()` computes the next `version_number` per post (`SELECT max()+1`, retried once on the rare concurrent-save collision against the `uq_resource_post_versions(post_id, version_number)` constraint) and inserts a snapshot containing exactly the spec §44 fields (core metadata, content blocks, taxonomy mappings, CTA references, compliance classification, SEO) — no secrets, no audit metadata. Triggered on first save, every manual Save Draft, and every meaningful workflow transition (§43); never on autosave. An optional Change Summary field feeds `change_summary`. The `RevisionHistoryPanel` shows version number / timestamp / author ("you" vs "another editor", matching R1.2's existing precedent for not joining to a display name) / change summary, read-only. **Full restore is not implemented** — explicitly optional per spec §47, and listed in §AE.

## W. Accessibility

**Verified by code construction and by the automated test suite**, not by a live Tab-through session, for the same Browser-pane authentication limitation as §V:

- Every field uses `FormField.tsx`'s `TextField`/`TextAreaField`/`SelectField`/`CheckboxField`, each with a real `<label htmlFor>`, optional hint text wired via `aria-describedby`, and error text wired via `aria-describedby` + `aria-invalid` (spec §84/§121) — no placeholder-only input exists anywhere in the editor.
- Block controls (Move Up/Down/Duplicate/Delete) each carry a descriptive `aria-label` including the block type and index (e.g. *"Move Paragraph block 3 up"*, spec §86).
- Save status is an `aria-live="polite"` region, updated only on real state transitions (spec §85).
- `ConfirmDialog` (reused from the existing app, unmodified) already implements `role="alertdialog"`, `aria-modal`, Escape-to-cancel, and initial focus on the confirm button.
- Sidebar sections are native `<details>`/`<summary>` — keyboard-operable (Enter/Space to toggle) with zero custom JS.
- Headings never produce more than one logical hierarchy level per document — H1 is the page title (rendered outside the block editor entirely), body headings are typed `2 | 3 | 4` at the data-model level, making an in-body H1 structurally impossible rather than merely discouraged (spec §122).

**Not live-verified:** an actual Tab/Shift-Tab walkthrough with visible-focus screenshots, for the reason given in §V.

## X. Error / Loading / Empty States

- **Save failure** — distinct `error` state, retry control, exact server message shown (§M).
- **Stale record (409 conflict)** — distinct confirm dialog, never silently discarded (§M).
- **Workflow RPC rejection** — the RPC's own specific message surfaced, never a raw exception (§Q).
- **Missing/unauthorized Resource** — generic 404, identical for "doesn't exist" and "exists but you can't see it" (§S).
- **Invalid/duplicate slug** — inline field error, both on live "Check availability" and on save attempt (server re-checks regardless of whether the client called the check endpoint).
- **Zero content blocks / zero tags / zero additional categories / no CTA / no revision history** — every one of these renders an explicit, non-broken empty-state message (e.g. *"No revisions saved yet. The first Save Draft will create version 1."*, *"None available yet."* for empty author/tag/category pickers) rather than blank space or `undefined` text.
- **Initial load** — the editor page is a server component that fetches the full payload before rendering; there is no client-side "loading…" flash state to test, by construction (this mirrors R1.2's own server-component-first pattern).

## I. Import Architecture

- **Dry-run by default** (`npm run resources:import-r0a`, no flags): parses, validates, resolves taxonomy/slugs/CTAs, writes `artifacts/resources/r1-7-preimport-validation.json` + `docs/resources/R1.7-preimport-validation-report.md`, predicts insert/update/skip counts. **Zero DB writes.**
- **Apply** (`-- --apply --confirm-project=vqycarelcoijzwlpkpcz`): re-validates (aborts on any error), prints an explicit environment/project/row-count confirmation banner, then writes in two passes:
  - **Pass 1** (batched, 40 rows/batch): upsert `resource_posts` keyed on `content_id`. Not found → INSERT (status=draft, visibility=private, is_indexable=false, published_at=null, compliance_classification from Risk_Class). Found and unprotected → UPDATE metadata fields only (title/content_type/jurisdiction/difficulty/freshness_type/compliance_classification/visibility/is_indexable) — **never** touches `content_blocks` or `slug` on an existing row (content_blocks contains `crypto.randomUUID()`-seeded block ids that are non-deterministic across calls, so it is deliberately INSERT-only to keep re-runs a true no-op and to never overwrite a human's actual editorial work). Found and protected → skip, recorded with reason.
  - **Pass 2**: category/tag relationship upserts, run only after every post from Pass 1 exists (never relies on row order).
  - Provenance audit rows written last, batched.
- **Idempotency**: keyed on `content_id` (unique DB constraint is the hard backstop even if the pre-check ever raced — see §Y for a real transient anomaly this defended against). Running apply twice produced 218 inserted + 0 duplicated the first time it mattered, then 0 inserted / 218 reconciled / 0 duplicated on the real second run (live-verified, §N).
- **Human-edit-protection**: a row is protected (skipped, never overwritten) if `status` has moved past `draft`/`idea`, or `updated_by` is non-null. `updated_by` is a real FK to `auth.users` that the importer (service-role, no `auth.uid()`) never sets — only the real editor save path (`lib/resources/editor/mutations.ts`) ever sets it — making it a reliable, non-drifting signal. Proven with a real human-edit simulation using a genuine throwaway auth user (see §Y for why a fabricated UUID doesn't work here).
- **Manifest** (`artifacts/resources/r1-7-import-manifest.json`): source_file, source_hash, run_id, run_timestamp, environment, total_rows, inserted/updated/skipped/failed, post_ids, content_ids, `inserted_post_ids` (the rollback-safe set — only rows genuinely created by that specific run), created_categories/tags, warnings, per-row outcomes.
- **Rollback** (`npm run resources:rollback-r0a -- --manifest=<path> --confirm-project=...`): deletes only `inserted_post_ids` from one manifest, re-verifies each row's `content_id` is genuinely from that manifest immediately before deleting (defense against a stale/tampered manifest), relies on `ON DELETE CASCADE` (already present on every child table since migration 0033) for relationship cleanup, deletes matching `resource_audit_log` rows. Newly-created categories/tags are deliberately left in place (harmless, reusable taxonomy).
- **Verify** (`npm run resources:verify-r0a`): re-parses the workbook fresh (ground truth, not the manifest) and checks live DEV: presence of all 218 Content_IDs, no duplicates, exact per-type/jurisdiction reconciliation, zero `money_update` rows, Draft/private/non-indexable/unpublished defaults, zero fabricated `resource_videos` rows, anonymous-client leak checks (slug fetch + search RPC).

### AN.1 Root cause of the original blocker

The original report could not explain why `next dev` 404'd on `/resources/*` and any newly-added route. The closure pass root-caused it precisely:

1. Rebuilt in **production mode** (`npm run build`, exit 0) and started the server through the same MCP `preview_start` tool used throughout this project (`next start -p 3070`). **The exact same 404s reproduced** — `/resources`, `/sitemap.xml`, and even the brand-new `/r17-closure-login` QA route all 404'd, while `/contact`, `/login`, `/dashboard`, `/api/reference/goal-types` all worked. Response headers (`x-nextjs-cache: HIT`, `x-nextjs-prerender: 1`) and RSC payload inspection (`"c":["","_not-found"]`) proved the *framework's own root not-found* was being served, not the Resources-specific one — meaning these requests were never reaching Next's router/page-matching logic at all, despite `.next/server/app-paths-manifest.json` correctly listing every one of these routes as compiled (confirmed by direct inspection: `/(marketing)/resources/(browse)/page`, `/sitemap.xml/route`, `/r17-closure-login/page` were all present with full manifest artifacts).

This isolates the cause precisely: **the MCP preview-tool wrapper/proxy layer itself was intercepting or misrouting certain requests** (plausibly related to the shared, multi-worktree-agent nature of this sandbox host, evidenced earlier in the original session by browser tabs from other concurrent agents' worktrees appearing in this session's own tab list). It is not Next.js, not Turbopack, not `next dev` specifically, not the build, and not any R1.7 code — the same anomaly reproduced identically in both dev and production mode through the wrapper, and vanished completely bypassing it.

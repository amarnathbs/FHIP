## B. Closure Item B — Root cause

Next.js 16.2.12 (confirmed installed version). `app/(marketing)/resources/loading.tsx` implicitly wraps every nested route — including the dynamic `[slug]` and `topic/[slug]` pages — in a Suspense boundary. The framework must flush the loading-fallback HTML shell, committing a `200` status line, before an async page component's `notFound()` call can resolve. The correct not-found body still streamed in afterward, but the HTTP status could never become `404` while wrapped in that boundary.

**Diagnosis was verified by controlled experiment** (temporarily removing `loading.tsx` and confirming the status changed), not assumed from the prior report.

## C. Closure Item B — Fix

Moved the four listing pages (`page.tsx`, `glossary/page.tsx`, `videos/page.tsx`, `money-updates/page.tsx`) and `loading.tsx` into a new `(browse)` route group. Route groups are not part of the URL path, so no URLs changed. `[slug]/page.tsx` and `topic/[slug]/page.tsx` deliberately stay outside `(browse)`, so they are no longer wrapped in any shared Suspense boundary and can fully resolve their visibility/existence check before any response headers commit.

Confirmed via `git show 9253cfe --stat --name-status`: the 5 moved files are pure renames (`R100`, 0 content changes each). No changes to `lib/resources/public/visibility.ts` or any query logic. No service-role usage introduced.

# 2. Primary Objective
Implement production-quality content creation and editing for exactly these three Resource content types:
1. **Article**
2. **Guide**
3. **FHIP Explainer**
The result must allow authorised Resources staff to:
* create content;
* save drafts;
* edit existing content;
* build structured content using reusable blocks;
* manage core metadata;
* manage taxonomy;
* manage jurisdiction/difficulty/freshness;
* manage compliance classification;
* manage SEO metadata;
* manage review/publishing metadata;
* submit content into the approved workflow;
* perform role-permitted workflow transitions;
* view validation errors clearly;
* preserve revision history;
* avoid accidental content loss;
* safely navigate away from unsaved work;
* use the editor on desktop and tablet;
* maintain R1.1 security boundaries.

# 38. Autosave Strategy
Implement autosave only if it can be made reliable and visible.
Preferred:
* debounced autosave after meaningful changes;
* explicit save-state indicator.
States:
```text
Saved
Saving…
Unsaved changes
Save failed
```
Do not silently swallow save failures.
---
# 39. Autosave Failure
On autosave failure:
show visible feedback.
Example:
> Your latest changes could not be saved.
Provide:
**Retry Save**
Never tell the user "Saved" unless the server actually confirmed success.
---
# 40. Manual Save
Provide an explicit:
**Save Draft**
button even if autosave exists.
Users should never be forced to trust autosave exclusively.
---
# 41. Save Concurrency Protection
Consider stale-write protection.
At minimum:
* send current `updated_at`;
* detect if another editor has changed the record since it was loaded where practical.
If stale:
do not silently overwrite.
Show:
> This Resource was updated by someone else. Reload before saving your changes.
Do not implement complex collaborative editing.
---
# 42. Unsaved Changes Protection
If unsaved changes exist and the user navigates away:
show a warning/confirmation.
Do not interrupt navigation when everything is saved.
Use an accessible dialog/pattern.
---
# 43. Revision History
R1.1 created:
```text
resource_post_versions
```
R1.3 must activate meaningful revision snapshots.
Create a version on significant explicit saves.
Recommended:
* first saved draft;
* manual Save;
* workflow submission;
* pre-publish save.
Avoid generating a new version on every keystroke/autosave cycle.
---
# 44. Version Snapshot
Snapshot must contain sufficient state to reconstruct the Resource at that point.
At minimum:
* core post metadata;
* content blocks;
* taxonomy mappings;
* CTA references;
* compliance classification;
* SEO metadata.
Do not include secrets or irrelevant audit data.
---
# 45. Version Numbering

Prevent race collisions.

## A. Executive Summary

Implemented the complete R1.1 foundation: **20 new Resources tables in total** — 9 content/reference tables (`resource_posts`, `resource_categories`, `resource_tags`, `resource_authors`, `resource_media`, `resource_ctas`, `resource_sources`, `resource_faqs`, `resource_videos`), 6 relationship/join tables (`resource_post_categories`, `resource_post_tags`, `resource_post_sources`, `resource_post_faqs`, `resource_related_content`, `resource_context_links`), and 5 governance/workflow/config tables (`resource_user_roles`, `resource_post_versions`, `resource_workflow_history`, `resource_audit_log`, `resource_settings`) — RBAC (a new `resource_user_roles` table reusing the existing `admin_users` Super Admin concept), row-level security across every table, a column-level lockdown that makes a single `SECURITY DEFINER` RPC the only way to change a post's workflow status, the GREEN/AMBER/RED compliance workflow with a hard database-level backstop (not just application logic), workflow history, an audit log, revision-history and @GKTC video-metadata foundations, hand-authored TypeScript types (see §N for why), server-side permission/workflow helpers, and a database test suite. ## H. RBAC Implementation

- **Storage:** `resource_user_roles` (new table) + `admin_users` (existing, reused as Super Admin).
- **Permission helpers:** `lib/resources/permissions.ts` — server-only, reads `resource_user_roles`/`admin_users` via the request-scoped client (relying on their own self-read RLS policies), mirrors the SQL-side `private.*` functions' logic exactly so app-layer and DB-layer decisions never disagree.
- **Super-admin integration:** `admin_users` is checked first in every SQL helper function (`private.is_fhip_super_admin`) and every TS helper (`isSuperAdmin`) — a Super Admin automatically has every Resources capability without a duplicate row.
- **Role assignment protection:** zero INSERT/UPDATE/DELETE grant on `resource_user_roles` to any client-facing Postgres role (`authenticated`/`anon`) in R1.1. Assignment is service-role-only, exactly matching how `admin_users` already works — verified by test (§O, "role escalation denied").

## I. RLS Policies

Summarised in full in `docs/resources/R1.1-database-foundation.md` §4 (the RLS Access Matrix). In brief: public reference data (active categories/tags/authors/CTAs) is world-readable; `resource_posts` and everything joined to it follows one consistent predicate (`status in (published, review_due, archived) AND visibility in (public, unlisted) AND published_at <= now()`) for anonymous/ordinary-authenticated reads, with staff (any active Resources role, or Super Admin) additionally able to read every row regardless of status; workflow history, audit log, and role-assignment tables have no public or blanket-authenticated policy at all.

## J. Workflow Implementation

- **GREEN:** `draft → editorial_review → approved → scheduled/published`, editorial approval only.
- **AMBER:** `draft → editorial_review → compliance_review → approved → scheduled/published`; `approved`/`scheduled`/`published` require `compliance_approved_by`/`compliance_approved_at` to be set by a real Compliance Reviewer (or manager) — enforced in the transition RPC *and* as a table `CHECK` constraint.
- **RED:** can reach `compliance_review` but `scheduled`/`published` are structurally blocked by a `CHECK` constraint that holds even against a direct service-role write — no override path exists in R1.1, matching the brief's explicit instruction not to invent one.

---

## K. Compliance Enforcement

Two independent layers, not one:
1. **Application-level (the RPC):** `public.transition_resource_post_status` checks the caller's role and the post's `compliance_classification` before allowing any transition, with a specific error message per rule violated.
2. **Database-level (hard backstop):** `chk_resource_posts_amber_requires_compliance` and `chk_resource_posts_red_never_publishes` are table `CHECK` constraints — they fire even if someone bypassed the RPC and issued a raw `UPDATE` with elevated (service-role) privileges. Verified by test (§O, "RED never publishes").

Direct `UPDATE` of `status`/approval columns/`scheduled_at`/`published_at` is not possible for `authenticated` at all — `REVOKE UPDATE ON resource_posts FROM authenticated` followed by a column-scoped `GRANT UPDATE (...)` that excludes exactly those columns. The RPC is `SECURITY DEFINER`, so it alone can write them.

---

## L. Audit & Workflow History

Every successful status transition (via the RPC) writes one `resource_workflow_history` row (from/to status, actor, actor role, action, reason, notes) and one `resource_audit_log` row (entity type/id, action, actor, before/after JSONB state) atomically with the status change, in the same transaction — a partial failure cannot leave a status change unrecorded.

## Q. Security Findings

**Resolved:**
- Role self-escalation: no grant path exists for `authenticated` to write `resource_user_roles` at all.
- Status-bypass: column-level grant lockdown + RPC + CHECK-constraint backstop (three independent layers).
- RED publication: CHECK constraint holds even against a privileged direct write.
- `SECURITY DEFINER` search-path hijacking: every such function sets `search_path = ''` and fully qualifies every reference.
- Anonymous/logged-in-customer parity: the same read policy applies to both — no elevated access from merely being authenticated.

**Outstanding:**
- The migration has not yet been applied to DEV — every RLS/constraint/RPC claim above is verified by code review and the passing (unit-level, non-DB) test suite, but not yet by a live query against the real Postgres RLS engine. This is the single largest outstanding item; §O's "gracefully skipped" tests will exercise the real behavior the moment the migration is applied.
- No TypeScript types were generated from the live schema (hand-authored instead) — low risk (schema and types were written together, field-for-field), but worth closing when a CLI link becomes available.

## D. Database Changes

One migration: **`supabase/migrations/0039_resources_public_settings_read.sql`**.

The single genuine schema gap found (spec §131 D: "expected None unless a genuine gap requires a narrow migration"). `resource_settings` carries the seeded central disclaimer text (`default_disclaimer`, migration 0034) but had no RLS SELECT policy reachable by `anon`/ordinary `authenticated` at all — only a staff-only policy from migration 0033. Spec §57 requires reading the one centrally-managed disclaimer value rather than copy-pasting a hardcoded string into every component; without this policy, that would have been forced.

The migration adds one narrow, additive policy:
```sql
create policy "public read safe settings" on resource_settings for select
  using (key in ('default_disclaimer', 'youtube_channel_handle', 'youtube_channel_url'));
```
A fixed three-key allowlist — not blanket settings access — so nothing else that might later be added to `resource_settings` is silently exposed.

**Not yet applied to DEV.** This environment has no Supabase CLI project link and no direct Postgres connection string configured (only the REST API URL and anon/service-role keys, which cannot execute DDL) — the same documented constraint R1.1's own database-foundation doc records for migrations 0033/0034, with the same sanctioned fallback: paste the file into the Supabase Dashboard SQL editor for `vqycarelcoijzwlpkpcz`. **This is not blocking**: `getCentralDisclaimer()` (`lib/resources/public/queries.ts`) attempts the live read first and falls back to an identical hardcoded string (`DEFAULT_RESOURCE_DISCLAIMER` in `lib/resources/public/metadata.ts`) if the read returns nothing — covering both "migration not yet applied" and "row not seeded" — so the disclaimer renders correctly either way, from exactly one shared function either way. Confirmed live: the disclaimer displays correctly on every detail page today, via the fallback path.

No other schema changes. No changes to any R1.1–R1.4 table, policy, function, or grant.

## H. Public Visibility Model

The exact, audited rule, encoded in one place (`lib/resources/public/visibility.ts`) and used by every public query:

**Statuses treated as public:** `published`, `review_due`.
**Statuses treated as hidden:** `idea`, `draft`, `editorial_review`, `compliance_review`, `approved`, `scheduled`, `archived`.
**Content types excluded regardless of status:** `money_update_template` (positive allowlist of the other six types — fails safe against any future content_type this file doesn't yet know about).
**Also required:** `visibility in ('public','unlisted')`, `published_at is not null and published_at <= now()`.

**`review_due` (spec §10 — audited, not assumed):** the R1.1 workflow RPC (migration 0033/0035) only reaches `review_due` from a Publisher/Resource-Admin action on an already-published post, with no separate "unpublish" semantics anywhere in the schema or workflow history model. Decision: `review_due` represents previously-published content flagged for internal re-review, and **remains public**. Live-verified: a fixture pushed through published → review_due stayed fully visible by slug, in listings, and in the sitemap.

**`archived` (spec §11 — audited, not assumed):** the RLS policy itself technically permits reading `archived` rows (it is one of the three statuses in the "public read published posts" predicate). No R0-B document exists anywhere in this repository or was provided to this session defining an approved public archive experience. Per spec §11's own explicit default ("Preferred public behaviour: 404 for archived content unless the approved specification explicitly requires an archive"), R1.5's product-level policy is **narrower than what RLS would allow**: `archived` is excluded from every public query, and a direct request for an archived slug 404s exactly like a nonexistent one. This is a deliberate, documented application-layer tightening beyond the RLS ceiling, not a gap in it.

**`money_update_template` (spec §9 — the critical case):** the RLS predicate is keyed on `status`/`visibility`/`published_at`, not `content_type` — a template that somehow reached `status='published'` would pass RLS. The R1.5 application layer is the only thing standing between that and public exposure. Proven, not assumed: a template row was deliberately pushed to `status='published'` via direct write and confirmed, live, to never appear through any public query while its DB status independently reads `published`.

**`expires_at` (spec §12):** expired time-sensitive content is never auto-hidden or auto-unpublished — workflow state is never silently altered. If it remains legitimately published, a visible `FreshnessWarning` component renders ("This information may no longer be current," plus the last-reviewed/current-as-of date). No freshness state is fabricated when the underlying date fields are null.

## X. Public Security Tests

- **Anonymous visibility (spec §85):** Published Article/Guide/Explainer/Video/Glossary/Money Update — all visible, confirmed both via `getPublicResourceBySlug` (automated) and live browser rendering. Draft, Editorial Review, Compliance Review, Approved-unpublished, Future Scheduled, Money Update Template — all confirmed **not visible**, both via direct function call and live direct-URL request. Archived — confirmed not visible (documented app-level decision, §H). Review Due — confirmed **visible** (documented decision, §H).
- **Direct-URL tests (spec §86):** every hidden fixture's exact slug was requested directly (`curl`), not discovered via list filtering. Every one rendered the identical generic "We couldn't find that page" content with no distinguishing wording. **Known, disclosed defect**: the HTTP status line for all of these (and for a genuinely nonexistent slug, tested identically) reads `200 OK`, not `404`. Root-caused: this is not specific to R1.5's routes — even Next's own `_not-found` fallback correctly returns `404` for a truly unmatched URL, but a *programmatic* `notFound()` call from within an async page/`generateMetadata` in this Next.js version (16.2.12) does not retroactively change an already-streamed response's status line. Tried the standard documented workaround (raising `notFound()` from `generateMetadata` as well, which resolves before the body streams) — verified live via `curl -D-` that it does **not** fix the status code in this version, so left in place as still-more-idiomatic but not claimed as a fix. **Why this does not block FULL PASS:** (a) the actual security property spec §71 cares about — identical treatment for hidden vs. nonexistent, no "this exists but isn't published" leak — is fully intact, proven identical for both cases; (b) the `noindex` meta tag is present in the response regardless of the status line, so a JS-rendering crawler (which is what matters for real-world indexability) still will not index it; (c) no FAIL condition in spec §130 is met (no content leaks, no RLS bypass, no unsafe execution). Classified P2 (technical-correctness/SEO-hygiene, not a security or content-leak defect) and documented for the Product Owner's own judgement rather than hidden.
- **Money Update Template (the critical test, spec §9):** a template row deliberately pushed to `status='published'` at the database layer — confirmed absent from every public query and from direct-slug lookup, while independently confirmed `published` in the database. This is the proof that the R1.5 application layer, not RLS alone, is what stops it.
- **XSS (spec §83):** a literal `<script>alert('R1.5')</script>` string stored in an Article paragraph block rendered as inert visible text on the live page; no alert dialog fired; no console error. Structurally guaranteed by `BlockRenderer`/`richtext.ts`'s design (no HTML parser anywhere in the render path), not merely tested-and-hoped.
- **Unsafe source URL (spec §96):** a `javascript:` URL source, inserted directly (bypassing the editor's own creation-time validation, specifically to test the render-time defence), never appears as an executable link — the literal string `javascript:` is absent from the rendered HTML entirely.
- **Video embed (spec §92):** iframe `src` confirmed, live, to always be `https://www.youtube.com/embed/<validated-id>` — no arbitrary iframe possible (the embed component has no `src` prop).

## Z. Performance / Query Behaviour

- List/card queries select metadata columns only; detail queries load what a single reader needs (§S).

## AF. Technical Debt

- **Not-found HTTP status code** (§X/§AC) — a Next.js 16.2.12 framework-level characteristic affecting any programmatic `notFound()` call from an async page component in this app, not unique to R1.5. Worth a dedicated framework-level investigation (e.g. `generateStaticParams` + ISR restructuring, or waiting for a Next.js patch) in a later phase; not attempted further here to stay within scope.

Correct and simple for this phase's traffic and freshness requirements; a caching strategy (ISR, `revalidate`, or a CDN layer) is a reasonable future optimisation once real traffic patterns exist, deliberately deferred rather than over-engineered now (spec §109).
- **Optional reading-time indicator** (spec §56) — not implemented; explicitly optional and non-blocking per the spec's own text.
- **Per-category public counts** (§S) run as a handful of small parallel `count` queries rather than a single grouped query — acceptable at the current foundation-taxonomy scale (spec §22's own "if inexpensive/safe" allowance); would want revisiting if the taxonomy grows into the dozens.
- **migration 0039 not yet applied to DEV** (§D) — non-blocking (graceful fallback in place) but should be applied via the Supabase Dashboard SQL editor before relying on the DB as the actual source of truth for the disclaimer text going forward.

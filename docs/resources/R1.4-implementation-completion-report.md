## H. @GKTC Video Architecture

YouTube remains the only video host. `parseYouTubeVideoId()` (`lib/resources/video/youtube.ts`) never makes an outbound request — pure `URL` parsing, protocol-gated to `http(s)` only. The embed component (`YouTubeEmbed.tsx`) takes only a `videoId` prop — there is no code path through which an arbitrary iframe URL can reach the DOM. No YouTube API key, no MP4 upload, no transcoding, no automatic channel sync anywhere. "Hosted on @GKTC YouTube" / "Watch on YouTube" copy appears in the list empty-state, the new-video form, the editor, and the preview.

## I. Video List

Server-paginated (25/page, clamped 100 max, reusing R1.2's `ResourcePagination`), searches title/YouTube ID, filters by status/jurisdiction/compliance. List query selects metadata only — verified live and by a dedicated unit test that no returned item carries `transcript`/`chapters` (spec §124).

## J. Video Editor

Fields: title, slug, excerpt, duration, YouTube publish date, thumbnail URL (defaults to the YouTube-derived `hqdefault.jpg`, overridable), @GKTC channel handle/URL, embed-enabled toggle, transcript (plain textarea, manual paste only), chapters (add/move-up/move-down/delete, each with `aria-label`, timestamp format validated). No `content_blocks` body — Video's spec §17 field list has no long-form structured content, so this was deliberately omitted rather than force-fit into the Article block model.

## K. Video Preview

`/admin/resources/videos/[id]/preview`, admin-only. Embed URL is always `buildYouTubeEmbedUrl(videoId)` — derived, never accepted raw. iframe carries a meaningful `title` ("@GKTC video preview: {title}"). An invalid/missing video renders the exact required message: "This YouTube video cannot be previewed. Check the Video ID or URL." — never an iframe.

## L. Glossary Management

Term → `title`, Short Definition → `excerpt`, Detailed Explanation/Example → `content_blocks` (R1.3's `BlockEditor`, unmodified — optional per spec §28), Aliases → new `aliases text[]` column with a chip editor, Related Terms → `resource_related_content` reused as-is (self-reference/duplicate-pair already blocked by its own DB constraints). Duplicate protection: an exact case-insensitive match hard-rejects the save; a substring match warns (debounced check-as-you-type) without blocking.

### AI.1 Environment note: a Browser-pane rendering quirk, not an app defect

Before any of the cells below could be tested, this pass hit a new environment quirk in the sandboxed Browser-pane proxy — a different flavour of the same category R1.3/R1.4's own closure passes already documented for the dev server's HMR websocket. Two related symptoms, both traced to the same root cause and both confirmed **not** to be application defects:

1. **Next.js's streaming-SSR reveal never fires on a cold full-page navigation.** The server correctly streams the real content (confirmed via a raw `fetch()` of the same URL, which always returned the complete, correct HTML including its trailing `$RC(...)` reveal script), but the Browser-pane tab's own rendering of that exact same response stays stuck showing the `loading.tsx`/Suspense fallback skeleton indefinitely. Root cause, confirmed by direct experiment: the reveal script's `$RC`/`$RV` handshake schedules the actual DOM swap via `requestAnimationFrame`, and rAF never fires in this tab because — per the Browser pane's own `screenshot` tool, which fails with "the Browser pane is not displayed, so the page is not compositing frames" — the tab is not actively compositing. Manually invoking `window.$RV(window.$RB)` from the console (the exact function the browser's own reveal script would have called) immediately produces the correct, fully-rendered page every time.
2. **A client component's very first `useEffect`-driven data fetch on a cold navigation sometimes never flushes**, for the identical reason — React's effect flush is gated behind the same paint cycle. Confirmed non-defect: the underlying API endpoint always returned correct data when called directly, and the exact same fetch logic, re-triggered by any subsequent real state change (e.g. typing into the list's search box), rendered correctly every single time thereafter.

Every navigation in this pass therefore ran a small, standard console snippet immediately after `navigate()` — `if (window.$RB && window.$RB.length) window.$RV(window.$RB)` for streaming pages, plus a trivial input-driven state change for client-fetched list pages — before evaluating the page.

## What changed since CONDITIONAL PASS

The main implementation report (`R1.6-implementation-completion-report.md`) issued CONDITIONAL PASS with exactly one blocker: migration `0040_resources_discovery_context_support.sql` could not be applied from this sandbox.

The Product Owner's first application attempt hit a genuine Postgres error — `42P17: generation expression is not immutable` — on the `search_vector` generated column. Root cause: `to_tsvector('english', ...)` cannot be written directly inside a `GENERATED ALWAYS AS (...) STORED` expression; the 2-argument `to_tsvector(regconfig, text)` is itself `IMMUTABLE`, but resolving the `'english'` literal to a `regconfig` OID is a catalog lookup the generated-column validator won't accept as provably immutable (a well-known, schema-independent Postgres limitation). Fixed (commit `59e8724`) by wrapping the computation in a new `resource_posts_search_vector()` SQL function explicitly declared `IMMUTABLE` — the generated column now calls that function instead of inlining `to_tsvector()`. Zero behavioural change to the resulting tsvector values or weights.

The corrected migration was applied successfully to DEV (`vqycarelcoijzwlpkpcz`) by the Product Owner.

# Risk-free "confirmed through" date: root cause, fix and evidence (19-10-2026)

Branch `fix/risk-free-verified-through-20261019`, written against `origin/main` `44ff8d6` and rebased on `origin/main` `7b26956` (no conflicts; the 12 risk-free suites were re-run on the rebased tree, 242 tests green). Nothing pushed, nothing merged, nothing applied anywhere. Evidence labels used below: **UNIT** (no database), **PGLITE** (the real service code and the real migration SQL in an in-process Postgres, as the `authenticated` role; not DEV, not production), **not performed** (stated as such).

## 1. The observation and the answer in one paragraph

On 19-10-2026 the repo series (`RBI_POLICY_REPO_RATE`) still showed `verified_through_date` 02-10-2026 after the rate file (one row, 07-10-2026, 5.50, already committed) was submitted again with "Verified through" 19-10-2026, and the T-bill series also showed 02-10-2026. **The code path that moves the date works.** Run end to end with the real functions on the real production function body (migration 0260 alone), it moves the date in both cases the Product Owner could have been in. So "the update failed" is **not** the cause. What the path got wrong are four traps the screen hid, and any of the first two would produce exactly "the date stayed at 02-10-2026 and nothing told me": a **UTC "today"** that refuses an operator's own day, and an **answer that never says whether the date moved**. I could not prove from the repository which of the two happened on 19-10-2026 (production was not accessed); read-only SQL `P2`, `P3` and `P4` settle it from facts (section 4). The fix does not depend on which one it was.

Candidate causes from the brief and what the evidence says:

| Candidate | Result |
|---|---|
| same-file branch needs a matching hash recorded against another series or row set | the unique index is per (series, hash); a different hash simply takes the normal branch (case B), which also moves the date. Ruled out. |
| preview/commit returns a no-op | `noop` needs `plan.verifiedThrough === null`, i.e. no date reached the server; with a typed date it does not fire (case A). Ruled out for a typed date. |

| Upload button when 0 new rows | `canCommit` only needs no blockers; with 0 new rows and a date it is true (case A). Ruled out. |
| `greatest()` semantics | forward only, correct (case B and case C). Ruled out. |
| same-file update only when `< p_verified_through` | correct and intended; an equal or earlier date is a silent no-op (trap 1). |

Not provable offline. |

**Observed vs intended.** Intended: a governed, attested, audited confirmation of the date for the repo series, forward only, with an answer that says what it did. Observed: the update path itself is sound; the operator is told "Uploaded" when the date did not move, a morning-of-the-day date is refused as "future" without naming the server day, a weekly series stores a meaningless date, a stale field travels between series, and confirming "no change" requires a data file plus a data attestation (an act that should not exist for "no data changed").

## 3. The fix. Migration 0294 (PGLITE) and the screen (UNIT)

**Migration `supabase/migrations/0294_nav2_risk_free_confirm_verified_through.sql`** (next free number: 0286, 0289, 0290, 0292, 0293 are taken on other branches, 0285 is the highest on main; scanned 19-10-2026 across every ref and worktree; re-check at merge). Functions only: no table, row, constraint or CHECK is touched, so the drop-and-recreate constraint trap does not apply; 0260 is not edited (its immutability and the part-equality test are intact). Passes the editor-safety lint.
- `risk_free_today()`: the Asia/Kolkata calendar day. Used by every "not in the future" rule.
- `confirm_risk_free_verified_through(series, date, reason)`: the dedicated control. SECURITY DEFINER, fixed search_path, `auth.uid()` and `is_risk_free_data_admin()` checked inside (42501), execute revoked from public and anon. Refusals (22023, each with a sentence): reason under 20 characters; unknown series; **weekly series**; a day after the India day (names the day); a day before the last published rate; **a day not later than the one already recorded (never a silent no-op)**; a series with no published rate. It changes no rate and no batch. It writes one append-only state-log row: actor, time, both dates, the reason.
- `commit_risk_free_upload` replaced by `create or replace` with exactly three changes (a test diffs the code lines against 0260: 10 lines removed, 21 added, none a validation, attestation, hash, conflict or insert line): the future rule uses `risk_free_today()`; a weekly series ignores a verified-through date; the answer adds `verified_through_moved` and `verified_through` (the existing key `verified_through_recorded` is kept).

**Application code.**
- New route `app/api/admin/investment-intelligence/risk-free-data/confirm-current/route.ts` (upload capability, caller's session client, authorises before reading the body; a 22023 sentence is returned as 422; 42501 as 403; a missing function as 503 naming migration 0294).
- `riskFreeToday.ts`: the India day, used by the status read and the upload route (previously UTC).
- `riskFreeUploadService.ts`: a weekly series drops the date with a warning and does not send it; the future blocker names the India day; a warning when the entered date is not later than the recorded one; the outcome carries `verifiedThrough {requested, moved, current}` (`moved` null when the database still runs the 0260 function, shown as "not reported", never guessed).
- Screen `RiskFreeDataClient.tsx`: new box "Confirm the repo rate is still current" (upload capability, day-first date, reason of at least 20 characters, the same rules checked before the press, result directly under the button); the "Verified through" field is **cleared when the series changes** and an amber warning appears when a date is typed for the T-bill series; the upload result now says "The series is now confirmed through DD-MM-YYYY" or, as an error, "The confirmed-through date was NOT changed: ... already confirmed through ..."; an already-uploaded file no longer reports the original batch counts as rows written; the history list labels a confirmation line.

**Is the stored T-bill 02-10-2026 harmless?** Yes (UNIT, same test file): `riskFreeObservationOn` ignores `verifiedThroughDate` for a `weekly_auction` series (identical result with and without it); `riskFreeFreshness` measures a weekly series from the last observation; the monitoring snapshot (0262) computes days since the last observation for a weekly series and only echoes the date. One side effect: it is part of the dataset version digest (`datasetVersion`), so it changes a cache key, not a number. Leave it.

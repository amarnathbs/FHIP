# 6. Rollback, feature by feature

**Principles (apply to every row).** (1) Each feature has its own controls; one switch does not stop everything. (2) Rollback never deletes
canonical user data: accepted statements, payslips, transactions and holdings stay. (3) The **spending cap and the security controls are
preserved**: no rollback step drops `aie_reserve_ai_cost_v2`, the cap columns, or the Module 11 limit tables; never recommend dropping them as a routine
rollback. (4) A change to an Amplify variable takes effect **only on the next build**. A database switch takes effect on the next request.
(5) Never turn the real malware scan off to "stop" something: with it off the AI reading refuses, but every upload falls back to structural
checks only. That lowers security and is not a rollback.

## Order for an incident ("stop the spending now")

1. `sql/ops/O02a` (document AI: no deploy, immediate). For Module 11 run `M11_90` block STOP 2.
2. Read `sql/A02` and `sql/E05` to see what happened and who.
3. Decide the fix; restore with `O02b` (type the value `A02` showed before) and the Module 11 RESTORE blocks.
4. Only then, if needed, the Amplify switches (they need a build).

## G6.026 — User disclosures

**Repository owner:** `lib/engines/investment-intelligence/tax/disclaimer.ts` (disclaimer text constants), `lib/engines/investment-intelligence/tax/residency.ts` (NRI-flagging logic), `lib/engines/investment-intelligence/tax/taxOrchestrator.ts` (wiring), `lib/services/investment-intelligence/taxRepository.ts` (persistence of `ii_tax_profiles`), `components/investment-intelligence/TaxIntelligenceClient.tsx` (UI), `app/(app)/investment-intelligence/tax/page.tsx` and `app/api/investment-intelligence/tax/summary/route.ts` (surface). Canonical country ownership itself lives in `lib/services/jurisdiction.ts` (`AUTHORITATIVE_COUNTRY_CODES`, `FULL_EXPERIENCE_COUNTRY_CODES`) and `lib/services/countryGate.ts`.

**Findings:**
- No disclosure/explanatory copy in `lib/engines/reportSections.ts` (Free tier) names a specific regulatory body. `lib/engines/reportSectionsPremium.ts` has one country-named gate: the `tax_and_cost` chapter (line ~740) is explicitly "India tax-and-cost intelligence."
- The only jurisdiction-naming disclosure text in the app is in `lib/engines/investment-intelligence/tax/disclaimer.ts`: `TAX_SIMULATION_DISCLAIMER` ("Indian capital-gains tax rules..."), `NRI_SCOPE_DISCLAIMER` ("Resident-taxpayer estimate only — NRI-specific rules... are not modelled"), and `PLACEHOLDER_RULE_DISCLAIMER` — all explicitly name India, not the user's own country, so they are not literally misleading on their face.
- **Whether NRI_SCOPE_DISCLAIMER is suppressed is driven entirely by a self-declared, per-module field (`ii_tax_profiles.taxpayer_type`), never cross-checked against the canonical `country_of_residence`.** `lib/services/investmentIntelligenceReportData.ts:109-114` derives `residencyProfile` solely from `taxProfile.taxpayerType`; `lib/engines/investment-intelligence/tax/residency.ts:27-46` (`checkResidency`) fails safe (flags NRI) only when the field is unset/unknown/garbage — if a user (in any country, including a FULL_EXPERIENCE country like AU that has cross-border holdings) explicitly selects "Resident individual" or "Resident HUF" from the dropdown in `TaxIntelligenceClient.tsx:91-96`, the NRI disclaimer is suppressed with **no comparison to their actual `country_of_residence`**. The UI copy at `TaxIntelligenceClient.tsx:200` explicitly discloses this design choice ("Set explicitly by you — never inferred from your address, nationality, or portfolio country"), so this is a deliberate decoupling, not an oversight — but it also means there is no consistency guard between the self-declared flag and the authoritative country field.
- **The GENERIC-country-user scenario the checklist asks about is currently blocked at the access-control layer, not by disclosure logic.** Every Reports route (`app/api/reports/route.ts`, `[id]/route.ts`, `availability/route.ts`, `generate/route.ts`) and the tax summary route import `requireCountryConfirmedUser` (`lib/api.ts:53-68`), which delegates to `lib/services/countryGate.ts`'s `countryConfirmationBlockResponse`. Per `lib/api.ts:70-92`, this refuses **GENERIC-experience users (GB/US/SG/AE)** with a 403 `GENERIC_EXPERIENCE_RESTRICTED` for "every financial module, every domestic calculation... reports... until G4." So a true GENERIC-experience user cannot reach the Reports module, the tax chapter, or the disclosure copy at all today — this is **implemented but unreachable** for that user population, by design, not accidentally.
- Residual, live-reachable gap: a FULL_EXPERIENCE country user (AU, or IN with a cross-border/NRI declaration) who mis-selects the taxpayer-type dropdown could see India-framed disclaimer copy with the NRI caveat suppressed, unchecked against their real country_of_residence — no test covers this cross-field consistency (see `tests/unit/iiR6FinalTaxpayerContext.test.ts`, which only tests the pure `resolveTaxpayerContext`/`checkResidency` functions in isolation, never against a household's actual country).
- Onboarding and Dashboard surfaces: no country-named regulatory disclosure copy found in `app/(onboarding)/**` or `lib/engines/dashboard.ts`.
- **Multi-country dimension:** no disclosure mechanism exists today that is keyed off "household has assets in more than one country" — the only per-instrument multi-country awareness is `country_of_domicile` on `ii_instruments` (used for scheme classification), not surfaced as a disclosure. This is a **new requirement** for G6/multi-country specifically.

Classification: **partially wired** (disclaimer text itself is well-scoped and honest; the residency/self-declaration path is a live, uncovered gap for FULL_EXPERIENCE users; the GENERIC-user version of the risk is currently **implemented but unreachable** due to the country gate).

## G6.027 — Calculation reconciliation

**Repository owner:** no single owner — reconciliation logic is spread per domain: `lib/financial-data-hub/bank-csv/reconciliation.ts`, `lib/financial-data-hub/investment/{cashReconciliation,holdingsReconciliation}.ts`, `lib/financial-data-hub/liability/statementReconciliation.ts`, `lib/financial-data-hub/payslip/reconciliation.ts`, `lib/financial-data-hub/retirement/{reconciliation,payslipReconciliation}.ts`, `lib/services/investment-intelligence/reconciliation.ts` + `reconciliationConfig.ts`. Independent "oracle" scripts live under `scripts/` per phase (see below), all written ad hoc for that phase's certification.

**Findings:**
- `tests/unit/lrFi2HouseholdDebtRatios.test.ts` is **not** an independent oracle — it imports and calls the real production functions (`computeDashboard`, `previousDebtToIncome`, `applyScenario`, `runNetWorthForecast` from `lib/engines/dashboard.ts`/`reportSections.ts`/`whatIf.ts`/`forecast/netWorthCalculator.ts`) and asserts against hand-computed literal arithmetic (e.g. `400000 / 96000`) plus positive/negative controls (`withSmsf` vs `withoutSmsf` vs a `retagged` mis-tagging negative control, lines 71-144). This is a "source-level guard" pattern (inline expected-value math + control fixtures), not a separate re-implementation.
- A genuinely independent, cross-language oracle does exist, but only for one phase: `scripts/r12-certification/r12_independent_multiasset_oracle.py` — its own header states it "Deliberately does NOT import any production TypeScript code... a fresh, independent re-derivation." It writes `r12_oracle_results.json`, consumed by `tests/unit/iiR12IndependentOracle.test.ts`, which runs the same case list through real production engines (`resolveInstrumentIdFromIdentifiers`, `computeDisposalTax`, `calculatePortfolioLookThrough`, etc.) and diffs with pre-declared tolerances (line 16-18 of the test: currency 0.01, units 1e-6, exact for classification/booleans).
- This "independent oracle + comparison test" **pattern is repeated but never shared as a library**: `scripts/ii-r4-certification/`, `ii-r5-certification/`, `ii-r6p1-certification/` each have their own `generate_cases.mjs` + `cases.json` + `oracle_results.json` + `comparison_report.json`; similarly `tests/unit/r11IndependentOracleComparison.test.ts`, `r11ProfessionalSecurityOracleComparison.test.ts`, `fdh7ApprovedSummaryOracle.test.ts`, `fdh14_golden_household_e2e_oracle.mjs`, `r10_visual_cert_generate.mjs`. There is no shared `lib/testing/oracle*` or `tests/support/oracle*` module — `tests/support/` only contains PDF/fixture builders (`buildBankPdfFixture.ts`, `buildEncryptedCamsPdf.ts`, `buildMinimalPdf.ts`, `importBridgeMemoryStore.ts`), not oracle/diffing infrastructure.
- Dozens of one-off `scripts/*_certification.mjs`/`.ts` files exist (60+ counted under `scripts/`), each named for its own phase (fdh1 through fdh16, r7 through r12, g1/g2/g3/g5/g5b, admin_a02 waves, mcc/mcc14, air_consolidation, ii_r9). No common CLI/harness/runner ties them together — each independently reads its own JSON fixtures and does its own comparison logic.
- **Conclusion: there is no general-purpose reconciliation harness. Each phase builds its own one-off**, following a repeated but unenforced convention (cases.json / oracle script / comparison test triad).

Classification: **stale/dead** is not right — these are **live and connected** (many are still referenced by passing test suites), but the checklist's premise ("general-purpose harness") is a **new requirement**: none exists.

## G6.028 — Failure and rollback

**Repository owner:** `supabase/migrations/*.sql` (131 files total, `0001_foundation.sql` through `0136_lr13_family_trust_entity_type.sql`).

**Findings (sampled/verified across the full history, not just ~10):**
- A precise, colon-delimited `-- ROLLBACK: <sql>` single-line convention appears in exactly **5 files**: `0130_g5b_mcc14_delete_cascade_exemption_fix.sql`, `0132_lr9_account_closure.sql`, `0133_lr10_payment_operationalisation.sql`, `0134_lr11_business_entity_registry.sql`, `0136_lr13_family_trust_entity_type.sql` — all from the most recent G5B/LR development phase (2026-08/09).
- A looser `-- Rollback notes (manual — this repo has no down-migration runner): ...` block convention appears in exactly **2 files**: `0049_reconcile_phase0c_resources_lineage.sql` (a "RE-EMITTED FROM ARCHIVED HISTORICAL MIGRATION" consolidation file, i.e. re-authored later, not an original early-era artefact) and `0129_g5b_generic_universal_module_write_enablement.sql`.
- **7 of 131 migrations (~5%) carry any real rollback documentation**, and all 7 cluster in two points: the Phase-0C historical re-consolidation (0049) and the G5B/LR phase from 0129 onward. Even within that recent cluster it is not universal: `0131_lr3_bank_import_surplus_bridge.sql` and `0135_lr1_document_purge_sweep_scheduler.sql` have **no** rollback comment at all.
- Verified false positives that could be mistaken for the convention: `0090_smsf_current_balance_integrity_guard.sql` ("commit/rollback" — describing Postgres transaction semantics), `0107`, `0116`, `0118`, `0125` (all use the word "rollback" to mean transaction rollback, an unrelated SQLSTATE class name, or references to unrelated cleanup scripts under `scripts/resources/`) — none of these document how to undo their own migration.
- Sampled broadly across eras: `0001_foundation.sql`, `0010_module9_reports.sql`, `0020_recommendations_data_import.sql`, `0030_contact_submissions.sql`, `0040_ii_r2_transaction_lineage_and_dedup.sql`, `0050_fdh2_taxonomy_mcc_foundation.sql`, `0060_ii_r6_final_reference_seed.sql`, `0070_ii_r10_reports_authoritative_write_hardening.sql`, `0080`-range, `0100_app_review_tier2_india_retirement_catalogue.sql`, `0110_module11_ai_foundation.sql`, `0120_fdh15_income_member_mismatch_guard.sql` — **zero** rollback documentation in any of them.
- **Conclusion: rollback documentation is NOT a consistently-applied convention across the whole migration history.** It is a recent practice (last ~7 migrations of 131, i.e. the final ~5%), introduced only in the current G5B/LR development wave, with one earlier one-off exception in a historical re-consolidation file. Early- and mid-history migrations (roughly 0001-0128, minus the 0049 exception) have no established rollback-documentation convention at all.

Classification: **partially wired** (a real convention exists and is followed in the newest files, but it is not retroactively applied and does not cover the whole history — establishing it repo-wide for the country-programme's migrations would be a **new requirement**, not an extension of an existing universal practice).

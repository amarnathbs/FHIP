## G7.004 — Reporting currency and date

**Files traced**: `lib/services/reportSnapshotResolver.ts:228, 377-378, 383-384`, `lib/services/reportsData.ts:150, 200, 206`, `lib/validation/profile.ts:32`, `supabase/migrations/0010_module9_reports.sql:57-58, 66`.

**Currency**: At generation time, `resolveReportSourceData` reads `user_profiles.preferred_currency` **live and fresh** for that generation call (`reportSnapshotResolver.ts:207, 228`: `const currency = (profileRes.data?.preferred_currency as 'AUD' | 'INR') ?? 'AUD'`) — not cached, not derived from country. This value is then **frozen** onto the immutable `reports.reporting_currency` column at insert time (`reportsData.ts:150` for the failed-eligibility path, `reportsData.ts:206` for the success path: `reporting_currency: source.currency`). Because `reports` rows are immutable/versioned (comment at migration line 44-46: "Published reports are immutable; corrections create a new row... linked via `revises_report_id`"), **a report generated last month keeps the currency that was current at the moment it was generated — it does NOT retroactively change if the user's `preferred_currency` changes afterward.** Every render path (`ReportPreview.tsx`'s `currency` prop, passed from the stored `report.reporting_currency`/`ReportRow`, not re-fetched from the live profile) confirms this: the component takes `currency: 'AUD' | 'INR'` as a prop sourced from the persisted row, never re-queries `user_profiles`.

Both `ReportSourceData.currency`, `ReportProfile.preferredCurrency`, `reports.reporting_currency` (`char(3)`), and `lib/validation/profile.ts:32`'s Zod schema (`z.enum(['AUD', 'INR'])`) are hard-typed to exactly two currencies — there is no GBP/USD/SGD/AED support anywhere in the Reports pipeline, consistent with Reports generation being blocked for GENERIC-experience countries at the API layer (`app/api/reports/generate/route.ts:1` uses `requireCountryConfirmedUser`, which — per `lib/api.ts:53-68` and `lib/services/countryGate.ts:337-339, 493-495` — refuses `GENERIC_EXPERIENCE_RESTRICTED` users by default; Reports is not among the explicitly-allowlisted generic-safe surfaces documented in `lib/api.ts:82-89`).

**"As of" date**: `source.asOfDate = new Date().toISOString().slice(0, 10)` (`reportSnapshotResolver.ts:377`) — this is **the wall-clock date the generation call runs**, not the last day of `reportMonth`, not a data-freshness timestamp, and not derived from any underlying financial-snapshot date. It is stored verbatim to `reports.as_of_date` (`reportsData.ts:147, 200`) and displayed on the cover as "Financial position snapshot: {formatSnapshotDate(report.as_of_date)}" (`ReportPreview.tsx:230`). Because report generation can be triggered for a past `reportMonth` (the route only rejects a *future* month, `app/api/reports/generate/route.ts:11-13`), a report for e.g. July 2026 generated on 8 September 2026 would show "Financial position snapshot: 8 September 2026" while its `report_month` reads July — an internal inconsistency that is a pre-existing, structural property of the resolver, not something G7 introduces.

**Classification**: currency freeze-at-generation = **live and connected**, and correctly answers the master question ("no, a report generated last month would NOT show a different currency later"). The AUD/INR-only ceiling on the entire currency type chain = **live and connected as a scope boundary**, consistent with the GENERIC-country block, not a bug — but widening Reports to GB/US/SG/AE would require touching `ReportProfile.preferredCurrency`, `ReportSourceData.currency`, `reports.reporting_currency`'s check assumptions, `reportContentData.ts:currencyName(code: 'AUD'|'INR')`, and `formatMoneyWhole`, making this a **new requirement** with no partial scaffolding beyond the type alias itself. The `asOfDate` = generation-wall-clock-date (not tied to `reportMonth` or a real snapshot date) is **live and connected** but its potential mismatch against `report_month` for back-dated generation is worth flagging as a pre-existing lineage/audit-trail characteristic — not caused by, or requiring correction from, G7.

**Cross-cutting notes (not a fifth topic, but relevant to all four)**:
- **Canonical ownership**: `country_of_residence` itself is canonically owned by `user_profiles` + `lib/services/countryGate.ts`/`lib/services/jurisdiction.ts` (per G3, per that file's own header comment). Reports does not own or duplicate this — it reads it once, live, at generation time into `ReportProfile.countryOfResidence`, uses it in exactly one place (`stress_testing`'s `homeCountry`), and never persists it onto the `reports` row itself (no snapshot/audit lineage for country, unlike currency which is frozen).
- **Currency vs. country substitution**: only one defended/tested boundary exists in the entire Reports module (`stress_testing`'s currency_shock note, backed by `reportSectionsPremiumStressApplicability.test.ts`). Everywhere else in Reports (Free tier entirely; Premium's `cross_border_full`, `investment_analysis` "by country" split, `tax_and_cost`'s implicit India assumption) there is no explicit rejection of currency-as-country-proxy because country is never consulted there at all — the risk is latent (an AU-resident-reporting-in-INR household, or vice versa, would still get factually correct country-code-keyed breakdowns since those come from each row's own `country_code`, not from `preferred_currency`).
- **Cross-tenant / failure-injection coverage**: `getReport`/`archiveReport`/`publishReport` in `reportsData.ts` all scope by `.eq('user_id', userId)` from a caller-validated session; `getReportByRenderToken` (line 368-384) is the one path with no `user_id` check, authorized instead by a short-lived `render_token` match against `report_exports` — by design, for the headless PDF renderer. No dedicated cross-tenant or render-token-forgery test file exists under `tests/unit/` (searched for `*tenant*`, `*render*token*` — none found), so this is **cannot verify** as tested, though the code shape itself appears sound on inspection.
- **Generic-country reports**: today no GB/US/SG/AE user can reach `/api/reports/generate` at all (blocked pre-country-gate), so G7.001-004's "unresolved path" question is moot in the current codebase — Reports is architecturally AU/IN-only via the API gate, not via any in-module country branch.

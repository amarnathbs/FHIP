## G6.022 — Country-change interaction

**Owner today:** G1 (`supabase/migrations/0122_g1_country_foundation.sql`), consumed by `app/api/user/primary-country/{preview,confirm}/route.ts`, `app/api/user/billing-country/confirm/route.ts`, `app/api/user/country/confirm/route.ts` (G3, migration `0127`), `app/api/user/profile/route.ts` (`PUT`), and gate logic in `lib/services/countryGate.ts`. Tests: `tests/unit/g1CountryFoundation.test.ts`, `scripts/g1_country_foundation_pglite_certification.mjs`, `scripts/g1_country_foundation_live_dev_certification.mjs`.

**What `confirm_primary_country_change()` actually touches** (migration `0122`, lines 441–572): it locks and updates exactly `user_profiles.primary_country`, `.primary_country_source`, `.primary_country_set_at`, and conditionally `.preferred_currency`, plus one `audit_events` insert (`PRIMARY_COUNTRY_CHANGE`). It never reads or writes `cross_border_relationships`, never reads or writes `country_of_residence`/`country_confirmed_at`, and has no branch for any NRI/tax-residency concept. **Classification: live and connected** for primary-country/currency only; **new requirement** for any G6-relevant state (declared cross-border relationship, NRI status, consolidated multi-country view) — none of that is inside the RPC's transaction today.

**The preview route makes an unverified claim.** `app/api/user/primary-country/preview/route.ts` lines 88–109 hard-codes `cross_border_relationships_retained: true` and the warning text "Your confirmed country of residence and existing financial records are never changed by this action" — but the preview computation (lines 26–86) never queries the `cross_border_relationships` table at all. The claim happens to be true only because nothing in the confirm RPC touches that table (a static fact, not a computed one). **Classification: implemented but unreachable as a *verified* check** — the field name suggests active reconciliation with the multi-country dimension; it is actually an untested assumption baked into a literal.

**Separate write path, `PUT /api/user/profile`** (`app/api/user/profile/route.ts` lines 34–102) changes `country_of_residence` (MCC-owned) and, on an actual change to an already-confirmed profile, resets `country_confirmed_at`/`country_source` to null and writes a `country_change_pending_reconfirmation` audit event via `recordCountryAuditEvent()`. This is a **second, independently-guarded country-change surface**, structurally separate from `confirm_primary_country_change()`. It also has zero interaction with `cross_border_relationships` or any NRI concept.

**The WP-10 pattern (LR10, cited by the background brief) is the closest existing precedent for "a country change with a side effect must be explicitly guarded."** `app/api/user/billing-country/confirm/route.ts` lines 38–56: a billing-country **change** (not re-confirmation) while `user_entitlements.subscription_status` is a premium status (`isPremiumSubscriptionStatus`) is blocked with `ACTIVE_SUBSCRIPTION_BLOCKS_COUNTRY_CHANGE` (409), enforced entirely in the API route, not the RPC (`confirm_billing_country` itself is unmodified — see migration `0122` lines 574–622). Documented in `docs/live-recovery/LR10_PHASE_REPORT.md` line 45 ("WP-10"). **This establishes the exact template G6 would need to replicate**: the RPC/DB layer stays generic; a specific call site adds a domain-aware guard before invoking it. No equivalent guard exists yet for primary-country change vs. an active cross-border relationship, an NRI declaration, or a consolidated multi-country view — confirmed by reading the full body of `confirm_primary_country_change()` and its only caller, `app/api/user/primary-country/confirm/route.ts` (47 lines, no side-effect check of any kind beyond preview staleness/expiry/consumption).

**Existing NRI concept is a completely separate, tax-scoped subsystem, not connected to country-change at all.** `lib/engines/investment-intelligence/tax/residency.ts` (`checkResidency`, 46 lines) and `lib/engines/investment-intelligence/tax/taxProfile.ts` (`resolveTaxpayerContext`, spec sections 20–23) implement an explicit-only (never inferred) `taxResidencyStatus`/`taxpayerType` used solely to attach an `NRI_SCOPE_DISCLAIMER`/`INDIA_DOMESTIC_LAW_ESTIMATE` note inside India capital-gains tax simulation (`app/api/investment-intelligence/tax/summary/route.ts`). It is set via a query-param override or `POST /api/investment-intelligence/tax/profile` (`taxpayerType` body field), stored presumably via `taxRepository.ts`'s persistence, and **never reads or writes `user_profiles.country_of_residence`/`primary_country`/`billing_country`, `cross_border_relationships`, or `secondary_country`.** `residency.ts`'s own doc comment (lines 12–18) notes it expects "the household/profile schema if available" but per `docs/investment-intelligence/R6P1_IMPLEMENTATION_REPORT.md` line 170, "No household-profile residency field was found or wired" — the API route passes an empty profile object, so `checkResidency()` always fails-safe to `'unknown'` in production traffic; only `taxProfile.ts`'s independent, explicitly-supplied `taxpayerType` (`NON_RESIDENT_INDIVIDUAL`) is actually reachable end-to-end. **Classification: backend-only / partially wired** — real code exists, exercised by an explicit override, but has no link whatsoever to any G1/G6 country-change or cross-border-relationship state.

**A dormant precedent for a "multi-country dimension" already existed and was explicitly retired.** `lib/validation/profile.ts` lines 23–26: `secondary_country: z.enum(['AU','IN']).nullable().optional()` with the comment "G1/G3 both treat `secondary_country` as superseded by `cross_border_relationships`; widening it here would grow a legacy field this programme is retiring." Column defined in `supabase/migrations/0001_foundation.sql` line 22. **However it is still actively read** in two places: `lib/services/twinData.ts` line 168 (`secondaryCountry`, feeds the Financial Twin cohort resolution) and `lib/ai/context/financialContextObject.ts` line 182 (`crossBorderIndicator = Boolean(profileRes.data?.secondary_country)`, feeds the AI household-context object). Neither of these two live consumers has been migrated to read `cross_border_relationships` instead — so today there are **two disconnected, inconsistent multi-country signals in production code**: the new declaration-only `cross_border_relationships` table (not read by AI context or Twin data) and the legacy `secondary_country` field (marked for retirement, but still the only thing AI context/Twin actually consult). **Classification: partially wired / stale-but-still-live** — a genuine inconsistency any G6 work must reconcile, not invent from scratch.

**Historical discovery doc** `docs/jurisdiction-applicability/09-cross-border-model.md` (pre-dates migration 0122; written when `cross_border_relationships` did not yet exist) documents the prior state in detail: cross-border status was "entirely implicit and per-record" (any `assets`/`liabilities`/etc. row whose own `country_code` differs from `country_of_residence`), `forecast_profiles.country_code` goes **stale** on a later country change (Medium risk, `lib/services/forecastData.ts` lines 26-57, still true today — not re-derived by `confirm_primary_country_change()`), and `households.primary_country` also goes stale (Low risk today only because nothing reads it). Section 6 documents Decision PO-5 (four DEV SMSF rows owned by IN-resident users, preserved read-only, explicitly not reconciled) as a live open question about "residence country / primary financial country / cross-border relationship / record country" staying distinct — directly the G6 problem space, marked unresolved.

**Field-naming/type/nullability consistency assessment:**
- Country codes are consistently `char(2)`/two-letter uppercase strings everywhere at the DB layer (`countries.country_code` FK target used by `country_of_residence`, `primary_country`, `billing_country`, `secondary_country`, `cross_border_relationships.country_code`, `business_entities.country_code`).
- **Inconsistency 1 — validation strictness varies by route for the same underlying two-letter shape.** `country/confirm` accepts `z.string().min(1)` and does its own manual `classifyCountryValue()` shape/registry check; `primary-country/preview`, `primary-country/confirm`(via preview id)/`billing-country/confirm`, `cross-border-relationships` POST all use `z.string().length(2)`; `profile` PUT uses a closed `z.enum(AUTHORITATIVE_COUNTRY_CODES)`. Three different zod strategies for "a country code" across the same route group — not a defect (each has a documented reason, e.g. `country/confirm`'s comment explains why `'GLOBAL'` must fail the length check before any registry lookup) but a real inconsistency a unified G6 contract would need to reconcile explicitly rather than copy one pattern blindly.
- **Inconsistency 2 — nullability/enforcement semantics of "country_code" differ by owning table.** `user_profiles.country_of_residence`/`primary_country`/`billing_country` are strictly validated (registry-checked, controlled-write-guarded, FK to `countries`); `cross_border_relationships.country_code` is `not null`, FK-enforced, and additionally guarded by `enforce_cross_border_country_is_foreign()` (migration `0127`, rejects self-referential or non-offered countries); **`business_entities.country_code`** (`app/api/business-entities/route.ts` line 9-10, schema in `lib/validation/businessEntity.ts` line 9, migration `0134_lr11_business_entity_registry.sql` line 80) is nullable, FK-enforced, but **"purely informational... never enforced by a trigger"** — explicitly documented as a deliberate deviation from SMSF's AU-only gate (WP-09 lesson). A future G6 multi-country contract touching business entities would inherit a field with the same name/type as the strict user-profile fields but categorically weaker semantics (no registry-selectability check at all, unlike every other `country_code` write path in this app).
- **Inconsistency 3 — currency scoping.** `preferred_currency` is a closed `z.enum(['AUD','INR'])` (2 values only) in `lib/validation/profile.ts`, while `business_entities.currency_code` is also `z.enum(['AUD','INR'])` (`lib/validation/businessEntity.ts` line 19) — these two are actually consistent with each other, but both are narrower than the 6-country/6-currency registry (`countries`/`currencies` tables seeded in migration `0122` include GBP/USD/SGD/AED), reflecting that the FX engine (`lib/engines/fx.ts`, referenced in migration `0122` comments) still only knows AUD/INR. Any G6 multi-country currency field would need to either accept this same 2-currency ceiling or explicitly widen the FX engine — the current contracts give no signal either way.

## Cross-cutting summary: does canonical ownership already exist for the MULTI-COUNTRY dimension?

No single canonical owner exists today. Three independent, only-partially-reconciled signals coexist:
1. **`cross_border_relationships`** (migration `0122`/`0127`) — the newest, most structurally sound (RLS, unique-active-index, foreign-country trigger, TIER-1 confirmation gate) but explicitly documented as "a declaration store only; nothing reads it to change a total, gate a product, or run a calculation" (migration `0122` line 417) — confirmed by code search: **zero consumers** outside its own CRUD routes and test fixtures.
2. **`secondary_country`** — legacy, explicitly marked for retirement in `lib/validation/profile.ts`, yet still the only thing two live consumers (`twinData.ts`, `financialContextObject.ts`) actually read for "does this household have cross-border activity."
3. **NRI/tax-residency status** (`residency.ts`/`taxProfile.ts`) — a third, fully disconnected signal, explicit-only, India-tax-scoped, with no link to either of the above.

This is a genuine new requirement for G6: reconciling or superseding all three, not a case of an existing owner needing minor extension.

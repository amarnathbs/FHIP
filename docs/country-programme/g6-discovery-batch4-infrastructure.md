## G6.017 — FDH ingestion and source provenance

**Owner:** `lib/financial-data-hub/**` (FDH), specifically `bank-csv/adapters/**` (CSV, R7, migration `0064`) and `bank-pdf/adapters/**` (PDF, FDH-5, migration `0071`). Callers: `app/api/financial-data-hub/bank-csv/upload/route.ts`, `.../bank-pdf/upload/route.ts` → `services/bankCsvUploadService.ts` / `bankPdfUploadService.ts`. Tests: `tests/unit/r7SchemaContract.test.ts`, `tests/unit/fdh5SchemaContract.test.ts`, `tests/unit/fdh1Isolation.test.ts` (isolation only, not country coverage).

**Classification: live and connected, but AU/IN-only by construction — not merely "no GB/US/SG/AE adapters exist," the type system and validation actively reject them.**

- `lib/financial-data-hub/constants/enums.ts:19` — `export const FDH_COUNTRY_CODES = ['AU', 'IN'] as const;` — this is FDH's own authoritative country vocabulary, independent of G1's `country_capabilities` registry. `fdhCountryCode` (`lib/financial-data-hub/validation/primitives.ts:14`) is `z.enum(FDH_COUNTRY_CODES)`, used by every FDH upload-metadata schema (`bankCsv.ts:25`, `accounts.ts:25`, `liabilityStatement.ts:18`, etc.). A GB/US/SG/AE `country_code` on any upload request fails Zod validation before any file byte is read — a clear 422, not a parse attempt.
- `BankCsvAdapter.country` type (`bank-csv/adapters/types.ts:38`) is literally `'AU' | 'IN' | null` — GB/US/SG/AE cannot even be expressed in an adapter definition.
- `BANK_CSV_ADAPTER_REGISTRY` (`bank-csv/adapters/registry.ts:16-20`) = `AU_ADAPTERS` (5 certified: CBA, Westpac, NAB, ANZ, Macquarie) + `IN_ADAPTERS` (5 certified: SBI, HDFC, ICICI, Axis, Kotak) + `GENERIC_ADAPTERS` (2, `certificationState: 'experimental'`) = exactly 10 certified adapters, matching the LR-3/LR-4 discovery figure.
- **There IS a generic/fallback parser path for CSV only**: `genericAdapters.ts` — `GENERIC_SINGLE_SIGNED_V1` / `GENERIC_DEBIT_CREDIT_V1`, `country: null`, structural (column-shape) matching only, explicitly documented as never to be presented as "we recognised your bank" (`genericAdapters.ts:1-10`), and deliberately capped (`* 0.95`) so it can never outscore a certified adapter. `detection.ts` (`detectBankCsvFormat`) runs every adapter (AU+IN+generic) through the same confidence-scoring pipeline and returns one of `detected | ambiguous | unsupported | manual_mapping_required | invalid`.
- **PDF has NO generic fallback**: `bank-pdf/adapters/registry.ts:12` — `PDF_BANK_ADAPTER_REGISTRY = [...AU_PDF_ADAPTERS, ...IN_PDF_ADAPTERS]` only. `bank-pdf/detection.ts:17,39` — no adapter match anywhere resolves to `unsupported_layout`, which `bank-pdf/orchestrator.ts:157,160` turns into `emptyResult('unsupported_layout', ...)`, surfaced to the user via `services/bankPdfProcessingService.ts:125-126` and `liabilityStatementProcessingService.ts:76` as a clear, specific error ("We couldn't read this file as a statement export... add manually"), never a crash or silent misparse.
- **Net answer to the topic question**: even a plausible GB/US/SG/AE bank CSV can *only* ever land on the country-neutral generic structural fallback (and only if its column shape happens to match `Date/Description/Amount` or `Date/Description/Debit/Credit`) — but the request can never reach that far in practice, because the upload endpoint's own `country_code` query parameter is validated against `FDH_COUNTRY_CODES` first (`app/api/financial-data-hub/bank-csv/upload/route.ts:26,32`) and rejects GB/US/SG/AE before the file bytes are even parsed. A GB/US/SG/AE bank statement therefore fails with a clear, typed error at the metadata-validation layer, not a parser-detection failure — the two are different failure points worth distinguishing for any G6 design.
- Note on authoritative input: `country_code` on this endpoint is **client-declared** (a query parameter the caller/UI sets), not derived from `resolveCountryContext()` — a disclosed, pre-existing characteristic of FDH's upload contract, not a G6 finding to "fix" here, just to note as a genuine input-authority gap if G6 extends FDH.
- DB-level: `fdh_parser_registry.country_code` (`0064` line 60) is `char(2) references countries(country_code)` — the FK is to the *global* `countries` table (which does list GB/US/SG/AE), so the database schema itself does not structurally forbid a future non-AU/IN parser row; the restriction today is entirely in the TypeScript/Zod layer (`FDH_COUNTRY_CODES`), not the schema.
- **Multi-country dimension**: no canonical ownership exists for "a household with income/expenses spanning >2 countries' bank formats" — FDH's whole adapter model is binary AU-or-IN per statement, with no cross-country household concept at all. **New requirement** for G6 if FDH bank-statement ingestion is ever meant to cover NRI multi-country flows beyond the AU↔IN pair.

## G6.019 — Historical snapshots (`financial_snapshots`)

**Owner:** table created `supabase/migrations/0005_module3_dashboard.sql:7-27`; MCC trigger added/hardened in `0105` and `0108`. Sole writer: `lib/services/dashboardData.ts:274-288` (`loadDashboard()`'s own upsert). Readers: `dashboardData.ts:91-101` (`getLatestSnapshotAsOf`), `dashboardData.ts:182-187` (last-12-months in `loadDashboard` itself), `lib/services/twinData.ts:144`, `lib/services/resilienceData.ts:261`, `lib/services/forecastReportData.ts` (via `getForecastVariance`, only reads `snapshot_month` for a comparison date), `lib/engines/resilience.ts`, `lib/engines/reportSections.ts`, `lib/ai/contextualExplanations/service.ts`, `lib/ai/context/certifiedSourceClient.ts`. Tests: none dedicated to `financial_snapshots` itself; incidentally referenced by `twinDataCountryResolution.test.ts`, `lrFi2HouseholdDebtRatios.test.ts`, and two `tests/live-dev/*` fixtures — no test exercises a currency/country change between snapshot months.

**Classification: live and connected, but genuinely stale/misleading by design for the multi-country/currency case — this is a real, currently-undetected data-integrity gap.**

- **Full schema** (`0005_module3_dashboard.sql:7-21`, confirmed unchanged — no later migration `ALTER TABLE`s it): `id uuid PK`, `user_id uuid FK auth.users`, `snapshot_month date not null`, `total_assets numeric(18,2)`, `total_liabilities numeric(18,2)`, `net_worth numeric(18,2)`, `monthly_income numeric(18,2)`, `monthly_expenses numeric(18,2)`, `monthly_surplus numeric(18,2)`, `savings_rate numeric(6,4)`, `currency_code char(3)`, `created_at timestamptz default now()`, unique `(user_id, snapshot_month)`. **There is no `country_code` column at all** — only `currency_code`, and that is a plain `char(3)` with no FK to the `currencies` table.
- **RLS**: `for all using (auth.uid() = user_id) with check (auth.uid() = user_id)` (`:26-27`) — the standard owner-only pattern (see G6.021).
- **The single writer, exact mechanics** (`dashboardData.ts:230,274-288`): `currency = profile.data?.preferred_currency ?? 'AUD'` (a live read of the user's *current* preferred currency, with an AUD fallback if unset) is stamped onto `currency_code` on every upsert, keyed `onConflict: 'user_id,snapshot_month'` — so within the same calendar month, re-running `loadDashboard()` (which happens on every dashboard page load) **overwrites** that month's row with whatever currency is preferred *at that moment*, silently rewriting a value that was previously computed and stored under a different currency, with no re-conversion of the numeric fields.
- **Confirmed misleading-result scenario**: if `preferred_currency` changes from AUD to INR (or vice versa) partway through using the app, (a) the *current* month's snapshot row is overwritten in-place with new INR-denominated figures under the old row's month key — no historical AUD figure for that month survives; (b) *prior* months' rows are left untouched, each still carrying whatever `currency_code` was live when they were written. Every reader (`dashboardData.ts:182-187`, `twinData.ts:144`, `resilienceData.ts:261`) selects `snapshot_month, net_worth, monthly_income, ...` **without ever selecting or checking `currency_code`**, and `lib/engines/dashboard.ts:147,494,1159` passes the raw `SnapshotRow[]` straight through to the trend/history UI with no per-point currency label and no FX normalisation. A user who switched AUD→INR would see a 12-month net-worth trend mixing raw AUD and raw INR magnitudes as if they were one continuous currency series — exactly the "AUD snapshot displayed as if it were always INR" risk the topic asks about, and it is real, not hypothetical, given the write/read code above.
- **Record ownership / audit lineage**: `user_id` is the sole ownership key (no `household_id`); there is **no audit trail at all** for a snapshot being overwritten — the upsert is a silent `UPDATE`-equivalent with no `audit_events` insert, no versioning, no `created_at`-vs-`updated_at` distinction (the table has only `created_at`, which itself doesn't change on an upsert-conflict-update in Postgres unless explicitly re-set, so `created_at` is unreliable as "when this row's *current* values were computed").
- **Canonical ownership for the multi-country dimension**: none exists. `financial_snapshots` was designed as pure single-currency, single-owner historical rollup with no notion of "country" at all — **genuine new requirement** for G6 if per-country or per-currency-consistent historical trending is in scope.

## G6.021 — RLS and ownership (meta-topic: general pattern + disclosed exceptions)

**Confirmed general pattern** (534 `create policy` statements surveyed across `supabase/migrations/*.sql`): the overwhelming majority of user-owned tables follow the exact LR-11-documented pattern —
- Parent/root table: `alter table X enable row level security; create policy "own rows - X" on X for all using (auth.uid() = user_id) with check (auth.uid() = user_id);` (e.g. `0003_module2.sql:128-142` for income/expenses/assets/liabilities/investments/retirement/insurance; identically repeated for `0006` health scores, `0007` DNA, `0008` resilience, `0009` goals, `0010` reports, `0013` forecasting, `0017` recommendations, `0032`-`0047` Investment Intelligence/FDH tables, `0122` `cross_border_relationships`, etc.).
- Child table cross-referenced to its parent: `with check (auth.uid() = user_id and <child_fk> in (select id from <parent> where user_id = auth.uid()))` — the exact pattern confirmed live in `supabase/migrations/0134_lr11_business_entity_registry.sql:150-159` (`business_entity_assets`/`business_entity_liabilities` cross-referencing `business_entities`), which LR-11's own phase report (`docs/live-recovery/LR11_PHASE_REPORT.md:27`) states was "reused from SMSF (migration 0084) — owner-only on the parent, cross-referenced WITH CHECK subquery on every child table." An equivalent subquery form (`exists (select 1 from <parent> r where r.id = <child_fk> and r.user_id = auth.uid())`) is used for `financial_twin_metric_results`/`financial_twin_insights` (`0011_module8_financial_twin.sql:323,326`).

**Confirmed, disclosed exceptions to the owner-only pattern** (all pre-existing and intentional, not oversights):
1. **World-readable reference/catalogue tables** — `for select using (true)`: `countries`, `currencies` (`0001_foundation.sql:107-108`), `country_capabilities` (`0122:188`), `master_financial_items`, every `benchmark_*`/`ii_*` reference table, `fdh_financial_institutions`, `fdh_parser_registry`, `fdh_mcc_master`, etc. (dozens — reference/lookup data, not user-owned, expected exception.)
2. **`audit_events` itself** — `for select using (auth.uid() = user_id)` only, deliberately **no** `for all`/insert policy for the authenticated role (`0001_foundation.sql:101-102`) — owner-read, service-role-write-only. This is a distinct, disclosed sub-pattern for audit tables specifically (also followed by `ii_audit_events`, `0036:39`).
3. **Admin/staff-governed content tables** — `resource_*` CMS tables (`0049_reconcile_phase0c_resources_lineage.sql`) gated by `private.is_resource_staff(auth.uid())` / `private.can_manage_resources(auth.uid())`, and `0132_lr9_account_closure.sql:111,114` gated by `public.is_account_deletion_admin(auth.uid())` — genuinely admin-owned content/operations, not end-user data, so "owner = auth.uid() = user_id" doesn't apply by design.
4. **Multi-party shared-access tables** — Investment Intelligence R11 professional access (`0083_ii_r11_professional_access.sql:94,96,106,168,172,230,234,337,341,382,384`): policies keyed on `client_user_id` **or** `professional_user_id`, i.e. two legitimate distinct owners can read the same row (a client and their linked professional) — a genuine, deliberate departure from single-owner RLS for a client/professional relationship, not a gap.
5. **Differently-named owner column, same semantics** — `report_exports`/`report_generation_runs` use `requested_by_user_id` instead of `user_id` (`0010_module9_reports.sql:202`, reaffirmed `0070_ii_r10_reports_authoritative_write_hardening.sql:76`) — same owner-only pattern, just a domain-specific column name.
6. **`public read active X`/`is_active`-gated selects** on `resource_categories`/`resource_tags`/`resource_authors`/`resource_ctas`/`resource_faqs` (`0049:800,809,818,847,984`) — public marketing-content visibility toggle, not user ownership.

No undisclosed/unexplained departure from the owner pattern was found in this survey — every non-owner-only policy corresponds to one of the six categories above, each with a clear, legitimate reason.

**Canonical ownership for the MULTI-COUNTRY dimension specifically**: the general RLS pattern (owner-only + cross-referenced child `WITH CHECK`, per LR-11) is already the settled, reusable convention any G6 table would conform to — there is nothing new to invent at the RLS-pattern level. What does **not** yet exist is a canonical *country-scoping* dimension inside that pattern (e.g., RLS or app-layer logic that additionally scopes rows by which of a user's multiple confirmed countries they belong to) — that remains a **new requirement** specific to G6's multi-country framework, layered on top of, not replacing, the existing owner-only pattern.

## G6.007 — Consolidated net worth

**Owner today:** `lib/engines/dashboard.ts` (`computeDashboard()`, lines 750–760 build the formula; `DashboardInput`/`DashboardSummary` types lines 138–163, 377–504). Callers: `lib/services/dashboardData.ts::loadDashboard()` (line 255–272, the only production caller), consumed by `app/(app)/dashboard/page.tsx`, `lib/services/goalsData.ts`, `lib/services/forecastData.ts`, `lib/engines/reportSections.ts`/`reportSectionsPremium.ts`, `lib/engines/resilience.ts`, AI context builder (`lib/ai/context/financialContextObject.ts`). Tests: `tests/unit/dashboard.test.ts`, `tests/unit/lrFi2HouseholdDebtRatios.test.ts`, `tests/unit/iiR3NetWorthCertification.test.ts`, `tests/unit/lrFi3NetWorthContributionExactlyOnce.test.ts`.

**The exact formula (dashboard.ts:750–760):**
```
businessEntityOwnershipValue = computeBusinessEntityOwnershipValue(input.businessEntities ?? [], currency, fxRateAudInr)
totalAssets       = Σ reportingValue(row.currency_code, row.current_value)   over input.assets
totalInvestments  = Σ reportingValue(row.currency_code, row.current_value)   over input.investments
totalRetirement   = Σ reportingValue(row.currency_code, row.current_balance) over input.retirement
totalLiabilities  = Σ reportingValue(row.currency_code, row.balance)         over input.liabilities
netWorth = totalAssets + totalInvestments + totalRetirement - totalLiabilities + businessEntityOwnershipValue
```

**Does it branch on country at all? No — never on `country_code`.** It branches only on **`currency_code`** via `reportingValue()` (dashboard.ts:537–541) → `convertToReportingCurrency()` (`lib/engines/fx.ts:14–22`). `SupportedCurrency` is `'AUD' | 'INR'` only — `toSupportedCurrency()` (dashboard.ts:523–525) maps any other/absent code to `null`, and a `null` row-currency is **assumed already in the reporting currency and added raw, unconverted** (dashboard.ts:531–533 comment states this explicitly). `businessEntityValuation.ts` (LR-11) follows the identical currency-only pattern (`convert()`, lines 36–39) and carries **no `country_code` field on business entities at all** — only `currency_code`.

So: **netWorth today is "sum every row, converting by currency, into one number" — genuinely currency-aware but not country-aware.** It is not "blind summation" (LR-FI-1/LR-FI-2 already carved out SMSF household-vs-wealth scoping, and LR-3/LR-11 correctly scope bank transactions and business entities) — but the specific dimension G6 asks about, jurisdiction, plays no role in the netWorth number itself.

**Per-country breakdown DOES already exist, as a separate, deliberately non-consolidated concept:**
- `assetsByCountry`/`liabilitiesByCountry`/`retirementByCountry` (dashboard.ts:782–793, via `byCountry()`) and `investmentByCountry` (dashboard.ts:893–898) — these sum **raw, unconverted, in each country's own currency** ("Cross-border rollups... reuses the country_code already recorded", comment at dashboard.ts:780–781). `countriesInUse` (dashboard.ts:899–906) is the union of all four.
- Dashboard UI: `components/dashboard/sections.tsx:313–317` renders only `investmentByCountry` as a pie chart — the *only* per-country UI surface on the live Dashboard. No per-country net worth widget exists there.
- **Reports (both tiers) DO surface a genuine per-country breakdown**, gated on `countriesInUse.length > 1`:
  - Free tier: `buildCrossBorder()`, `lib/engines/reportSections.ts:652–675`, section code `cross_border`, gated via `reportEligibility.ts:130–134` (`countriesInUseCount > 1 ? 'included' : 'omitted'`).
  - Premium tier: `buildCrossBorderFull()`, `lib/engines/reportSectionsPremium.ts:463–503`, section code `cross_border_full`. Its own `limitationText` (line 501) states verbatim: **"Local-country totals are shown as recorded, in each country's own currency. A fully converted single-reporting-currency consolidated view is not yet implemented."** This is the codebase's own admission that a true FX-consolidated per-country net-worth view does not exist — only (a) one blended total (currency-converted, not country-labelled) and (b) per-country totals (country-labelled, not currency-converted).
  - Both are wired end-to-end: `reportsData.ts:179` → `app/api/reports/generate/route.ts` et al. → rendered in `components/reports/ReportPreview.tsx:160,176`. **Classification: live and connected** for both tiers.
- Design intent is documented in `docs/investment-intelligence/R0_CROSS_BORDER_CONTRACT.md` (§1–4): "Investment Intelligence keeps source-country values... FHIP's existing cross-border/household services remain solely responsible for household base-currency translation" — i.e., the two-number model (one converted total, one unconverted per-country table) is the *designed* architecture, not an oversight.

**Authoritative inputs / rejects:** `AUTHORITATIVE_COUNTRY_CODES = ['AU','IN','GB','US','SG','AE']` and the FULL/GENERIC split live in `lib/services/jurisdiction.ts:36–66`; the canonical residence field is `user_profiles.country_of_residence` (jurisdiction.ts:5–14, explicitly rejects `households.primary_country` as a second source of truth). Reporting currency is `user_profiles.preferred_currency`, DB-constrained to `('AUD','INR')` only since migration `0127` (`user_profiles_preferred_currency_supported_check`) — added specifically because migration `0122` widened the `currencies` FK to 6 rows and a direct PostgREST write had been proven live to set `preferred_currency='USD'` for a real user (0127 comment, lines 176–213).

**Gap found (currency, not country, but bears on the "reject currency as substitute" checklist item):** The equivalent DB-level guard was **never extended to the four register tables' own `currency_code` columns** (`assets`, `liabilities`, `investments`, `retirement_accounts` — migration `0001_foundation.sql:51` et al.). These are `char(3)` FK-to-`currencies` with no `CHECK ... in ('AUD','INR')`. App-layer Zod (`lib/validation/asset.ts:9`, `liability.ts:22`, `investment.ts:11`, `retirement.ts:9`) enforces `z.enum(['AUD','INR'])`, but (mirroring exactly the class of defect 0127 fixed for `preferred_currency`) a row-owning RLS policy would let a direct PostgREST PATCH set e.g. `currency_code='GBP'` on an asset row, which `reportingValue()`/`toSupportedCurrency()` would then silently treat as **already-reporting-currency, added unconverted** — no error, no flag. Classification: **cannot verify from static reading alone whether this is currently exploitable in production RLS** (no migration equivalent to 0127 §3b was found for these four tables) — worth flagging as a residual verification gap, not asserting a live vulnerability.

**AU/IN/GENERIC/unresolved paths:** GENERIC-experience residents (GB/US/SG/AE) can never reach `computeDashboard()` with any real data — the MCC ~85-table trigger backstop (migrations `0104`/`0108`/`0111`, confirmed for `income_sources`/`expense_items`/`assets`/`liabilities`/`investments`/`retirement_accounts` at `0108_...crud_and_onboarding_fix.sql:6-7,186-188,496-498`) blocks INSERT into every financial table unless `is_country_confirmed()` is true, which requires `countries.is_supported = true` — true for AU/IN only (0127 header, lines 13–43). So a GENERIC user's dashboard is structurally empty; there is no "GENERIC path" through `computeDashboard()` to trace beyond "zero rows, zero net worth."

**Existing controls (inventory, not proposing new):** `tests/unit/dashboard.test.ts:22–98` is the direct positive/negative-control suite for the currency-conversion behaviour, explicitly including "does not convert an unrecognised or missing currency_code (treated as already in reporting currency)" (line 75) — i.e. the silent-passthrough behaviour above is a *tested, deliberate* contract, not an unnoticed bug. `tests/unit/reports.test.ts:41,61` test the `cross_border`/`cross_border_full` omitted/included gating directly (Persona A single-country → omitted; Persona E `countriesInUseCount: 2` → included).

**Verdict on the G6 framing question:** Canonical ownership of "one converted total" already exists (dashboard.ts) and canonical ownership of "per-country, unconverted breakdown" already exists (byCountry rollups + both report tiers). What genuinely does **not** exist — confirmed as a **new requirement** by the codebase's own documented limitation text — is a **per-country net worth breakdown in the SAME reporting currency** (e.g., "AU: $X AUD, IN: $Y AUD, Total: $X+Y AUD"). Today you can see the blended total (converted, unlabelled by country) or the per-country split (labelled, unconverted) but never both combined into one reconciling table.

## G6.008 — Cash-flow consolidation

**Owner:** same file/function, `computeDashboard()` cash-flow block, dashboard.ts:563–727 (`grossMonthlyIncome` line 592, `netMonthlyIncome` line 593, `totalMonthlyExpenses` line 676, `monthlySurplus` line 694). Caller/selects: `dashboardData.ts:126–228` (note: **no `country_code` column is even selected** on `income_sources`/`expense_items` — line 128/133 — only `owner`/`superseded_by_bank_import`; country plays literally no role in these two registers' schema as read here).

**Does it discriminate by country at all? No — zero country dimension.** `IncomeRow`/`ExpenseRow` (dashboard.ts:16–41) have no `country_code` field at all (unlike `AssetRow`/`LiabilityRow`/`InvestmentRow`/`RetirementRow`, which all carry one). The only discriminators applied are: (a) LR-FI-1's household-vs-SMSF split (`householdOperatingCashFlowRows()`, via `owner`), (b) LR-3's `superseded_by_bank_import` opt-out, (c) currency conversion of bank-derived transactions and liability repayments via `reportingValue()` (same currency-only mechanism as G6.007, lines 583–590, 684). A GB-resident's income row (if one could exist) would be summed identically to an AU-resident's — but per G6.007's MCC trace, it structurally never can.

**GENERIC-gating confirmed at the database layer, not merely UI:** `income_sources`/`expense_items` both carry the full MCC INSERT/UPDATE/DELETE trigger (`0108_...:186-188,496-498`), so a GENERIC-experience user cannot create rows in either register regardless of any app-layer capability flag. This is a hard backstop, not the softer G4/G5 "restrict what you can even enter" capability gating the task hypothesised — it's one layer stronger: GENERIC users get `COUNTRY_CONFIRMATION_REQUIRED` (42501) at the trigger, before any UI-layer capability check (`lib/services/countryGate.ts`, `lib/nav/appNavCapability.ts`) is even relevant.

**Classification:** **live and connected** as pure amount/currency aggregation (no country awareness needed or present); the "does a GENERIC user's income get treated identically" question is **moot in practice** because GENERIC residents cannot record income/expense rows at all — confirmed by migration text, not inferred.

**New requirement:** any country-aware cash-flow view (e.g., "household income by country of source") would be a **genuine new requirement** — no `country_code` exists on `income_sources`/`expense_items` today to even key such a breakdown off, unlike the wealth registers which already carry it.

## G6.009 — Goal linkage

**Owner:** `lib/services/goalsData.ts` (717 lines) + `lib/services/goalFundingAllocation.ts` (`computeLiveLinkedFundingValue()`, lines 247–265; `resolveAllocatedAmount()`, lines 139–184). Schema: `user_goals` (`currency_code`, `country_code` selected at goalsData.ts:251–252, 479–480), `goal_funding_sources` (`currency_code` at line 57). Tests: `tests/unit/goals.test.ts`, `tests/unit/goalArchivedLinkedFunding.test.ts`.

**Country/currency dimension in the funding mechanism itself: none.** `grep` for `country`/`currency`/`convertToReportingCurrency`/`fxRate` inside `lib/services/goalFundingAllocation.ts` returns **zero matches**. `computeLiveLinkedFundingValue()` (lines 247–265) is purely: for a percentage-based source, `currentValue (raw, from currentValueById map) * allocationPercentage / 100`; for a fixed-amount source, the stored `allocatedAmount` verbatim. Neither branch ever consults the linked record's `currency_code` or the goal's own `currencyCode`.

**The `currentValueById` map itself is built with no currency awareness either:** `loadLinkedContributionSources()` (goalsData.ts:282–336) selects `current_value`/`current_balance` from `assets`/`investments`/`retirement_accounts` **without even selecting `currency_code`** (lines 305, 310–314, 322–326) — so there is no data available at this call site to convert even if the function wanted to.

**Consequence (genuine finding, not proposing a fix):** if a goal's `currency_code` (AUD or INR) differs from a linked asset/investment/retirement account's own `currency_code` (also AUD or INR, but potentially the *other* one in a cross-border household), `computeLiveLinkedFundingValue()` adds the raw local-currency figure directly against the goal's target with **zero exchange-rate conversion** — e.g., a ₹500,000 linked PPF balance would count as "500,000" toward an AUD-denominated goal target. `country_code` is present on `user_goals` (goalsData.ts:70,252) but is carried through purely as **pass-through display metadata** — never read by any comparison/allocation/forecast logic in `goalFundingAllocation.ts` or `goalForecast.ts`.

**Classification:** **backend-only / stale-as-a-signal** for `country_code` on goals (stored, displayed, never computed against); the cross-currency funding gap above is **cannot verify severity without a live cross-border fixture**, but is a real, traceable code path, not speculative — it's a straightforward reading of the two functions cited. This is squarely "purely amount-based regardless of which country the linked asset's `country_code` is," matching the task's hypothesis exactly, and additionally purely amount-based regardless of **currency**, which is the sharper version of the same gap.

**Existing controls:** `checkFundingAllocation()` (goalFundingAllocation.ts:34–59) prevents over-allocation (>100%) of a single linked balance across goals — a real control, but currency/country-blind by the same construction. No test in `tests/unit/goals.test.ts` was found asserting cross-currency funding-source behaviour (only single-currency AUD/INR-homogeneous fixtures were found in a scan of that file's `describe`/`it` blocks — a genuine coverage gap for this specific scenario, inventory only).

## G6.010 — Forecast consolidation

**Owner:** `lib/engines/forecast/*` (engine.ts orchestrator, netWorthCalculator.ts, retirementCalculator.ts, debtCalculator.ts, **crossBorderCalculator.ts**, resilienceCalculator.ts) + `lib/services/forecastData.ts` (1661 lines, `buildCalculatorInput()`). Registered in `CALCULATORS` map, `lib/engines/forecast/engine.ts:34–42`.

**`crossBorderCalculator.ts` (166 lines) is a real, distinct calculator — not a stub.** It models "net foreign wealth" (assets+investments+retirement−liabilities, in the *foreign* currency) with its own growth/return assumptions, then converts to the reporting currency each month via the shared `convertToReportingCurrency()` (fx.ts), explicitly separating **local-currency return** from **FX gain/loss** (lines 93–100, "Return attribution (spec 12.5)"). Scope is exactly the two supported currencies, matching the file's own header (lines 1–13): "an AUD-base user's INR-denominated holdings, or an INR-base user's AUD-denominated holdings."

**Is it reachable from the real UI/backend, or backend-only?** **Live and connected, end to end:**
- `lib/services/forecastData.ts:421–485` builds real `CrossBorderCalculatorInput` from live `assets`/`investments`/`liabilities`/`retirement_accounts` rows filtered by `.eq('currency_code', foreignCurrency)` (lines 426–444) — genuinely queries the household's actual foreign-currency holdings, not synthetic data.
- UI route: `app/(app)/forecast/cross-border/page.tsx` renders `components/forecast/CrossBorderForecastPanel.tsx`, which POSTs `{ forecast_type: 'cross_border', scenario_id }` (panel.tsx:44).
- Nav-registered: `lib/nav/appNavCapability.ts:44` (`'/forecast/cross-border': 'FORECASTING'`), listed in `components/ui/AppShell.tsx`, and asserted present in `tests/unit/appNavCapability.test.ts:48`.
- e2e coverage exists: `tests/e2e/forecasting-engine.e2e.spec.ts:235` (references `forecast_category === 'cross_border'` with a wider tolerance for FX-driven variance).
- Report surfacing: `components/forecast/ForecastReportContent.tsx:66,173`.

**Does the rest of the forecast engine (net worth/retirement/debt projections) treat a multi-country household differently?** No — `netWorthCalculator.ts`, `debtCalculator.ts`, `retirementCalculator.ts` all operate on a single already-consolidated opening balance per category (see G6.011 below for the retirement case specifically) and know nothing about country; **cross-border treatment exists only as this one separate, opt-in forecast type**, not as a property woven into the other calculators. A multi-country household gets: (a) a domestic-consolidated `net_worth`/`retirement`/`debt` forecast that has already summed AU+IN currency-converted balances into one blended trajectory (no per-country split going forward in time), plus (b) this standalone `cross_border` forecast type that projects *only* the foreign-currency slice in isolation. There is no single forecast that shows "AU trajectory + IN trajectory converging to one consolidated future net worth, broken out by country" — the two views (blended-total forecast vs. isolated-foreign-slice forecast) are not reconciled against each other.

**Classification: live and connected** (not backend-only, not dead) for the cross-border forecast type itself; **partially wired** as a *consolidation* concept, since it exists as a parallel, non-integrated calculator rather than a country-aware branch inside the main net-worth/retirement/debt trajectories.

## G6.011 — Retirement and pension boundaries

**Owner:** `retirement_accounts` table (schema: `lib/validation/retirement.ts`), `lib/services/retirementMemberData.ts` (retirement_members, 95 lines), `lib/engines/forecast/retirementCalculator.ts` (321 lines), SMSF carve-out (`lib/engines/smsf/`, LR-6).

**`retirement_accounts.account_type` is a real, validated enum distinguishing product types: `z.enum(['super', 'EPF', 'PPF', 'NPS', 'other'])` (`lib/validation/retirement.ts:7`).** This is captured on write. **It is never read by any engine.** Grepped `account_type` across `lib/engines/` and `lib/services/dashboardData.ts`/`forecastData.ts`/`retirementCalculator.ts` — **zero matches**. It surfaces only in the Financial Data Hub's statement-import/account-matching pipeline (`lib/financial-data-hub/retirement/*`, `lib/retirement-import-bridge/*`) for reconciling imported statements to existing rows — a data-ingestion concern, not a valuation/forecast concern.

**Confirmed conflation:** `dashboard.ts`'s `RetirementRow` (lines 99–107) and `totalRetirement` (line 754) sum **every** `retirement_accounts` row — AU superannuation, Indian EPF, PPF, NPS, SMSF, "other" — identically, differentiated **only by `currency_code`** (via `reportingValue()`), never by `account_type` or `country_code`. `forecastData.ts:510–527` (the `FHIP_50_User_Report_Accuracy_Validation_Review P0` fix comment, explicitly self-documented) does the same: it converts each account by `currency_code` before summing into one flat `currentBalance` for the entire retirement forecast — a *currency* fix for a real production overstatement bug (a household with AUD+INR+AUD accounts previously got summed raw and mislabelled with the first account's currency), but this fix is scoped to currency correctness, not product/jurisdiction differentiation. `retirementCalculator.ts` itself has zero references to country, SMSF, EPF, PPF, or NPS — it operates purely on `currentBalance`/`monthlyContribution`/`currentAge`/`retirementAge` as flat numbers regardless of the underlying product mix.

**The only place a country distinction is applied at all is the *retirement age default*, not any product-specific rule:** `retirementMemberData.ts:30-46` — `LITERAL_FALLBACK_RETIREMENT_AGE = { AU: 67, IN: 60 }`, seeded from `forecast_global_assumptions` keyed by `country_code`. `retirement_members.country_code` exists per-member (line 10) and gates via `toFullExperienceCountryOrNull()` (fails closed to `null`/error for a GENERIC country, line 74–83) — but this only ever picks a default retirement *age*, never differentiates preservation-age rules, contribution-cap rules, tax treatment, or withdrawal rules between AU super and Indian EPF/PPF/NPS.

**SMSF is the one genuine carve-out, and it is scoped narrowly:** LR-FI-1/LR-6's SMSF logic (`lib/engines/householdContext.ts`, `lib/engines/smsf/`) excludes SMSF-linked accounts from the household **cash-flow/contribution forecast** (`forecastData.ts:535–547`, `accountsEligibleForHouseholdContributionForecast()`) — but SMSF's **balance still counts in `totalRetirement`/`netWorth` identically to every other retirement_account row** (dashboard.ts comment lines 59–66: "an SMSF-owned asset, investment or retirement balance must keep contributing... Net Worth (spec §5, §28)"). SMSF creation is itself AU-residency-gated at the DB trigger level (`0084_geo_jurisdiction_smsf.sql`, `trg_retirement_accounts_smsf_au_gate`), documented exhaustively in the pre-existing `docs/jurisdiction-applicability/09-cross-border-model.md` §6 (Decision PO-5) — that doc already establishes, as certified ground truth, that **existing SMSF records remain fully counted in totals regardless of the owner's current country** (§6.1, §6.2 table) and that the trigger cannot currently express any finer-grained "AU-resident-with-cross-border-relationship" distinction (§6.3).

**Verdict:** retirement_accounts rows are kept as generic "one bucket, N currencies" rows exactly as the task's second hypothesis suggests, with **no product-specific math beyond (a) the SMSF cash-flow carve-out and (b) the AU/IN retirement-age default** — `account_type` (EPF/PPF/NPS/super) is captured but functionally inert for every valuation and forecast calculation. **Classification: `account_type` field — backend-only / captured-but-unread** (a genuinely stored, validated field with zero downstream consumers in the engines); the AU/IN retirement-age split — **live and connected**; jurisdiction-specific pension-rule modelling (contribution caps, preservation age, tax treatment per product) — **new requirement**, not a gap in an existing mechanism, since no such mechanism was ever attempted for any product other than SMSF's narrow AU-residency creation gate.

## Cross-cutting notes (applicable to all five topics)

1. **Canonical country authority** is `lib/services/jurisdiction.ts` (`AUTHORITATIVE_COUNTRY_CODES`, `FullExperienceCountryCode` narrowing, `isFullExperienceCountry()`) — every engine that has ever attempted country-awareness (`resilienceStress.ts`, `retirementMemberData.ts`, `reportSectionsPremium.ts`'s `applicabilityNote()`) explicitly routes through this file and explicitly rejects deriving country from currency (see `reportSectionsPremium.ts:509-519` comment citing a fixed defect: "a household can legitimately report in AUD while resident in India, or vice versa"). This is the established, audited pattern any G6 consolidation work should reuse rather than re-deriving country from currency/locale.
2. **Audit lineage:** country confirmation itself is fully audited and transaction-safe (`confirm_country_of_residence()` RPC, migration `0127` §9, writes `audit_events` in the same transaction as the profile write) — but **none of the five consolidation topics above (net worth, cash flow, goals, forecast, retirement) write any audit/lineage record when a cross-border total is computed or displayed** — these are pure read-time aggregations with no persisted "this consolidated figure was computed from countries X, Y on date Z" snapshot beyond the ordinary `financial_snapshots` row (which itself has no `country_code` breakdown column — `dashboardData.ts:274-288`, `SnapshotRow` dashboard.ts:127-136).
3. **Cross-tenant/negative controls:** none of the four engines' files reviewed (dashboard.ts, goalFundingAllocation.ts, crossBorderCalculator.ts, retirementCalculator.ts) accept a raw `userId` from anywhere other than the authenticated session in their service-layer callers — RLS-scoped Supabase queries throughout (`dashboardData.ts`, `goalsData.ts`, `forecastData.ts` all filter `.eq('user_id', userId)` from the session). No dedicated cross-tenant attack test was found specifically for the country/currency dimension of these five topics (existing cross-tenant coverage is generic RLS testing elsewhere in `tests/`, not consolidation-specific) — **inventory gap noted, not fixed.**
4. **Prior certified ground truth to reuse, not re-derive:** `docs/jurisdiction-applicability/09-cross-border-model.md` already contains a rigorous, code-traced analysis of "what activates cross-border today" (§1: implicit, per-record `country_code` mismatch, same `countriesInUse` mechanism confirmed independently above), the SMSF boundary (§6, Decision PO-5), and country-change behaviour (§4: net worth is unaffected by a country change, forecast assumptions are). `docs/investment-intelligence/R0_CROSS_BORDER_CONTRACT.md` independently certifies the same two-number (converted-total vs. unconverted-per-country) design intent for net worth. Any G6 consolidation work should treat these two documents as already-established priors rather than re-discovering them.

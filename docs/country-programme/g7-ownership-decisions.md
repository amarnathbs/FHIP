# G7 Canonical Ownership Decisions (G7.029–G7.056)

Synthesized directly from the G7 discovery pass (`docs/country-programme/g7-discovery-batch1..6*.md`) — same repo state, `cd7b201`/`b34137b`. These are **decisions, not implementation** — no code is written here. Each decision states the canonical owner going forward, why (grounded in discovery), and whether it requires new schema/code or is already correctly owned.

Guiding rule carried through, per discovery's own repeated finding: **country is never derived from currency, locale, or a client-supplied value.** Every Reports/Resources route that reaches an authenticated household is already gated by `requireCountryConfirmedUser()` — GENERIC-experience and unconfirmed-country users cannot reach any of the surfaces this phase covers except the fully public, unauthenticated Resources site (G7.037/041), which correctly has no country gate at all.

## G7.029 — Free report geography
**Owner: unchanged.** No free-tier report section is scoped to exclude foreign holdings (G7.005: no such mechanism exists at all — the opposite shape, blended totals, is what's built). **Decision: G7 does not build a domestic-only report section.** Discovery classified this a genuine new requirement, not a defect; building it needs (a) a canonically-resolved home country as an *additional* filter dimension layered on top of the existing blended engine, never a replacement for it, and (b) a `country_code` column on `income_sources`/`expense_items` that doesn't exist yet (see G7.042/G6.042). **Explicitly deferred** — out of this phase's boundary until a dedicated spec authorizes it.

## G7.030 — Premium report geography
**Owner: unchanged, same reasoning as G7.029.** `cross_border`/`cross_border_full` (Free and Premium) remain the sole country-scoped report sections, and their per-country totals stay deliberately unconverted/uncoverted-and-labelled ("as recorded," per each section's own `limitationText`). **Decision: no forced reconciliation of the blended-and-converted view with the per-country-and-unconverted view in this phase** — matches G6.035's own net-worth precedent (`netWorthByCountryConverted` is the sanctioned pattern for reconciling the two, decided in G6, not re-decided here); if G6.035's schema/read-side change ships, `cross_border_full` should read the same new field rather than either module inventing its own second reconciliation.

## G7.031 — Report header country context
**New owner required, narrow scope.** Discovery found no jurisdiction indicator anywhere on a report's cover/header, and `reports.country_scope` is a fixed, always-`'household'`, never-read literal — stale/cosmetic, confirmed zero consumers. **Decision: `country_scope` is repurposed, not replaced** — at generation time it should be populated from the same `source.profile.countryOfResidence` resolution already used by `stress_testing`'s `applicabilityNote` (`reportSectionsPremium.ts`), reusing the existing canonical resolution path, never adding a second one. This closes G7.008's own disclosed gap (no country-of-generation provenance stored) as a side effect. **Deferred to implementation phase** — this decision only fixes what the column stores; it does not mandate new header UI copy, which is a separate design decision outside ownership scope.

## G7.032 — Reporting currency and date
**Owner: reaffirmed, no gap found.** `reports.reporting_currency` is correctly `not null`, immutable, and frozen per-report (G7.008: confirmed stronger than `financial_snapshots`' own exposure — no silent overwrite path exists for reports at all, since `generateReport()`'s idempotency check returns the existing row rather than recomputing). **Decision: no change.** The one real, disclosed defect in this space — hardcoded `'en-AU'` date-locale formatting regardless of `reporting_currency`/country (G7.020) — is a **display bug, not an ownership gap**: the currency-vs-locale coupling is already correctly modelled (`Intl.NumberFormat` keyed off `reporting_currency`), only the *date* formatter never adopted the same pattern. **Decision: the date formatter should be keyed off the same `reporting_currency`-derived locale the money formatter already uses** (`'INR' → 'en-IN'`, else `'en-AU'`) — a bug-fix-shaped change reusing an existing resolved value, not a new mechanism.

## G7.033 — Domestic sections
**Same decision as G7.029** (identical underlying gap — no domestic-only section exists anywhere in either tier). **Deferred**, tracked once as a single open item rather than duplicated across Free/Premium.

## G7.034 — Cross-border sections
**Owner: `byCountry()` rollups (canonical since G6.031/035) stay the sole data source for both `cross_border` and `cross_border_full`.** Discovery confirmed both tiers are live, correctly wired, and unchanged since G6's own review. **Decision: no new ownership** — this is a correctly-wired reuse. The one real gap (duplicated `> 1`/`<= 1` eligibility threshold maintained independently in `reportEligibility.ts` and inline in `reportSectionsPremium.ts`) is a **maintainability fix, not an ownership question**: both should call the same eligibility function, following the exact precedent G6.034 already set for `isDomesticRecord()` (extract-and-share, not redesign).

## G7.035 — Consolidated sections
**Owner: `computeDashboard()`'s blended fields stay canonical for Net Worth/Cash Flow/Executive Summary/Health Score/DNA/Resilience/Trends/Diagnostic/Retirement Readiness — confirmed correctly consolidated by design, matching G6.035's own net-worth verdict.** Investment Analysis's hybrid (converted totals + unconverted per-country table in one section) is **reaffirmed as-is** — its own inline comment already documents the deliberate reasoning (avoiding return-vs-currency-movement misattribution), the same principle `buildInvestmentPerformance()` states explicitly. **Decision on the one real gap found** (no in-section "this blends N countries" disclosure on Net Worth/Cash Flow, unlike Investment Performance's own standard): **add a `limitationText` note to `net_worth`/`cash_flow`/`executive_summary` when `countriesInUse.length > 1`**, reusing the already-resolved `d.countriesInUse` value G7.034's sections already consume — no new computation, just a conditional narrative addition. This is additive disclosure, not a data-model change.

## G7.036 — Historical report snapshots
**Owner: `reports`/`report_sections`/`report_snapshots` stay canonical; the report-freeze-at-generation-time model (confirmed stronger than `financial_snapshots`) is reaffirmed as correct and untouched.** **Decision: extend `report_snapshots.snapshot_metadata_json`** (already a JSONB catch-all field, no schema migration needed) **to additionally record the resolved `fxRateAudInr`/`fxRateDate`/`countryOfResidence` values used at generation time**, for the same reason G6.033 added those columns to `financial_snapshots` — closing the "provenance not independently queryable" gap discovery confirmed. This is the report-side twin of G6.033's decision, using the report family's own existing metadata mechanism rather than new columns, since `report_snapshots` already has the field for exactly this purpose (per its own schema intent, just never populated with these values).

## G7.037 — Resources applicability taxonomy
**Owner: unchanged.** `resource_posts.jurisdiction`'s 4-value enum (`global`/`australia`/`india`/`australia_india_cross_border`) stays canonical for Resources content — it predates G1 and correctly serves a different purpose (content-relevance labelling) than the G1 `countries`/`country_capabilities` registry (account/capability gating). **Decision: do NOT unify the two vocabularies into one enum.** Discovery's own cross-cutting note flags this as a genuine open question, but reconciling them risks exactly the "parallel source of truth" problem this whole programme exists to avoid in the other direction — Resources' jurisdiction field has never been, and does not need to become, an instance of the G1 country registry. If a future phase wants GB/US/SG/AE-specific Resources content, it should **widen this same enum** (the way G6.031 widened `country_code` CHECKs) rather than migrating to a different field.

## G7.038 — Resources filtering
**Owner: reaffirmed, no gap found.** The manual, reader-operated jurisdiction filter (URL-state-driven, defaulting to `all`) is confirmed correctly built with zero client-supplied-country substitution risk — there is no country signal to substitute, since the filter never claims to be authoritative in the first place. **Decision: no change.** This correctly satisfies the "reject currency/locale/client-country as substitutes" principle by construction (an honest content filter is not a country determination).

## G7.039 — Resources admin governance
**Owner: reaffirmed.** `validateForReview()`'s mandatory jurisdiction-tagging gate (`lib/resources/editor/validation.ts:85`) stays canonical — confirmed live, enforced, correctly independent of G1. **Decision: no change to the jurisdiction-tagging requirement itself.** The one disclosed side-finding — the Resources admin dashboard route being gated by the general-purpose `countryConfirmationBlockResponse` (coupling staff residence-country to CMS access for content aimed at readers worldwide) — is **noted, not fixed**: it is the correct, intentional, universal admin-surface gate, not a Resources-specific defect, and loosening it for Resources alone would create an inconsistent admin-security posture across modules. Flagged forward for a future cross-module admin-access review, not this phase's call to make unilaterally.

## G7.040 — Recommendation applicability
**Owner: `action_recommendation_master`'s `country_code` condition rows stay canonical, fed exclusively from `user_profiles.country_of_residence` via `forecast_profiles`/`recommendationsData.ts` — confirmed correctly sourced, never currency-derived.** **Decision on the two real gaps found:** (1) `lib/services/appCapability.ts`'s `RECOMMENDATIONS.note` is corrected to state plainly that the library has AU/IN-only-triggering rows by design (28 confirmed rows), not merely "not yet re-certified as country-neutral" — a documentation-accuracy fix, not a behavior change. (2) `lib/engines/recommendations/matcher.ts` gets **direct unit-test coverage of its country-conditional branch** (positive: an AU-scoped rule fires for an AU household; negative: it does not fire for IN or null country) — closing the confirmed zero-coverage gap without touching the matcher's own logic, which discovery found is already correct.

## G7.041 — Generic-country limitations
**Owner: reaffirmed — the public Resources site's complete absence of any auth/country gate is correct, confirmed-live behaviour, not a gap.** **Decision: no gate is added.** The `RESOURCES` capability manifest entry (`requiredCapability: LOCALISED_RESOURCES`, false for GENERIC) is corrected in documentation only to note it describes a **hypothetical future in-app Resources surface**, since no such surface exists today for it to actually gate — the public site this capability's own note references as "out of this authenticated-app scope regardless" is the entirety of what exists. No functional change.

## G7.042 — AU regulatory wording
**Owner split, per discovery's own finding of two genuinely different surfaces.** Reports/Dashboard engines: confirmed zero AU-regulator naming exists — **no ownership decision needed, nothing to own.** Resources CMS content (the real, dated, regulator-attributed super-guarantee-rate prose): **owner stays the Resources editorial/compliance workflow** (already the correct place for dated regulatory claims, per its own versioning/review-workflow infrastructure, G7.050/051 below). **Decision on the one real gap:** `jurisdiction` currently functions only as a browse filter/badge on this content, never a display gate or country-aware warning when a non-AU visitor reaches AU-specific regulatory prose. **A jurisdiction-aware caveat (not a hard gate — Resources stays intentionally unauthenticated and universally reachable per G7.041) is a new requirement**, explicitly deferred pending a dedicated content-warning-copy decision; this phase only confirms the gap exists and that the underlying `jurisdiction` field is the correct place to key such a caveat off, not a replacement mechanism.

## G7.043 — India regulatory wording
**Owner: `lib/engines/investment-intelligence/tax/*` stays canonical for India-specific regulatory wording (Section 111A/112A, Income-tax Act citations) — correctly scoped to Investment Intelligence, not Reports/Dashboard generally.** **Decision: no change to the underlying scoping mechanism.** Discovery found the AU/IN admission gate is correct *by data-shape coincidence* (only India-shaped CAS/mutual-fund data flows through this path today), not by an explicit country check — this is **noted as a residual risk, not fixed in G7**, matching the same "correct today, not correct by construction" pattern G6 already disclosed and declined to retroactively harden elsewhere (e.g., G6.087's no-DB-CHECK gap). An explicit `country_of_residence === 'IN'` check inside `loadTaxDataset`/`runTaxSimulation` is a **future hardening candidate**, not authorized here, since nothing is currently exploitable (no AU household can produce India-shaped disposal data today).

## G7.044 — NRI disclosures
**Owner: `withTaxDisclaimer()`/`NRI_SCOPE_DISCLAIMER` stay canonical for disclaimer *propagation* — confirmed live, correctly wired into the report via `buildTaxAndCost`'s `limitationText`.** **Decision on the real, doubly-instanced gap:** the `residencyProfile` derivation (self-declared `taxpayerType` only, never cross-checked against `country_of_residence`) is duplicated byte-for-byte between `app/api/investment-intelligence/tax/summary/route.ts` and `lib/services/investmentIntelligenceReportData.ts`. **G6.054's own remediation (cross-check against `country_of_residence`) must be applied to BOTH copies, not just the report loader** — discovery specifically flagged that patching only the report side would create a new divergence (report cross-checked, live UI not) where none currently exists (both are currently equally wrong). **Decision: extract one shared `resolveResidencyProfile(taxProfile, countryOfResidence)` helper** used by both call sites, following the exact `isDomesticRecord()` precedent from G6.034 (extract-and-share on the second confirmed duplication of the same logic, not two independent fixes).

## G7.045 — Calculation explanations
**Owner: the informal, per-engine `explanation: string` convention (13+ independent modules) stays as-is — no shared `Explainable` interface is imposed in this phase.** Discovery confirmed this is genuinely rendered, real, and functioning across Dashboard-adjacent UI and Reports, just never unified into one type. **Decision: no new shared infrastructure.** The one concrete, scoped fix: `sourceReferences` (Reports' own structured provenance field, confirmed backend-only per the module's own documentation) **should be rendered** in `ReportPreview.tsx` — this is completing an already-specified data contract the report engine already populates, not designing a new one. Unifying all 13+ modules' explanation strings under one shared type is **explicitly deferred** — a much larger refactor than this phase's boundary permits, and discovery found no evidence of the informal convention actually causing inconsistency severe enough to require it now.

## G7.046 — FX lineage display
**Owner: `getFxRateAudInr()` stays canonical for the current-rate value; `crossBorderCalculator.ts`'s forward-projected rate stays canonical for forecast display.** **Decision, directly building on G7.036's snapshot-provenance decision above:** once `report_snapshots.snapshot_metadata_json` records the rate/date used (G7.036), the `cross_border`/`cross_border_full` sections' own `limitationText` should be updated to **state the rate and its date** rather than only stating that no converted view exists yet — a display change unlocked by, and sequenced after, G7.036's data-availability fix, not an independent new mechanism. The forecast module's own rate display (`CrossBorderForecastPanel.tsx`) is reaffirmed as correctly scoped to planning assumptions and does not need retrofitting with historical-lineage semantics — the two remain deliberately distinct concepts (a live current/historical rate vs. a forward planning assumption), per discovery's own explicit distinction.

## G7.047 — Report export formats
**Owner: `lib/engines/reportExport.ts` stays the sole entitlement/implementation-status decision point — reaffirmed, `print`/`pdf` live, `csv` an honest, deliberate `not_implemented` stub.** **Decision: no change.** Discovery confirmed this is not a bug (explicit design comment, honest DB bookkeeping) and confirmed the napi-canvas/pdfjs-dist production-bundling concern this topic's own background referenced is **unrelated** — a different module (II/FDH document extraction) entirely. No ownership question to resolve here.

## G7.048 — PDF rendering
**Owner: `lib/services/reportPdfRenderer.ts` (real Playwright headless Chromium against the app's own print route) stays canonical — reaffirmed live, correctly currency-locale-aware via `Intl.NumberFormat`.** **Decision on the one real, disclosed inconsistency:** date formatting is hardcoded to `'en-AU'` everywhere regardless of `reporting_currency`. **Same decision as G7.032** — key the date formatter off `reporting_currency` the same way the money formatter already is; tracked once here as the rendering-layer instance of that fix (the four call sites discovery found — `reportsData.ts`, `ReportHistoryTable.tsx`, `ReportPreview.tsx` ×2 — all need the identical change, since they currently each hardcode the same locale independently, the same "repeated inline, never shared" pattern G6/G7 keep finding elsewhere). A4-only page sizing is reaffirmed as correct/unchanged — no country ever had a different page-size expectation built or removed.

## G7.049 — Accessibility and plain language
**New owner required.** Discovery confirmed zero ARIA/role attributes exist anywhere in the Reports rendering stack, and no accessibility audit has ever been scoped to Reports specifically (FDH-14's certification is a different module). **Decision: Reports gets its own accessibility pass, scoped identically to FDH-14's own precedent** (`docs/financial-data-hub/FDH14_UI_ACCESSIBILITY_SMOKE.md`/`FDH8_ACCESSIBILITY_CERTIFICATION.md` as the template to follow, not to extend) — a genuinely new requirement, not a regression, since no prior pass ever covered this surface. Scoping this to G7's own certification phase (not silently bundled into an unrelated fix) is the ownership decision; the actual audit work is implementation, not decided here.

## G7.050 — Content versioning
**Owner: reaffirmed, already correctly built and live.** `resource_post_versions` + `createResourceVersion()` + the versions API routes + `RevisionHistoryPanel.tsx` are confirmed a complete, already-wired mechanism — this is a documentation-correction topic, not an ownership decision. **Decision: the stale migration comment** (`0049`'s own text claiming "write path is deferred") **is corrected in a follow-up migration-comment/doc note**, since a comment asserting something false about live infrastructure is itself a minor but real defect (a future engineer reading that comment would wrongly conclude they need to build what already exists). No schema or code change — comment/doc accuracy only.

## G7.051 — Audit and provenance
**Owner: reaffirmed — `reports`/`report_generation_runs`/`report_snapshots`/`report_access_events`, plus migration `0070`'s RLS hardening, stay canonical.** Discovery found this the strongest-evidenced control set across all of G7 (real forgery reproduction, real fix, real cross-tenant re-verification, a genuine negative-control-of-the-negative-control). **Decision: no ownership change.** The one real, disclosed gap — the R10 repro/certification scripts (`scripts/r10_repro_*.mjs`, `scripts/r10_reports_rls_certification.mjs`) exist only as standalone manual scripts, never wired into `npm test`/CI — is a **regression-coverage gap, not an ownership gap**. **Decision: at minimum the PGlite certification script (`r10_reports_rls_certification.mjs`, which needs no live Supabase credentials) should be promoted into `tests/unit/` or an equivalent CI-runnable suite** so a future accidental RLS re-loosening would be caught automatically — the live-DEV two-user scripts can reasonably stay manual (they need disposable real accounts), but the PGlite one has no such constraint.

## G7.052 — Broken-link protection
**New owner required for two separate things discovery found.** (1) The 2 remaining live `href="#"` placeholders in `LandingPage.tsx` (forecasting-demo widget) are **not owned by G7's scope at all** — they predate this whole country programme and are unrelated to country/jurisdiction content; **flagged for a separate, ordinary bug-fix dispatch outside this programme**, not decided or fixed here. (2) The complete absence of any CI pipeline (`.github/workflows` doesn't exist) or automated link-checking is a genuine infrastructure gap. **Decision: G7 does not stand up a general CI pipeline** (far outside a country-programme's scope) but **does recommend, as a forward-looking note, that any future CI investment include a link-checker** — not an action item this phase executes.

## G7.053 — Premium-report regression
**Owner: `tests/unit/reportSectionsPremiumStressApplicability.test.ts` stays the canonical country/cross-border regression suite for Premium reports — confirmed real, thorough, and already the direct regression test for the currency-derived-country defect class (G0-JA-1 Wave 1's own fixed bug).** **Decision: extend the same pattern (AU/IN mismatch + unresolved-country negative control) to the other five Premium chapters** (Investment Performance, SIP, X-Ray, Tax & Cost, Priority Review) that currently have zero country dimension in their own tests — a coverage-completeness decision, reusing the existing fixture/assertion pattern rather than inventing a new test methodology.

## G7.054 — Privacy and redaction
**Owner: reaffirmed — `redactPanFromLine()`/`maskPan()` stay scoped exclusively to Investment Intelligence's own parsing/provenance layer.** Discovery confirmed Reports has no code path that could reach `ParsedAccountRecord.raw` at all (the report-side II loader only ever consumes pre-aggregated computed results). **Decision: no redaction logic is added to Reports** — there is nothing there to redact, and adding a defensive redaction layer for data that structurally cannot appear would be scope invention, not hardening. **One documentation decision**: the "Reports never touches raw parsed statement text" boundary is **written down explicitly** (in `investmentIntelligenceReportData.ts`'s own header comment, alongside its existing "never recalculate/never touch a new dataset" governing rule) so this separation is asserted by design going forward, not merely true by accident of current code structure.

## G7.055 — Negative controls
**Owner: split by surface, per discovery's own finding of differing durability.** Resources' own-content isolation and the unauthorized-export gate stay owned by their existing, CI-runnable `tests/unit/*` suites — reaffirmed, no change. Reports' cross-tenant RLS certification (`scripts/r10_*.mjs`) is **the same gap as G7.051** — promoting the PGlite script into CI-runnable form is the one decision made here, tracked jointly with G7.051 rather than as a separate action. GENERIC-country report-generation denial stays owned by `requireCountryConfirmedUser()` at the API-gate layer (correct, reaffirmed) — **a direct report-level test asserting this specific denial is added**, closing the "enforced but untested at this layer" gap discovery found, reusing the existing gate rather than adding a second one.

## G7.056 — Rollback and withdrawal
**Owner split, per discovery's clear finding that these are two different states today.** Resources' withdrawal path (`lib/resources/public/visibility.ts`'s `PUBLIC_STATUSES` policy, no ISR/CDN cache layer) is **reaffirmed as genuinely clean** — no change. **Reports' withdrawal path has a real, previously-undetected gap**: `archiveReport()` correctly soft-deletes and `listReports()` correctly excludes archived reports, but `getReport()` (backing both the detail page and its API route) has no status filter at all, so an archived report's direct URL still serves full content indefinitely. **Decision: `getReport()` must exclude `status = 'archived'` for the owner's own direct-view path** (the same function already correctly excludes archived rows from the list — it should reject them from direct-by-id fetch too, returning a "this report was removed" state instead of the full content), and `getReportByRenderToken()` should carry the same check for consistency — this is a genuine, disclosed defect fix, not a new mechanism, since the exclusion pattern already exists one function away (`listReports()`) and only needs to be applied consistently.

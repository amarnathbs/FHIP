## 1. PO-D24-02: "I don't have any retirement savings" cannot be saved while retirement items exist

**Canonical mutation paths found.** Two stores written together by the grid: `PUT /api/user/profile` (`user_profiles.not_applicable_retirement`) and `PUT /api/user/section-status` (`user_financial_section_status`, section retirement, status `not_applicable`). The engine lets `not_applicable` win over rows (`effectiveSectionStatus`), which is why a contradiction silently removed Retirement from the Health Score. `reviewed_zero` is self-correcting when rows exist, so it is not blocked.

**Rule (one shared service, `lib/services/retirementDeclarationGuard.ts`).** Refuse with **409** `RETIREMENT_DECLARATION_CONFLICT` while the person has any active `retirement_accounts` row (`is_active` not false) other than the SMSF fund mirror row, or any active `smsf_funds` row. The SMSF fund and its mirror row count once. Inactive items are ignored. Clearing (false / null) is never refused. The message says what, why and how: "This was not saved. You have 2 active retirement accounts and an active SMSF, so ... would contradict what you have entered ... Remove or deactivate them first (Investment & Retirement > Retirement), then confirm you have none." The grid now shows the server reason (`grid-not-applicable-server-refusal`) instead of silently un-ticking.

**No race.** (a) Check before any write (nothing in the request is saved when refused). (b) Re-check after the write; if an account or SMSF landed in the gap the previous value is put back exactly (profile flag, or the previous section confirmation) and the 409 is returned. (c) **Migration 0298** puts the same rule in the database: two before triggers (`user_profiles` on the flag becoming true, `user_financial_section_status` on retirement / not_applicable) that take a per-person advisory transaction lock, count the same items and raise `RETIREMENT_DECLARATION_CONFLICT` (errcode 23514). So a direct REST call with the person's own session is also refused; the routes map that error to the same readable 409. Only the transition to true is checked: an old contradictory row is not touched and does not block unrelated edits.
Residual window (stated honestly): the trigger lock serialises declarations, but I did not add triggers on `retirement_accounts` / `smsf_funds` inserts. So "declare, then add an account a moment later" is the legitimate sequential order, and the UI already warns for it (`grid-not-applicable-contradiction`). The route re-check closes the other order.

**Tests.** `wpIRetirementDeclarationGuard.test.ts` (20, real route handlers over the in-memory PostgREST double): direct API bypass on both routes, accounts + SMSF, SMSF-only (one item, message does not invent accounts), inactive accounts and inactive SMSF allowed, null `is_active` counts as active, clearing allowed, unrelated profile edits and the other two declarations unaffected, two-user isolation both directions, both race re-checks, DB-refusal mapping. `wpIRetirementDeclarationGuardPglite.test.ts` (12, PGLITE-VERIFIED): direct updates and upserts refused as the person, SMSF-only, inactive allowed, deactivate-then-declare, clearing and legacy-contradiction edits, two-user isolation on both stores, idempotent migration, editor-safe, additive. **Negative controls (demonstrated):** counting disabled in the service made 10 named tests fail; dropping the two triggers in PGlite shows the same direct writes succeed (the guard is the only thing preventing the contradiction), then the migration is re-applied and refuses again.

## 2. PO-D24-01: Family Retirement Forecast

**Personal forecast untouched.** `buildCalculatorInput` is called unchanged for the personal input; its input hash, rows and explanations are not modified. The new function `runFamilyRetirementView` is read-only (no `forecast_runs`, results or explanations row is written, tested). Family = same calculator, same assumptions, same timing (WP-D `retirementTiming` resolver, saved age), same target method, with exactly two numbers added to the personal input: opening and monthly flow.

**SMSF opening** = the fund's one canonical net from the same builder the Dashboard family level uses (`loadSmsfBalanceSheets` -> `buildSmsfBalanceSheet`): itemised = assets less liabilities (the derived Detailed value, equals `smsf_fund_counted_net`; legacy linked personal loans counted once, as on the Dashboard); net-value-only = the typed net. Never Summary + Detailed, the fund account row never added on top, a stale typed figure on an itemised fund ignored, not clamped (an underwater fund reduces the family position and the card says so), unconvertible lines left out and counted. Converted once with the forecast's own FX context (the same one the personal part uses).

**SMSF flow** = ledger rows with `destination_kind = 'smsf'`, `status = 'active'` for each active fund (destinations from the WP-C interface `listSmsfContributionDestinations`), resolved by WP-D's own series rules (`resolveAccountRates`: repeated payslip = one contribution, one-off is history, unknown frequency left out and counted). For a kind (employer / personal) the ledger holds nothing for, the fund account's own figure is used; a kind the ledger governs is never also read from the account column (one flow, one source, LR-FI-3). If the ledger table is not available (0304 not applied) the account figures are used and the card says so. Note: for the rate itself I used WP-D's `listLedgerRows` + `resolveAccountRates` rather than `loadSmsfContributionHistory`, because the latter's entries lack the fields the series rules need (employer key, created date, legacy marker); fund and account discovery use the WP-C interface.

**Surface.** `POST /api/forecast/retirement/family` (signed-in, same body as the personal run, retirement only, never a user id from the body). On `/forecast/retirement` the page tells the panel whether an active SMSF exists; only then does Generate also request the family view, and only then does the card **"Family retirement position (Personal + SMSF)"** render (Personal row, SMSF row, Family row: starting balance, added each month, projected at retirement; family corpus, gap, readiness; plain notes). No SMSF: no card, no hint, endpoint answers `{available:false}`.

**Oracle (hand-computed, `wpIFamilyRetirementForecast.test.ts`, 20 tests, through contribution service -> ledger -> real balance-sheet loader -> real calculator):** personal super 100,000 and SMSF Detailed 400,000 -> personal opening 100,000, SMSF 400,000, **family 500,000** (not 900,000 = fund row + Detailed on top; not 650,000 = stale Summary on top). Personal 1,000 + SMSF 2,000 a month -> **family flow 3,000** (not 5,000 = ledger + the derived account column). Projection matches the hand future value at 6.5 percent for 191 months within cents for personal, SMSF and family, and family = personal + SMSF. The real personal `runForecast` still opens at 100,000 and flows 1,000 and its balance / corpus / readiness equal the personal figures in the family view. Also: Detailed with a liability (400,000 + 25,000 less 80,000 = 345,000), Summary mode (250,000, stray holdings ignored), underwater fund (-30,000), series and one-off rules, legacy account figure beside a ledger kind (2,500), ledger-unavailable fallback, no-frequency contribution, no SMSF, archived SMSF, two-user isolation (both directions). Route test (4) and static render tests (card rows, hint only with an SMSF). **Negative controls (demonstrated):** adding the fund row on top made 5 tests fail; reading ledger and column both made 4 fail.

**Known limits.** The family view uses the person's own (Self) retirement timing and does not model SMSF member ages separately. The Dashboard's family level reads the first SMSF sheet only (existing behaviour of `netWorthLevels`); the family forecast sums all active funds, so they would differ for a person with two SMSFs (flag for the PO). Dates: none shown.

## 3. Entity mode switch Undo (Company, Family Trust, HUF)

**Decision.** The itemised-or-net switch **changes the canonical valuation source** (an itemised entity is counted at assets less liabilities, a net-value-only entity at its typed net, so `net_before` -> `net_after` moves the family figure; the PGlite test shows a 600,000 -> 650,000 move). It is not presentation, so a cosmetic or absent Undo was not acceptable. The SMSF already had one; the entities did not (WP-C item 3).

**Built.** Migration **0299** `business_entity_undo_last_switch(entity, confirm)`: undoes only the NEWEST history row and only if it is a switch (a second undo is refused, so changes are undone once and in order). Preview first (confirm false does the work in a sub-transaction and rolls back, returning net before/after and how many lines would be archived or restored). To net-value-only: every active line is archived (`is_active` false, never deleted) and written into the new history row, the typed net recorded by the switch is restored. To itemised: the lines the switch archived come back (their ids were recorded in the history row), the typed net standing at that moment is cleared and kept in the history row. The either-or rule always holds (verified: `business_entity_mode_rule_violations()` empty after each undo). History row action `undo` with `undoes_log_id`. Security definer, scoped to `auth.uid()`, another household answers not found. Route `POST /api/business-entities/[id]/undo-switch` (preview-first, `confirm` default false), UI: "Undo the last change" in `EntityModeChooser`, offered only when the history says the newest row is a switch, confirmation dialog with the plain effect ("2 assets and 1 liability are archived, not deleted, and kept in the history" / "brought back"), history shows "Undid the last change". `smsfRpcError` now also strips the `entity:` prefix (one-line change to a WP-C file) so users do not see it.

**Tests.** `wpIEntityModeUndoPglite.test.ts` (8, PGLITE-VERIFIED, 600,000 trust -> 650,000 -> undo -> 600,000; company 250,000 -> 350,000 (+10,000 line added later) -> undo -> 250,000 with all three lines archived and kept; preview changes nothing; no duplicated lines; second undo refused; switch again afterwards works; two-user isolation; unauthenticated refused; migration hygiene), `wpIEntityModeUndoRoute.test.ts` (7). **Negative control (demonstrated):** removing the asset re-activation made 2 named tests fail; and a test shows the only alternative (switching again) re-types lines and leaves the originals archived, which is the gap.

## F15 - Expenses bank-statement import "extracting transactions" then an error

| Field | Content |
|---|---|
| Finding | F15 |
| PO comment | "Expense bank statement upload is not working it took some time showing extracting transactions after that error message". Screenshots: "Scanning your document for safety ..." then "Processing your statement - extracting transactions..." then "We could not process this bank statement." with Try again. |
| What the screenshots prove | The upload request SUCCEEDED (the scanning state only appears after it), the safety scan then cleared (the panel moved on), and the failure is in the PROCESS step. The sentence on screen is either the panel's own fallback (a response with no JSON, such as a gateway page) or the process route's fixed 500 sentence. Both are the same words; the route logged nothing. |
| Stage-by-stage, DEV, real routes, real S3 + GuardDuty scan (all DEV-verified) | Upload with owner chosen first: 200, account created or reused. Malware admission before any parsing: scan clean, then queued. Account assignment: set on every document. Native CSV (10, 120, 400, 1500 rows) and certified-layout PDF (3 and 400 lines): detect, process, certify, reconcile, approve: all 200. Classification (categorise route): ran. Review (set-category) and Accept (bulk-approve): ran. Apply (Expenses tab reads approved lines): correct. No stage other than PROCESS TIMING failed. |
| Timing (DEV, from a workstation with high latency to DEV; database-bound steps are overstated, the AI reading time is real provider time) | Native CSV process: 120 rows 6 s, 400 rows 15 s, 1500 rows 20 s (parsing itself is 0.57 s for 5000 rows: the time is database round trips). Certified PDF process 400 lines 21 s. Real bank PDF in an UNRECOGNISED layout (the normal case for a real bank PDF) reads through the AI fallback inside the same request: 25 lines 29.6 s, 120 lines 66 s (past the route's own 60 s maxDuration too). The platform ends a request at 28 s. |
| Root cause | The PROCESS request is synchronous and unbounded: a statement that needs more than the platform limit has its request ended without the handler running its catch. (1) The browser gets a gateway page and says "We could not process this bank statement." (2) The document is left in `processing` for ever with whatever rows were already committed. (3) PDF: every retry was then refused with "cannot process while the document is processing" (a dead end). CSV: the retry re-ran on top of the partial rows, which the dedup index read as duplicates of the same statement (DEV: killed at 500 of 3000 rows, retry answered 200 with only 2500 created, 500 reported as skipped duplicates of itself); and a fresh upload of the same file would silently lose those rows. (4) The route swallowed the real exception with no log, so the failing stage was invisible. |
| Not owner / account / malware / classification | Verified not the cause: owner-before-upload contract (owner required, 422 without; all DEV uploads carried one), account assignment, malware admission before the parser, certification contract (certified results returned as certified), classification, review, approval. |
| Regression? | Not a regression of owner-before-upload. The synchronous design predates it; the AI fallback for bank PDFs (23-09-2026) and the Premium AI switch (14-10-2026) made the long path the normal path for real bank PDFs. Severity High (a Premium user cannot import a real bank PDF). |
| Fix (narrow, server contract first) | services/interruptedRun.ts + both bank processing services: a document in `processing` is LIVE (409 `statement_in_progress`, never started twice) or DEAD after 120 s (partial rows removed, started again cleanly). bank-csv/repository.ts: the partial rows of a dead run are removed before the dedup index is read, so a fresh upload loses nothing. Both process routes log the failing exception (class and message, no content) and answer `{ error: 'process_failed', message }`. Browser: components/expenses/processResume.ts + the panel ask again (bounded, 5 s apart, up to 30 times) on a gateway error, dropped connection or the in-progress answer, show "Still reading your statement ... nothing is lost", and end with a plain sentence that offers a CSV. No migration. |
| NOT fixed (needs a PO decision) | A statement whose single reading genuinely needs more than 28 s (a real PDF through the AI fallback, about 40 lines or more in DEV) still cannot finish inside one request. The retry now recovers a reading that finished and was saved after the response was cut (a saved AI draft is returned again without a second provider call) and never double-writes, but a reading that cannot finish inside the function's own limit keeps restarting. The structural fix is to take the AI reading out of the request: read the pages in parallel in small groups, or run it as a background job with a status poll. That changes AI cost and cap handling, so it is a PO / architecture decision, not a patch here. |
| Test | tests/unit/doc2_4_wpE_interruptedRun.test.ts (11 tests): run state; PDF and CSV live/dead behaviour with the in-memory database; dedup index excludes only dead-run rows; browser retry classification and bounds; the two real route handlers' 500 code and 409. Negative control: with the five source files reverted to origin/main, 6 named tests fail (PDF live, PDF dead, CSV live, CSV dead, dedup index, route codes). |
| DEV proof | scripts/doc2_4_wp_e_dev_run.ts. bank / bankscale: CSV and certified PDF journeys pass before and after. killresume (server process tree killed after the first 500 of 3000 rows, fresh server started): BEFORE the fix the retry answered 200 with 2500 created (partial rows read as duplicates of themselves); AFTER: immediate retry 409 statement_in_progress, retry after the run is old: 200, exactly 3000 transactions, 0 duplicates, certified rows 3000, duplicate rows 0, reconciled; a fresh upload of the same file adds nothing (3000 total). applyflow (Upload, Analyse, Review set-category, Accept bulk-approve, Apply Expenses tab): first statement 5 expense lines, 12425.00; the same statement in a different file adds 0 (10 skipped as duplicates); an overlapping statement adds exactly its 3 new lines (12471.50 = 12425.00 + 46.50) and skips 5; a byte-identical re-upload adds nothing. bankai: measured the timings above (before and after identical, the fix does not shorten the reading). |
| Honest limits | The PO's own file and production were not available, so it is NOT PROVEN that his file took the AI path; production's record of his failed upload is the proof, and `docs/reviews/po_apply_wp_e/01_READ_ONLY_find_the_failed_bank_import.sql` (read only) shows it. The 28 s kill itself cannot occur on a local dev server; it was emulated by killing the server process tree mid-run. The PDF dead-run recovery is UNIT-TESTED only (the CSV one is DEV-verified). The same client pattern exists in the liability, retirement and investment statement panels and was NOT changed here. |
| Verdict | CONDITIONAL. Interrupted runs, duplicate/missing rows, invisible failures and the dead-end retry are fixed and proven; a real bank PDF whose AI reading alone exceeds the request limit still needs the structural change above (PO decision). |

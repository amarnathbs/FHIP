## End-to-end journey (spec section 45)

Exercised via `PayslipImportPanel.tsx`'s state machine against
`payslipProcessingService.ts` + `incomeProposalService.ts` +
`applyIncomeProposalAtomic.ts` — the same code path
`fdh9_certification.mjs` exercises at the database layer:

```
Income tab -> Import from Payslip -> upload (country=AU) -> process
  -> parsePayslipText detects AU (PAYG/superannuation/ABN/TFN signals)
  -> reconcileGrossToNet -> matchSalaryDeposit (bank candidates within
     ±7 days of payment_date) -> review screen (gross/ordinary/overtime/
     PAYG/employer-super/net, reconciliation status, bank-match status)
  -> Approve (fdh9_approve_payroll_event) -> Generate proposal
     (incomeAdapter.buildProposal: recurring gross excludes overtime/bonus,
     frequency mapped to the canonical AU vocabulary) -> Compare screen
  -> Apply (fdh9_apply_income_proposal) -> Income updated
```

**Live-DEV status**: this exact route-level journey has **not** been run
against a real Supabase project (`FDH9_LIVE_DEV_CERTIFICATION.md`). What is
certified here is: (a) the parser/reconciliation/bank-match logic
independently, at 278/278 against hand-computed AU oracles; (b) the atomic
apply RPC's `add_new`/`update_existing`/`apply_selected_fields` paths, live
against real Postgres via PGlite (`fdh9_certification.mjs`); (c) the new
route/service/UI wiring connecting the two, by direct code inspection and by
the auth/validation tests in `fdh9IncomeTabUx.test.ts`. The three together
are strong evidence the AU journey is correctly wired, but do not
individually or collectively constitute a live-DEV E2E run through the
actual browser against actual Supabase, which is the specific claim spec
section 45 asks for and which this environment cannot currently make.

## AU-specific financial rules verified

- **Employer super is evidence, never income** — `computeRecurringGross()`
  never adds `employerRetirementContribution`; the review screen labels it
  explicitly "evidence only — not added to your income".
- **Salary sacrifice** is captured as its own column
  (`salary_sacrifice`, structurally distinct from `employee_deductions_
  total`), never silently folded into a generic deduction figure that
  could double-count against a component-level reconciliation.
- **PAYG withholding** (`tax_withheld`) is extracted and shown but never
  used to compute an annual tax liability anywhere in FDH-9.

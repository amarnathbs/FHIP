# FDH-8 — Accessibility & Responsive Certification

**STATUS: CODE-VERIFIED + PARTIAL LIVE VERIFICATION — 2026-08-25.** Supersedes the prior version, which was code-review-only (no DEV credentials, no browser available). This pass has live DEV credentials and a real running app; a genuine live authenticated keyboard/AT walkthrough of the FDH-8 pages themselves was attempted but not completed (see "What was attempted and blocked" below) — reported honestly rather than rounded up.

## What was verified LIVE this session

Using the Claude Browser tool against the real running app (`http://localhost:3232`):

- **The login page's real accessibility tree** (`GET /login`, read via the browser's accessibility-tree reader, not source-code inspection): a proper `<form>` element, each input has an associated `<label>` (`Email`, `Password`, both correctly exposed as accessible names on their `textbox` roles), a `submit`-type button labelled "Log in", a "Forgot password?" link, and Google/LinkedIn OAuth buttons each with a real accessible name (not icon-only). Keyboard `Tab` navigation was exercised between the email and password fields and worked (focus moved correctly). This is genuine live evidence — not a code read — that this app's auth surface, which every FDH-8 page sits behind, has a real accessible foundation.
- Logging in as a freshly-created DEV test user to reach the authenticated FDH-8 pages themselves was attempted (form filled via both `form_input` and native keystroke simulation, submit triggered both by click and by `Enter`) but the session never authenticated within this browser-automation session — no auth network request was observed reaching Supabase, suggesting a browser-automation/input-event compatibility issue in this specific tool combination, not an application defect (the identical credentials worked correctly moments earlier via the live-DEV certification script's real HTTP `signInWithPassword` calls in `scripts/fdh8_live_dev_certification.ts`, which is real proof the auth backend itself works). Given the time cost of further debugging a tooling issue unrelated to FDH-8's own code, this was not pursued further this session.

## What was verified by code reading (all FDH-8 files, re-confirmed this session)

- **Semantic `<table>` markup**, not div-grids, with `<th scope="col">` headers: Transaction Explorer, Recurring table, the Overview trend's accompanying data table, and the new Review workspace's queue table (`ReviewWorkspace.tsx`) all use real `<table>`/`<thead>`/`<tbody>` with `scope="col"` headers and a `<caption className="sr-only">` — verified by reading each file's JSX directly, not inferred.
- **Every chart paired with an adjacent text/data alternative**: `AllocationPieChart`/`TrendLineChart` (both reused as-is from `components/dashboard/charts.tsx`) are marked `aria-hidden="true"` at the SVG/canvas level in that shared component (verified: `charts.tsx:94`), and every FDH-8 page rendering a chart places a `sr-only`-captioned `<table>` with the same numbers immediately alongside it (`activity/page.tsx`'s Monthly Trend section).
- **No colour-only status signalling**: every "Approved"/"Pending"/review-category chip renders both a text label and a colour class together (e.g. `activity/page.tsx`'s "Needs attention"/"Transfers"/"Duplicates" chips, `transactions/page.tsx`'s Approved/Pending badge) — never colour alone.
- **Loading state never flashes $0**: `app/(app)/financial-data-hub/activity/loading.tsx` (new this closure pass) provides a route-segment loading skeleton (`ResourceLoadingSkeleton`) so a slow server response shows an explicit loading UI, never a blank page that could be followed by a jarring content swap; no FDH-8 page renders a numeral before its real `await` resolves (all are server components that compute the real value before first paint).
- **Error vs no-data distinction**: `ResourceErrorState` (backend failure, explicit message) vs `ResourceEmptyState` (genuinely no approved activity, with a link to the upload flow) are used throughout — never a silently-rendered `$0` standing in for either. Verified in `activity/page.tsx`, `transactions/page.tsx`, and the new `review/page.tsx`/`ReviewWorkspace.tsx`.
- **Descriptive accessible names**: every interactive control in the new Review workspace has a real name — `aria-label="Corrected category"`/`"Corrected transaction type"` on the two correction selects, `<label htmlFor>` pairs for the correction-field select, real button text ("Approve", "Confirm", "Reject", "Confirm duplicate", "Keep both") rather than icons, and the queue table's per-row action reads "Review transaction" (not "Click here").
- **Responsive layout**: uses the same Tailwind grid/flex conventions already certified elsewhere in this codebase (`grid-cols-1 sm:grid-cols-2 lg:grid-cols-4` etc.) — no new layout primitive introduced.

## Multi-currency (spec Phase L, verified live)

Every FDH-8 aggregate is grouped by `currency_original`/`currencyCode` before any arithmetic — confirmed both by code reading (`groupByCurrency()` in `financialActivityAnalytics.ts`) and live: the Tenant B control row (Case in `FDH8_LIVE_DEV_CERTIFICATION.md`) and every scale-certification total in `FDH8_SCALE_CERTIFICATION.md` came back as a single-currency (AUD) array element, never a blended cross-currency sum. No FX conversion layer exists in FDH-8 by design (spec permits currency-separated display in the absence of a certified FX layer) — unchanged from the prior pass.

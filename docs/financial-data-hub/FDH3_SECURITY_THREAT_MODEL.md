# FDH-3 — Security Threat Model

Per spec section 101. Each row: threat, control, test, residual risk.

| # | Threat | Control | Test | Residual risk |
| --- | --- | --- | --- | --- |
| 1 | Cross-tenant document access (metadata) | RLS owner-only policy on `fdh_upload_sessions`; existing RLS on `fdh_statement_uploads`/`fdh_ingestion_jobs` | `fdh3_rls_certification.mjs`: Tenant B cannot read Tenant A's session (leaked 0) | None identified — proven live with a genuine negative control |
| 2 | Cross-tenant document access (FK-existence bypass, FDH1-F1) | Two new owner-assertion triggers on `fdh_upload_sessions`/`fdh_ingestion_jobs`, independent of RLS | `fdh3_rls_certification.mjs`: forged cross-tenant insert raises "cross-tenant reference"; same-tenant control succeeds | The remaining ~85 historical FKs across the platform are still unhardened — tracked as the still-OPEN global FDH1-F1 finding |
| 3 | Signed URL theft | 60-second TTL, single object, issued only after ownership+not-purged check; never logged (`services/auditLog.ts` metadata never includes a URL) | `fdh3_dev_certification.mjs`: signed URL resolves real bytes while valid, then fails after purge | A URL is a bearer credential for its 60-second window if intercepted in transit (mitigated by HTTPS, standard for the whole app) |
| 4 | Public bucket exposure | `public: false` at bucket creation; SELECT-only storage policy; no `using (true)` anywhere | `fdh3_dev_certification.mjs`: bucket's own public URL returns HTTP 400, not the object | None identified |
| 5 | Privileged key exposure to browser | `SUPABASE_SERVICE_ROLE_KEY` read only in `lib/supabase/admin.ts`; used only in 3 server-only service files | Static grep of `app/`/`components/` for the key name and `service_role` outside approved files — zero matches (see Completion Report §Security Static Analysis) | None identified |
| 6 | Malicious file upload | Strict PDF/CSV allowlist; magic-byte verification; no execution; no HTML rendering of raw bytes | `fdh3Domain.test.ts`/`fdh3UploadTestPack.test.ts`: renamed executable rejected, garbage bytes rejected | **No malware/AV scanner integrated** — a well-formed malicious PDF/CSV that passes structural checks is not caught. Disclosed, not hidden — see `FDH3_STORAGE_SECURITY.md` §6 |
| 7 | MIME spoofing | Declared MIME compared against magic-byte detection; mismatch → `mime_mismatch` | `fdh3Domain.test.ts`: real CSV bytes declared as PDF → rejected | Detection is signature-based, not exhaustive format validation (e.g. a byte-perfect polyglot could theoretically pass — considered extremely low likelihood for PDF/CSV specifically) |
| 8 | Oversized-file attack | Per-type size limits (20MB PDF / 10MB CSV); a hard `Content-Length` pre-check at the API layer before the body is read into memory | `fdh3Domain.test.ts`: file exceeding the limit rejected before content inspection; API route rejects on `Content-Length` alone | None identified for the declared-size path; a request that lies about `Content-Length` and streams more bytes than declared is bounded by Next.js/the platform's own request-body limits, not something FDH-3 re-implements |
| 9 | Orphan file retention | `domain/orphanDetection.ts` pure comparison function; `services/storage.ts#listObjectsUnderUserPrefix()` read-only live listing | `fdh3Domain.test.ts`: drift correctly identified in both directions | Full live orphan REPORT (storage listing cross-referenced against live DB rows) not yet run — needs migration 0058 applied first |
| 10 | Purge failure leaving a "deleted" document actually present | Purge never marks `purged` before an independent post-delete `verifyDocumentObjectAbsent()` check succeeds; DB constraint refuses `purged` status while a storage reference remains | `fdh3_rls_certification.mjs` (DB constraint) + `fdh3_dev_certification.mjs` (live delete-then-verify) | None identified |
| 11 | Admin overreach | Zero admin route/page/service anywhere reads FDH data beyond the pre-existing operational-metadata allowlist; `fdh_upload_sessions`/`fdh_document_audit_events` both explicitly listed as no-standing-access | `fdh1Isolation.test.ts`: greps the entire admin surface (`app/api/admin`, `app/(app)/admin`) for any FDH reference — zero found | None identified — this is a hard, mechanically-tested invariant |
| 12 | PII in logs | Controlled error-code taxonomies only; purge error messages sanitised (URLs redacted, capped at 200 chars); audit-event metadata is always structured, never free document content | Code review of every `console.error`/audit-metadata call site in the 3 service-role files (all pass structured, bounded fields) | No automated log-scanning test exists yet — this is a manual-review guarantee, not a mechanically enforced one, disclosed as a gap |
| 13 | PII in object names | Opaque `{user_id}/{document_id}/{document_id}.bin` key, never a filename | `fdh3Domain.test.ts`: key never matches filename/institution/email patterns | None identified |
| 14 | Password leakage | No password is ever accepted, stored, or logged anywhere in FDH-3 — a password-protected PDF is detected structurally only and left for a future parser phase to handle transiently | Code review — `password_required`/`password_invalid` are pure status codes, never carry the password value; grep confirms no field named `password` exists on any FDH-3 table or type | None identified — FDH-3 has no code path that could leak a password because it never receives one |
| 15 | Upload-session hijacking/race conditions (spec section 96) | Sessions are single-use (terminal on `upload_complete`/`expired`/`failed`); `assertSessionIsLive()` rejects a late/duplicate completion callback and an expired-session completion attempt; a partial unique index prevents two concurrent live sessions for the same document | `fdh3Domain.test.ts`: completion on an already-completed session throws; completion on an expired session throws | A true concurrent double-completion race (two simultaneous requests both passing the liveness check before either writes `upload_complete`) is bounded by Postgres row-level locking on the `update` but was not exercised under real concurrent load — disclosed as untested, not claimed proven |

## Summary

15 threats assessed. 11 have a control with a passing, non-vacuous test and
no disclosed gap. 4 carry an honestly disclosed residual gap (#6 no malware
scanner, #9 orphan report not yet run live, #12 log-PII review is manual not
automated, #15 concurrency proven only at the domain-logic level, not under
real load) — none of these four are silently omitted; each is named again in
`FDH3_COMPLETION_REPORT.md`'s Known Findings section.

## Headline finding

**The canonical Investment Intelligence schema (`ii_instruments`/`ii_accounts`/`ii_transactions`/`ii_holding_snapshots`) already proved jurisdiction-agnostic before FDH-11 was ever scoped.** R12 ("Wider India Assets") added direct-listed-equity/ETF support to the exact same mutual-fund ledger, using `instrument_class IN ('equity','etf')`, `nse_symbol`/`bse_code`/`isin` identifiers, and `ii_accounts.account_type = 'broker'` — none of this is India-specific at the schema level; only the two *parsers* (`camsParser.ts`/`kfintechParser.ts`) and the *tax engine* (`capitalGainsEngine.ts`, `financialYear.ts` hardcoded to 1 Apr–31 Mar) are India-specific. FDH-11 therefore does not need a parallel schema for AU equities/ETFs — it needs new AU statement parsers/adapters and a genuinely new pre-canonical review/apply layer, feeding the *same* ledger via one narrow additive identifier-scheme extension (`asx_ticker`).

**FDH1_INVESTMENT_BOUNDARY.md (Product Owner Decision 2) explicitly anticipated FDH-11 by name** — it sketched (but left unimplemented) "a single one-way adapter function" from FDH-owned evidence to an II ingestion contract, and flagged reconciling with `ii_source_documents` as "an open item for FDH-11." This audit resolves that open item: AU statements upload through FDH-3's `fdh_statement_uploads` (already reserving `document_type = 'investment_statement'` since migration `0045`), not through `ii_source_documents` (which remains India-CAS-specific); the one-way adapter is `lib/investment-import-bridge/`.

## Answers to the explicit architecture questions (spec section 12)

1. **What does Investment Intelligence already own?** The entire canonical ledger: `ii_accounts`, `ii_instruments`/`ii_instrument_identifiers`, `ii_transactions`, `ii_tax_lots`/`ii_tax_lot_consumptions`, `ii_holding_snapshots`, `ii_prices_nav`, `ii_reconciliation_cases`, `ii_portfolio_truth_status`, `ii_review_items`, plus performance/risk/SIP/x-ray/tax engines and the publish bridge into `investments`.
2. **What does the India Investment module own?** Concretely: two RTA statement parsers (CAMS/KFintech), India-specific tax engine (grandfathering, Section 111A/112A/50AA, FY 1 Apr–31 Mar), the `/investment-intelligence` UI. It is *not* a separate schema — it is the India-only *parsers and tax rules* layered onto the same jurisdiction-agnostic II schema.
3. **Which II services are already reusable for Australia?** The whole canonical schema, `resolveOrCreateInstrument`/`resolveInstrumentIdFromIdentifiers`, the FIFO lot engine (schema-level, tax-treatment not wired), the AUD↔INR FX rate, and the R3 publish bridge (already AU-aware).
4. **What AU statement ingestion is genuinely missing?** Everything: statement detection, CSV/PDF extraction, account/security/bank matching, holdings/cash reconciliation, review UX, staged evidence storage, and the Apply bridge into the canonical ledger.
5. **What AU canonical processing is genuinely missing?** AU CGT (discount method), franking credits/dividend imputation, a distinct "distribution" transaction type, and any canonical representation for broker-cash-only events (deposits/withdrawals/interest not tied to a security) — `ii_transactions.instrument_id` is `NOT NULL`, so these cannot be written today. All four are disclosed as genuine II schema/engine gaps, not worked around here.
6. **Which India concepts are globally reusable?** The parser-interface *pattern* (not the interface itself — `InvestmentDocumentParser` bakes in India-MF fields), the fingerprint-dedup mechanism, the reconciliation-case/portfolio-truth model, the identifier-resolution algorithm, FIFO lot matching.
7. **Which India behaviours are genuinely India-specific?** CAMS/KFintech parsing, grandfathering/Section 111A/112A/50AA tax treatment, the 1 Apr–31 Mar financial year, AMFI-scheme-code/plan/option matching.
8. **Does II already provide a canonical import/review/apply pathway?** Two, and neither fits AU as-is: (a) R2's auto-apply-on-parse pipeline (no human gate), (b) R9's Review Centre (post-hoc observations about already-canonical data, not a pre-write gate). FDH-11 builds a third, narrow layer specifically for the pre-write gate spec sections 63-65 require.
9. **Are holdings ledger-derived or directly stored?** Both: `ii_transactions` is the ledger; `ii_holding_snapshots` is a point-in-time evidence/certification snapshot, never itself "the" canonical holding.
10. **Are positions snapshots, canonical records, or both?** Snapshots — see above; no separate "canonical position" table exists.
11. **How are transactions deduplicated today?** Two layers: `transaction_fingerprint` (SHA-256 over resolved account/instrument/date/type/amount/units, DB-unique via `uidx_ii_transactions_fingerprint`) and, for CAS statements, `source_reference`-based dedup (`uidx_ii_transactions_dedup`). FDH-11's bridge reuses the fingerprint layer.
12. **How are securities resolved today?** ISIN (global) → AMFI/name+plan/option (India-specific, country-scoped) → controlled alias map → provisional creation. FDH-11 adds ISIN → `asx_ticker` (country-scoped) as the AU-equivalent chain, with no fuzzy-name tier.
13. **How are goal relationships preserved today?** `goal_funding_sources` (country-neutral, pre-existing), mirrored by `ii_goal_allocations`. FDH-11 does not touch either.
14. **How are investment values incorporated into net worth today?** Only via the `investments` table, populated either manually or through the R3 publish bridge — never read directly from any statement-evidence table.

## Disclosed gaps and scope reductions carried into this pass

- Only ONE certified AU statement layout pair (a generic transaction CSV + a generic portfolio CSV) — no named-broker (CommSec/Selfwealth/CMC/Stake/nabtrade/Westpac/Macquarie) adapter was built; no real sample statements were available. See `FDH11_AU_BROKER_ADAPTERS.md`.
- No AU broker PDF adapter — CSV only this pass (spec section 16/22's honest coverage classification).
- No AU CGT engine, no franking-credit engine — evidence captured, not computed (see India gap register's AU-analogue disclosures in `FDH11_REUSE_AND_GAP_AUDIT.md`'s companion docs and the completion report's residuals).
- Broker-cash-only events (INTEREST/CASH_DEPOSIT/CASH_WITHDRAWAL with no associated security) cannot be applied to `ii_transactions` today (`instrument_id NOT NULL`) — captured as evidence, never applied, disclosed as a genuine Investment Intelligence schema gap.
- Migration `0106` was PGlite-certified (20/20 real-Postgres checks) but could not be applied to the live DEV Supabase project from this sandbox — no DDL execution mechanism is available (no `exec_sql`-style RPC, no Management API token, no direct Postgres connection string), confirmed by direct probe and consistent with the same finding independently documented in `scripts/r11_professional_live_dev_tests.mjs` from an earlier phase. This blocks the live-DEV tests in spec sections 108-124 that require the new schema; live-DEV tests not requiring it (positions 125-126) are addressed on their own merits in `FDH11_LIVE_DEV_CERTIFICATION.md`.

# FDH-11 — Live DEV Certification (spec sections 108-129, 148-149)

## Structural blocker: no DDL execution mechanism available in this sandbox

Migration `0106` was PGlite-certified (20/20, real Postgres — see `FDH11_SECURITY_CERTIFICATION.md`) and passed both migration guards (`check-migration-versions.mjs`, `check-migration-versions-against-branch.mjs` against `origin/main`, `fix/g0-wave2-closure-hotfix`, and `feature/mandatory-country-confirmation-beta-cleanup`), satisfying spec section 148's precondition for live-DEV application. **It could not actually be applied to the live DEV Supabase project from this sandbox.** Confirmed by direct probe: `supabase projects list` fails with `LegacyPlatformAuthRequiredError` (no `SUPABASE_ACCESS_TOKEN`); no `SUPABASE_DB_URL`/direct Postgres connection string exists in `.env.local`; a live probe for `exec_sql`/`execute_sql`/`run_sql`/`admin_exec`/`pg_execute`-style RPCs on the project returned `PGRST202` (function not found) for all five. This is the identical structural limitation independently documented in an earlier phase's own live-DEV script (`scripts/r11_professional_live_dev_tests.mjs`: "no DDL execution mechanism is available in this sandbox (no exec_sql RPC, no Management API token, no Postgres connection string)"), not something new or worked around here.

**Consequence**: every live-DEV test in spec sections 108-124 that depends on the NEW `fdh_investment_statements`/`_positions`/`_activities` schema or the `asx_ticker` identifier scheme existing on the live DEV database **cannot be executed** until a human with DDL access (Supabase SQL editor or `SUPABASE_ACCESS_TOKEN`) applies migration `0106`. This is disclosed as a genuine, unresolved residual — not downgraded to "blocked" language, and not fabricated as PASS.

## What could NOT be verified: the new UI, live

A second structural limitation, independent of the DDL issue: the Browser-pane preview tool available in this sandbox session was bound to a different, pre-existing worktree's directory (`D:\fhip-fdh10-terminal`) rather than this task's own worktree (`D:\fhip-fdh11`) — confirmed by the dev server's own startup log explicitly naming that other path, and reproduced after stopping the server, killing the process holding the port, clearing `.next`, and retrying with an entirely new `launch.json` name and a different port (the tool continued returning the same cached session pointing at the other directory). This meant `get_page_text`/`javascript_tool` checks against `http://localhost:3000/investments` were reading the OTHER worktree's build output the whole time, not this codebase's edited `page.tsx` — explaining why the new "Import Australian Investment Statement"/"India Investments" UI never appeared despite the file being correct on disk (independently confirmed via direct file read and via `tsc`/`next build` both succeeding against this worktree).

**Consequence**: sections 141 (desktop/tablet/mobile/keyboard/accessibility) and the live click-through parts of 108 (full journey) and 125-127 (India navigation, mixed portfolio) could not be executed as live browser interactions this pass.

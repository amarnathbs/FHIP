# FDH-8 — Reuse & Gap Audit

Real code/schema inspection performed before any FDH-8 code was written: `lib/financial-data-hub/**` (FDH-1 through FDH-7, R7/R8), `app/api/financial-data-hub/**`, `components/**`, `app/(app)/**`, and migrations 0045-0077. Confirms the spec's own framing (section 4/10): FDH-8 is a presentation/analytics layer over an already-certified pipeline, not a new financial-truth engine.

## Classification key
- **REUSE AS-IS** — used unmodified, no new code needed.
- **EXTEND** — a thin, additive query/service layered on top of an existing table/function, using the same semantics.
- **NEW UX-ANALYTICS** — genuinely new capability FDH-8 owns (spec section 8/82: aggregation, grouping, filtering, presentation — never a new financial-truth definition).
- **OUT OF SCOPE** — deliberately not touched.

## Zero duplicate engines (spec section 5, 10)

Duplicate ingestion engines: **0**. Duplicate reconciliation engines: **0**. Duplicate merchant-matching engines: **0**. Duplicate categorisation engines: **0**. Duplicate transfer-detection engines: **0**. Duplicate refund-matching engines: **0**. Duplicate recurring-detection engines: **0**. Duplicate approval engines: **0**. FDH-8's only new computation is grouping/aggregation (by month, by merchant, by account, by category-percentage) around calls to FDH-7's own certified `computeApprovedFinancialSummary` — confirmed by grep: `financialActivityAnalytics.ts` is the only new file that imports `approvedSummary.ts`, and it is the only caller of that function anywhere in FDH-8's own code.

## Genuinely new schema/migration

**None.** FDH-8 requires no new table, column, index, or RLS policy — spec section 7 explicitly permits this ("If FDH-8 requires no migration, that is acceptable — do not manufacture one"). Confirmed: `git status --short supabase/migrations/` is empty for this branch; the highest migration remains `0077_retirement_member_target_age.sql` (pre-existing, from a concurrent Retirement Member UI workstream, not FDH-8).

## Disclosed limitation inherited from the FDH-7 oracle (not introduced by FDH-8)

`computeApprovedFinancialSummary`'s `category_totals` keys solely by `category_id` (defaulting a null category to `'uncategorised'`), without partitioning by `economic_transaction_type`. FDH-8's Spending/Income breakdown pages recover per-type separation by filtering categories through the category master's own `economic_type` field (categories are schema-typed to exactly one economic type — migration 0045), which is correct for every normally-classified category. The one residual: the `'uncategorised'` bucket itself sums ALL non-transfer economic types together, so an uncategorised expense and an uncategorised income (if both exist in the same period) would appear as one combined "Needs categorisation" figure rather than two. This is the same limitation FDH-7's own persisted summary already has — FDH-8 does not introduce it, and does not silently paper over it either; it is called out explicitly in `FDH8_SPENDING_EXPERIENCE.md` and `FDH8_INCOME_EXPERIENCE.md`.

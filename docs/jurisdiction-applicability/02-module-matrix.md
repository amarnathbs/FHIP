### Missing-country architecture (Decision PO-3, APPROVED 2026-08-27)

**RESOLVED — PRODUCT OWNER APPROVED.** The 98 DEV profiles with `country_of_residence = NULL` (§`05-live-dev-usage-audit.md` — figure re-used from the discovery baseline, not re-queried in this closure pass since no relevant schema/data-path changed on `origin/main`, see `00-README.md` baseline-refresh note) are **not** to be defaulted to AU or IN, permanently or otherwise, and IP/request-derived location is a suggestion only, never a confirmation. Full future-state flow (spec §9), not implemented in this task:

**Authentication/session behaviour:**
- Unresolved status is detected the same way it is today — `country_of_residence IS NULL` — no new column needed to detect it.
- The user may view and edit all GLOBAL functionality and their own profile/onboarding data while unresolved; nothing about being unresolved should lock a user out of the app entirely.
- Any jurisdiction-sensitive action (creating a `HOME_JURISDICTION` or `HOME_OR_CROSS_BORDER_COUNTRY` item) requires explicit confirmation first — the app must present a confirmation step, not silently allow or silently block into a guessed country.
- Redirect loops are avoided by making confirmation a **gate on the specific restricted action**, not a global app-wide interstitial — a GLOBAL-only user should never be forced through a country-confirmation screen to use GLOBAL functionality (this mirrors how SMSF's own gate today only fires on `retirement` creation, not on login).
- Profile-completion access remains available at all times regardless of confirmation state — a user must always be able to reach the screen that lets them resolve their own country.

**Catalogue/API behaviour:**
- GLOBAL items remain permitted for an unresolved user — this is already true today (`isItemAvailableForCountry()` treats NULL `country_applicability` as available regardless of resolved country).
- New creation of any `HOME_JURISDICTION`/`HOME_OR_CROSS_BORDER_COUNTRY`-classified item is rejected while unresolved — already true today for SMSF (fails closed on `null` country per `01-canonical-architecture.md` §3); must remain true for any future restricted item (Wave 2/3).
- Existing records (if any exist for a user who somehow later became unresolved — not observed in live DEV today, but must not be assumed impossible) remain fully accessible — the `EXISTING_RECORD_ONLY` state (`01-canonical-architecture.md` §7) applies, not deletion or hiding.
- Server/API enforcement must mirror UI restriction exactly — a direct forged API call for a restricted item's creation must fail closed for an unresolved country exactly as it does for a mismatched-but-resolved country (already true for SMSF's `assertItemCreationAllowedForUser()`; must be true for any future restricted item per `07-jurisdiction-standard.md` §4 checklist).

**Confirmation (future implementation, not built here):**
- Requires an explicit user selection — never inferred.
- Requires a confirmation timestamp and a confirmation source (`user_selected` / `suggested_then_confirmed` / etc.) — **no such column exists today**; `country_of_residence` alone cannot distinguish "the user actively chose this" from "this was set at onboarding by default". This is the concrete gap behind the "confirmed/unconfirmed country state" row in `01-canonical-architecture.md` §8.
- Requires an audit trail (who/when/from-what-source the country was confirmed or changed) — does not exist today for any profile field.
- A suggested country (from IP/request headers, if ever built) is stored and displayed only as a suggestion, never auto-applied.
- Travel/VPN: a suggested country from IP/request data must never override an already-confirmed `country_of_residence`, and must never itself count as confirmation — it is advisory only, exactly per Decision PO-3.
- Conflicting stored currency (`preferred_currency` not matching the confirmed country) is not itself a jurisdiction signal and must not be used to "auto-resolve" a missing country (this generalises the `resilienceStress.ts` defect's lesson to the missing-country case specifically).
- Conflicting household country (`households.primary_country`) must not be used to auto-resolve an individual's missing `country_of_residence` either — per §1 above, `households.primary_country` is a passive copy of whichever member most recently onboarded, not an independent signal.
- Existing cross-border records (a hypothetical unresolved user who already has AU- and IN-tagged records) must all remain visible and counted regardless of confirmation state — confirmation governs future creation only, never existing visibility.

**Historical and economic integrity:** no historical record is rewritten when a user later confirms their country; no currency is auto-converted; no value is removed from any total because of confirmation state; a historical report already generated is not regenerated using a newly-confirmed current country (must retain whatever jurisdiction context — including "unresolved" — was in effect when originally generated, per Decision PO-6/Reports); a pre-confirmation display default (e.g. any future onboarding-form pre-selected value) is never treated as a financial fact.

**Not built in this task, and not a closure blocker per spec §16:** the 98 users remain unconfirmed; no confirmation UI, timestamp column, or audit table exists yet. This is explicitly Wave 4 scope (`06-implementation-waves.md`).

#### India retirement architecture (Decision PO-1 — full detail, spec §G)

**Approved future scope:** three distinct new `retirement` catalogue items — EPF (Employees' Provident Fund), PPF (Public Provident Fund), NPS (National Pension System) — available when India is the user's confirmed primary financial country, **or** an explicitly enabled cross-border country associated with the specific holding (i.e. the same `HOME_OR_CROSS_BORDER_COUNTRY` class as the reclassified AU items, not a stricter `HOME_JURISDICTION`-only rule) — this explicitly covers eligible NRIs, per PO-1's own instruction.

**Required architecture treatment (binding constraints on the future Wave 3 implementation, not implemented here):**
- Reuse the existing `retirement_accounts` domain/table — do **not** build a product-specific schema unless a later calculation requirement (e.g. EPF/NPS-specific withdrawal-rule modelling) proves it necessary. This mirrors exactly how every non-SMSF retirement item works today (Annuity, Overseas Pension, etc. — no bespoke table, no bespoke component).
- Preserve original currency, record country, ownership, and valuation on each new item exactly as every existing `retirement_accounts` row does today — no new normalisation rule specific to these three items.
- Make available to eligible NRIs — i.e. classify as `HOME_OR_CROSS_BORDER_COUNTRY(IN)`, not `HOME_JURISDICTION(IN)` alone, so a confirmed-AU-resident NRI with an explicit India cross-border relationship can still create one.
- **Do not force existing India-resident holdings into a generic "Retirement Savings" item** — the new items must be genuinely selectable, not just documented as a theoretical option.
- **Do not automatically convert an existing generic retirement record into EPF/PPF/NPS** — any existing `retirement_savings`/`other_retirement_assets` row an IN-resident user already has stays exactly as it is; migration must never reclassify live data by inference.
- **Do not create product-specific tax or forecasting logic merely by adding these catalogue rows** — catalogue availability (an item existing and being selectable) is explicitly separate from calculation support (whether Forecasting's assumption cascade, Financial DNA, or any tax engine has EPF/PPF/NPS-specific logic). Per the discovery baseline, `forecast_global_assumptions` (migration `0014`) already models generic AU/IN retirement assumptions (retirement age, withdrawal rate) at the *country* level, not the product level — adding these three catalogue items does not, by itself, give Forecasting any new product-specific behaviour, and none should be assumed to exist until separately built and certified (same principle as Decision PO-6's Investment Intelligence India Tax & Cost rule: "do not invent unsupported equivalents").
- No calculator, tax engine, forecasting certification, institution-import support, or compliance/reporting logic is implied or approved by this decision — Decision PO-1 approves catalogue-level *existence*, not calculation-level *support*. Whichever future wave adds these items must state explicitly which of those capabilities (if any) it is also adding, and which remain absent.

**Classification status:** approved future remediation (Wave 3), **not** an unresolved question — the discovery baseline's original open question ("PO decision required") is now resolved via Decision PO-1 (`00-README.md` §C). The three items are still, correctly, absent from the live catalogue today (§table above) — nothing was added by this closure.

## Forecasting (spec s.25 — CRITICAL)

The best-architected jurisdiction-dependent module found. `forecast_global_assumptions` (migration `0014`) stores AU, IN, and `country_code IS NULL` (global-fallback) rows for every assumption (inflation, investment returns, retirement age, life expectancy, withdrawal rate, salary/property growth, etc. — full list in the migration). `lib/engines/forecast/assumptions.ts:resolveAssumptions()` implements a clean 4-tier cascade (scenario override → profile override → country-specific default → global-null default) that **never silently substitutes AU for an unresolved/IN country** — when `countryCode` is `null`, the country tier is skipped entirely, falling straight to the null-keyed global defaults, not to AU's row. `forecastData.ts:getOrCreateForecastProfile()` sources `country_code` from `country_of_residence` with no fallback to a specific country (only `?? null`). **No violation of spec s.25's "no silent AU defaults" found in this module.** One soft note: `base_currency` (a separate concept) does default to `'AUD'` when `preferred_currency` is unset (`forecastData.ts:50`) — a currency default, not a jurisdiction one, but worth a PO sanity check since a new IN user with an incomplete profile could theoretically see AUD-denominated forecast figures until `preferred_currency` is set.

- A server-side RPC (same migration, lines ~1817-1901) also takes a `p_jurisdiction` parameter and applies the identical selected+global logic at the database layer, not just in the application query builder.

**This means Resources is not a "zero jurisdiction differentiation" module (as this report originally, incorrectly, classified it) — it is the SECOND fully-built, already-working jurisdiction system in the codebase, independent of `lib/services/jurisdiction.ts`/`master_financial_items.country_applicability`.** It predates the SMSF-era foundation (migration `0049` vs SMSF's `0084`) and was built with its own, different vocabulary:

| | `master_financial_items` foundation (SMSF-era, `lib/services/jurisdiction.ts`) | Resources (`resource_posts`/`resource_faqs`, migration `0049`) |
|---|---|---|
| Column | `country_applicability char(2)[]` | `jurisdiction text` (single value, not an array) |
| Values | ISO alpha-2 codes (`AU`, `IN`), NULL = global | English words (`global`, `australia`, `india`, `australia_india_cross_border`) |
| Cross-border representation | Not modelled as a distinct value — inferred per-record from a holding's own `country_code` differing from the owner's home country | **Modelled as an explicit fourth value**, `australia_india_cross_border` — content can be tagged as inherently cross-border content, not just "available to both" |
| Filter semantics | "Available for creation if country matches or is NULL" | "Selected jurisdiction OR global" (explicit, documented product decision) |

**This is directly relevant to the newly-approved `HOME_OR_CROSS_BORDER_COUNTRY` applicability class (Decision 6/the new architecture class table)** — Resources' `australia_india_cross_border` value is a working precedent for exactly that concept, already shipped and functioning, just under a different name and in a different table family. **Do not design a second Resources jurisdiction system — extend/rename toward the canonical convention only if and when a genuine need to unify the two vocabularies is identified; the existing Resources system does not need to be rebuilt to be usable.**

**Revised Wave 6 scope for Resources**: no new schema is needed (contrary to this report's original recommendation) — the jurisdiction infrastructure already exists and is live. Wave 6 work here is about (a) deciding whether to align Resources' bespoke `jurisdiction` vocabulary with the canonical ISO-code convention used elsewhere (a naming/consistency decision, not a build-from-scratch one), and (b) auditing actual content tagging accuracy (are AU-superannuation articles correctly tagged `australia` rather than left as the `global` default) — a content audit, not an architecture task.

**Decision PO-6 (approved 2026-08-27) directly confirms this conclusion as Product Owner policy, not just an architectural recommendation:** "reuse the existing Resources jurisdiction architecture if confirmed present — do not create a second Resources jurisdiction model." This closure's own fresh investigation (`00-README.md` §D) independently re-confirms the architecture is present, live, and working — so PO-6's Resources instruction is satisfied by inspection, not by any new build.

## Dashboard (spec s.30)

`lib/engines/dashboard.ts` already implements the correct target architecture: canonical totals (Net Worth, per-category totals) are computed unconditionally from the full record set, while `assetsByCountry`, `liabilitiesByCountry`, `retirementByCountry`, `investmentByCountry`, and `countriesInUse` are separately computed per-record breakdowns used only for cross-border *presentation* (confirmed via direct read, lines 343-629). **No filtering of totals by home jurisdiction or `country_applicability` was found anywhere in this file.** This is the reference pattern the spec is asking every other module to converge toward.

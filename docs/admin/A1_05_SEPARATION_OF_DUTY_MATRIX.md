# A1.1 — Separation-of-Duty Matrix

For each named pair, the control, whether it exists today, and where it is enforced. Per Standard §4, an enforcement layer count of "UI only" is never sufficient on its own.

## Enforcement-layer legend, applied consistently

For every row above, "enforced" means at minimum the **database layer** (RLS policy or `SECURITY DEFINER` RPC-internal check) actually blocks the disallowed action — a UI-only or API-only separation is never recorded as "Yes" in this matrix, per Standard §4's own rule that navigation and even API-layer checks alone do not constitute a security boundary.

## Findings for the Product Owner

1. **Rows 3 and 4 have no real separation today because there is no second actor to separate** — both Recommendations and Benchmarks authoring/approval are entirely Super-Admin-only. This is not a defect (nothing currently requires two people), but it means if either domain's authoring is ever delegated to a non-Super-Admin role, a segregation rule must be designed at that time, following the FDH-13 REG-01 pattern (row 8) rather than inventing a new one. Flagged in `A1_19`.
2. **Row 5's `admin_users` (Super Admin) grant/revocation path has no Admin-UI task at all** — it is currently a database-console action outside the Admin surface entirely. A1 records this as ADM-44 (future) rather than silently treating "no UI" as "no separation concern."

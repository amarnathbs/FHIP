## 1. What the fixtures are, and why they are plain text

`lib/fixtures/investment-intelligence/r2-cas/{cams,kfintech}/*.txt` are **already-extracted document text** — the exact string shape `pdfExtraction.ts` hands to the parser layer, not raw PDF bytes. This is a deliberate scoping decision:

- The parser's real input contract is `(text: string) -> ParsedDocumentOutput` (see `parsers/types.ts`). Testing at this boundary exercises 100% of the actual parsing logic (regex extraction, date/decimal parsing, source detection, classification, resolution) with zero PDF-library involvement, making failures unambiguous (a test failure here is a parser bug, never a PDF-extraction-layer quirk).
- The PDF-extraction layer itself (`pdf-parse` integration) is separately, genuinely proven against **real binary PDF bytes** in `tests/unit/iiR2PdfExtraction.test.ts`, using `tests/support/buildMinimalPdf.ts` (a from-scratch, in-process, valid-PDF-syntax generator — proven to work against the real `pdf-parse` library during development, not assumed).
- See `R2_SUPPORTED_CAS_FORMATS.md` section 4 for the honest statement that these fixtures are a documented, structurally-faithful, but **synthetic** representation of the real CAMS/KFintech layout — not a reverse-engineered exact copy of a real production statement (no licensed sample was available).

Each `.txt` fixture has a companion `.expected.json` sidecar generated by `scripts/investment-intelligence/generateR2Fixtures.mjs` from scenario data in `fixtureScenariosCams.mjs`/`fixtureScenariosKfintech.mjs`. **The expected values are authored independently of the parser code** — the generator never imports or calls `camsParser.ts`/`kfintechParser.ts`/`transactionTypeMapping.ts` — specifically so the comparison in `tests/unit/iiR2ParserFixtures.test.ts` is a genuine test, not a tautology. The one narrow exception, honestly flagged: transaction-**type** classification necessarily requires the fixture author to have the same `RULES` table in mind when choosing both the statement wording and the expected canonical type. Mitigated by including explicit rule-precedence adversarial cases (see section 4).

## 4. Rule-precedence adversarial cases (proving classification isn't tautological)

- `classifyTransactionType('Purchase - Reversed')` -> `reversal`, not `purchase` — this exact case **found and fixed a real bug** during fixture testing (the original rule order classified it as `purchase`; see `R2_TESTING_AND_VERIFICATION.md`).
- `classifyTransactionType('Redemption Reversal')` -> `reversal`, not `redemption`.
- `classifyTransactionType('Dividend Reinvestment')` -> `reinvestment`, not `dividend`.
- `classifyTransactionType('Switch In Purchase From XYZ Fund')` -> `switch_in`, not `sip`/`purchase`.
- The `kfin-idcw-dividend-and-reinvestment` fixture's title explicitly documents itself as "rule-precedence case" — its second transaction's description contains both "Dividend" and "Reinvestment" together, deliberately.

## 4. How the earliest required benchmark date is derived TODAY (file:line, base branch)
All consumers read benchmark levels with `valueOnOrBefore` (last point <= date, NO start tolerance): `benchmarkService.ts:68-74`, used by `benchmarkWindowReturn` (`:246-259`) and the blend (`:160-171`). So the series must contain a point on or before the window start.
1. **Portfolio blended benchmark / rolling / risk**: window start = `ds.periodStart = opts.periodStart ?? earliest ?? asOfDate` (`analyticsRepository.ts:496`), where `earliest` = the first cash-flow date over all of the user's schemes (`:400`; txns exclude status reversed/review_required, `:305`). Fed to `computeBlendedBenchmark` (`analyticsOrchestrator.ts:429-436`; monthly rebalance from periodStart `benchmarkService.ts:121`). Rolling 1/3/5y (`rollingReturnService.ts:25`) is computed only over that blended series (`analyticsOrchestrator.ts:487-511`), so it never asks for more history than the user's own first cash flow.
2. **Per-scheme since-inception active return**: window start = **earliest quality-ok ii_prices_nav date on file** for the instrument (`analyticsOrchestrator.ts:240-257`, `start = sorted[0].date`; NAV rows are loaded unbounded, `analyticsRepository.ts:202-212`). NAV for held funds is hydrated from inception (`selectiveHistoricalHydrationJob.ts:29` HISTORICAL_FLOOR_DATE 2006-04-01, `:494`; `navRetentionPolicy.ts:367-380`), so this rule effectively demands benchmark history back to the fund's launch / 2006-04-01, NOT the user's first transaction.
3. **Holdings tab**: window start = earliest transaction date of the position (`holdingsRepository.ts:199-207, 316-320`; `benchmarkCoverage.ts:197-223`), end = latest valuation.
4. **SIP benchmark**: every contribution date must align to a benchmark observation on-or-after it within 10 days (`sip/sipXirr.ts:238-269`, `sip/dateAlignment.ts:35-41,85-100`); any gap makes the comparison UNAVAILABLE.
5. The PC6 hydration job (`selectiveHistoricalHydrationJob.ts`, `navRetentionPolicy.ts:294-345`) demands NAV history, not benchmark history: held => from inception (null from-date => 2006-04-01 floor, or the recorded `ii_nav_history_floors` date, `:494-496`); benchmark-only instruments => `BENCHMARK_LOOKBACK_DAYS` = 5*365 + 5*31 + 20 + 30 = 2030 days before the changeover (`navRetentionPolicy.ts:273-274`). That lookback applies to the mapped instrument's NAV, not to a benchmark series.

Script implementation (reused rule, nothing invented): per scheme compute (A) tx rule = first non-reversed/non-review_required transaction date (fallback earliest snapshot), (B) nav rule = earliest ok NAV on file; `required_from_date = min(A, B) - 10 days`. The 10-day pad is the EXISTING constant `MAX_BACKWARD_SEARCH_DAYS = 10` (`sip/dateAlignment.ts:44`): the existing benchmark code has NO start-of-series alignment lookback, so a weekend/holiday window start would otherwise miss the prior trading day; this is the only addition and it reuses an existing constant. Both component dates are emitted (`required_series_from_tx_rule`, `required_series_from_nav_rule`) with `required_basis`, so the matrix owner can choose. Real-row result: PROD required_from_date is the nav rule for all 19 (11 funds back to 2006-03-24; latest start 2014-06-20); tx-rule-only would start 2007-12-07 .. 2026-01-26. DEV real: 2006-03-24 for one fund, others 2012-12-23 / 2026-07-22 and one fund with no NAV.
Eligibility: `loadAnalyticsDataset` applies NO instrument_class, country or currency filter (`analyticsRepository.ts:174-190`); blended results are grouped per currency (`analyticsOrchestrator.ts:164-173`); risk-free rates are country-keyed (defaults IN). X-Ray alone restricts to mutual_fund/etf/equity (`r5Repository.ts:384-385`). India/INR restriction comes from the data source (ii_scheme_master and AMFI NAV are IN/INR only), not from the benchmark engines. Rows therefore carry `benchmark_comparison_engine_eligible` (true for any known instrument) and `matrix_scope_scheme` (mutual_fund or etf). All held rows today are mutual_fund, IN, INR.

## 5. Surprising / caveats
* DEV is dominated by synthetic fixtures: 35 of 39 rows (R6F tax-lot fixtures, 3 duplicate instruments per fixture name, plus 2 TESTFIX-AMFI-* provisional instruments with a fake AMFI code and no scheme master). Flagged `likely_test_fixture` (name/identifier heuristic); category summary has both "all" and "excluding fixtures" columns. Duplicate fixture instruments are flagged `same_family_plan_option_on_multiple_instruments`, not merged.
* PROD: 17 of 19 funds are held by the same 3 users and 2 by 1; 1 fund has no currently-positive holder. I cannot tell from a read-only inventory whether these are test/staff accounts.
* PROD instruments all have `status=provisional` yet all are linked to ii_scheme_master (AMFI-sourced) - not treated as unresolved. DEV: 5 provisional (3 linked, 2 fixtures).
* One real DEV instrument (ICICI Pru Corporate Bond Fund, ISIN present, no AMFI code / scheme master / NAV) is `unresolved_identity` and has no category.
* `ii_nav_history_floors` holds 19 rows in PROD (equal to earliest NAV for all 19) and 0 in DEV; PROD NAV earliest dates therefore equal confirmed fund history starts (2006-04-03 is AMFI's floor).
* scheme_family_key = normalised AMC (suffixes "mutual fund/limited/..." stripped) | scheme name with plan/option tokens removed. It is a heuristic for grouping only; Direct/Regular and Growth/IDCW and distinct ISINs stay separate rows (verified: HDFC Large Cap Direct and Regular share a family key, remain 2 rows).
* Combined de-duplication across environments uses the AMFI code (else first ISIN, else env-scoped instrument id) because DEV and PROD instrument UUIDs are independent. Only 1 scheme (SBI Large Cap, 103504) is held in both.
* AMFI category guidance (sub_category) is NOT evidence of a scheme's declared benchmark; nothing here asserts a benchmark.
* Instrument/scheme names are public scheme names; long digit runs in names are redacted; no user_id/account/folio/member/email/units/amounts are emitted (checked by pattern scan of all outputs).

# R11 Manual Reconciliation

Spec section 94 asks for at least 20 deep manual reconciliations (suggested: 8 multi-source portfolios, 4 conflict scenarios, 4 consent/scope scenarios, 4 professional access/security scenarios). **Honest result: 12 genuine, real manual reconciliations were performed during this build — this is short of the requested 20.** Every one below is a real trace I performed by hand against real code/output during this session (not written after the fact to look complete); several found and fixed real bugs.

## Multi-source / conflict scenarios (6)

1. **CS-01 exact-match trace**: hand-traced `classifyPairwise` for two rows identical on every field except `sourceDocumentId`/`sourceKey` → `coreMatch=true`, `amountMatched=true`, `unitsMatched=true`, `bothRefsPresent && refsAgree=true` → falls through to `return 'exact'`. Matches test result.
2. **CS-04 both-references-null trace**: hand-traced why two rows with `sourceReference: null` on both sides do NOT reach `'exact'` — `bothRefsPresent=false`, so the final branch returns `'high_confidence'` instead. Confirms the design intent ("reference cannot corroborate what neither side provides") is actually implemented, not just commented.
3. **CS-21 conflict trace**: hand-traced a same-core-identity, both-references-present-but-different row → `refsDisagree=true`, `amountMatched && unitsMatched && refsDisagree` fires first → `'conflict'`. Confirms conflict is checked BEFORE the exact/high-confidence path, not after (ordering matters — a naive implementation could have let amount/units agreement short-circuit past a reference disagreement).
4. **CS-24/CS-25 real bug found and fixed**: originally wrote these two test cases with `grossAmount: '9999.00'` vs an existing `'10000.00'` (diff = exactly `1.00`). Hand-tracing `decimalsWithinTolerance`'s `<=` comparison against `currencyToleranceScaled = 1.00` revealed the diff is INSIDE tolerance (inclusive), so the case actually classifies as `'exact'`, not the `'conflict'` the test asserted — a test-data bug, not a production bug. Root-caused by manually computing the diff, fixed by changing the test fixture to `'9900.00'` (diff = `100.00`, genuinely beyond tolerance), reran, confirmed `'conflict'` as intended.
5. **CS-35/CS-36 "none" gate trace**: hand-traced that a different `accountId`/`instrumentId` short-circuits at the `coreMatch` check BEFORE amount/units are ever compared — confirmed by adding a deliberately-conflicting amount to a different-account case and verifying the state is still `'none'`, not `'conflict'` (the core-identity gate is a true prerequisite, not merely evaluated-and-ignored).
6. **Net-worth non-duplication inheritance trace**: read `investmentPublicationService.ts` line-by-line (not grepped, actually read) to find the "active publication" lookup — `select ... from ii_fhip_publications where account_id=... and instrument_id=... and status='published'` (line 717) — confirming it is keyed on the ECONOMIC POSITION, not on the specific `ii_holding_snapshots.id` being published. Traced through `decideRefreshSupersession`'s freshness comparison to confirm a second source's later-dated snapshot for the SAME position would be treated as a refresh/supersession, not a second publication — i.e., R3's existing net-worth-dedup mechanism already covers cross-source holdings without any R11 code change. This is the single most consequential manual reconciliation in the release: it is what justified NOT building a parallel net-worth-dedup mechanism.

## Consent/scope scenarios (2)

7. **Migration 0083 ordering bug found and fixed**: `professional_profiles`'s "client reads related professional_profiles" policy referenced `professional_relationships` in its `USING` clause, but `professional_relationships` was defined LATER in the same file. PGlite's replay threw `relation "professional_relationships" does not exist` — traced via a minimal isolated debug script (`node` running just the shim + migrations 0001-0082, then 0083 alone with full error object dumped) to the exact statement, confirmed Postgres resolves `CREATE POLICY` against real catalog objects at creation time (unlike a function body, which is deferred). Fixed by moving the dependent policy to after the table it references.
8. **Section 8 unique-constraint bug found and fixed**: `scripts/r11_rls_certification.mjs`'s Section 8 originally tried to INSERT a second `(A, P2)` relationship while Section 5's pending `(A, P2)` relationship still existed, violating `uidx_professional_relationships_live_pair`. Root-caused by reading the actual Postgres error text, then fixed by reusing/activating the Section-5 pending relationship instead of creating a duplicate — this is itself a small piece of live evidence that the partial unique index behaves as designed (it really does block a second live relationship for the same pair).

## Professional access/security scenarios (4)

9. **PGlite nested-role bug found and fixed (a real false-positive security finding)**: the first run of Section 7 ("client cannot UPDATE an audit row") reported `rowsAffected=1` — an apparent RLS leak. Root-caused by hand-tracing the `asService()`/`asUser()` helper functions: `asService()` calls `RESET ROLE`, and it was nested INSIDE an `asUser(A, ...)` callback, silently reverting the session to the table-owning superuser (which bypasses RLS by default) for the remainder of that callback — the UPDATE that followed ran as superuser, not as client A. Fixed by moving the `asService()` read outside the `asUser()` block; rerun genuinely returned `rowsAffected=0`. Documented in the script itself as a caution against nesting these helpers, since this is exactly the kind of harness bug that could otherwise produce a false PASS on a real vulnerability (in this direction it produced a false FAIL, which is the safer failure mode, but the root cause was worth fixing regardless).
10. **Trigger-necessity trace**: manually reasoned through why an RLS-only design would be insufficient for "even the trusted service cannot un-revoke" — RLS is bypassed by `service_role`/superuser by design (shim.sql: `service_role ... bypassrls`), so a policy alone cannot constrain it; only a `BEFORE UPDATE` trigger fires regardless of role. Verified the reasoning by testing the un-revoke attempt AS the service role specifically (not just as `authenticated`) in Section 6, confirming the trigger — not a policy — is what blocks it.
11. **NC5 sabotage prediction**: before running the NC5 negative control, manually predicted which/how-many tests would fail if the per-scope check were removed (every `PA-0[6-9]`/`PA-1[0]`/`PA-3[7-9]` scope-gating test, plus the full 8×N `PA-scope-*` matrix) — ran the sabotage, got exactly 14 failures, matching the prediction closely enough to confirm the mental model of the function was correct before relying on it further.
12. **Deactivation-vs-revocation independence trace**: hand-traced that `professionalIsActive` and `relationship.status` are two independent gates (PA-19-21) — deliberately constructed a scenario with every OTHER condition satisfied (active relationship, live scope, no expiry) and only `professionalIsActive=false`, confirming denial, then flipped it back to `true` and confirmed access resumed — proving deactivation is a real, independent, reversible-for-the-professional-account (but relationship-status-independent) gate, not accidentally implemented as an alias for relationship revocation.

## R11-FINAL closure round additions (MR13-MR20) — 2026-08-25

Spec section 46 requires the remaining 8 deep cases to bring this to 20/20. All eight below are genuine hand-traces performed against real code read in full during this closure round (`crossSourceIdentity.ts`, `permissions.ts`, `access.ts`, `documentProcessing.ts`, `manualImporter.ts`) and, where noted, cross-checked against real live-DEV results produced in the same round (`scripts/_tmp_r11_live_dev.ts`, `r11-live-dev-results.local.json`) — not restated automated-test output.

13. **MR13 Full overlap**: manually derived the expected classification for the CAMS+KFintech same-folio/ISIN/date/amount/units/reference fixture (`AXTXN01`, ₹15,000.00, 250.000 units, 10-Mar-2025) used in live case LIVE-R11-004/005. Hand-traced `classifyPairwise`: `coreMatch` (account/instrument/date/type all equal) = true; `amountMatched` (diff 0 ≤ ₹1.00 tolerance) = true; `unitsMatched` (diff 0) = true; `bothRefsPresent && refsAgree` (`AXTXN01` = `AXTXN01`) = true → falls through to `return 'exact'`. Expected: 1 canonical transaction, 1 auto-resolved `cross_source_exact_duplicate` case, 2 provenance links (1 originating + 1 corroborating). Compared against the actual live-DEV result: transaction/holding count matched exactly (1/1, confirming the core no-duplication invariant); the corroborating link count came back as 1, not 2 — root-caused (not merely observed) to a genuine DEV-environment gap this same round discovered: migration 0082's tail (the `match_basis` column) was never applied to DEV, so the corroborating link's insert fails silently on that missing column, the same silent-failure pattern `documentProcessing.ts` already had at the same-fingerprint link a few lines above it. Disclosed in the final report as a migration-completeness gap (migration `0086`, blocked on DDL access), not a code defect — the economic invariant this case actually exists to prove was unaffected.
14. **MR14 Partial overlap**: manually derived the expected unique/shared-asset set for LIVE-R11-007's fixture (Source A: Fund1+Fund2, Source B: Fund2+Fund3, same folio, three distinct ISINs). Hand-traced instrument resolution: each ISIN resolves to its own `ii_instruments` row (no alias collision, no shared normalised-scheme-name across the three funds), and Fund2's transaction — present in both A and B with identical date/amount/units/reference (`F2TXN01`) — classifies `'exact'` by the same reasoning as MR13. Expected: 3 distinct instruments, 3 canonical transactions (Fund1 once, Fund2 once, Fund3 once). Compared against actual live result: exact match (txns=3, distinctInstruments=3).
15. **MR15 Source conflict**: manually derived the expected decision for LIVE-R11-008's fixture — same folio/ISIN/date/type/units/reference (`CONFTXN1`) but a genuinely different amount (₹9,000.00 vs ₹9,500.00, diff ₹500.00 ≫ ₹1.00 tolerance). Hand-traced `classifyPairwise`: `coreMatch`=true, `amountMatched`=false → enters the `!amountMatched || !unitsMatched` branch; `bothRefsPresent && refsAgree` (both `CONFTXN1`) is true → returns `'conflict'` (not `'none'`, since the branch explicitly checks for a genuine ref-agreeing-but-magnitude-disagreeing case before falling through). Expected: both pieces of evidence preserved (2 transaction rows, not 1), the second marked `status='review_required'`, a `cross_source_conflict` case opened at `status='open'` (never auto-resolved, per `classifyPairwise`'s design — a conflict is never silently resolved by precedence). This is the case most directly protecting spec section 74's "source conflict silently ignored" critical-fail condition — traced by hand against the actual branch ordering in the source file, confirming conflict detection is checked BEFORE the exact/high-confidence path can short-circuit past it.
16. **MR16 Different as-of dates**: manually derived the expected outcome for LIVE-R11-009's fixture — Source A covers only `ASOFTXN1` (5-Jan-2025, closing 31-Mar-2025, 100 units); Source B covers `ASOFTXN1` + a genuinely new `ASOFTXN2` (10-May-2025, closing 30-Jun-2025, 140 units). Hand-traced: `ASOFTXN1` is present identically in both sources → `'exact'` match, linked not duplicated (same reasoning as MR13). `ASOFTXN2` has a different `transactionDate` than any existing row for this position, so `coreMatch` is false against every existing candidate → classifies `'none'` → inserted as a genuinely new transaction, never compared for conflict at all (a different date is not a contradiction to reconcile, it is simply a different transaction). Expected: 2 canonical transactions total, 2 holding snapshots (one per distinct `as_of_date`, R2's existing snapshot-per-date model, untouched by R11), 0 blocking/high-severity cases. Compared against actual live result: exact match (snaps=2, txns=2, reviewRequired=0, blockingCases=0) — confirms the engine correctly distinguishes "same transaction, corroborated" from "new transaction, different date" without ever conflating temporal progression with contradiction.
17. **MR17 Tax-basis incomplete**: manually derived the expected outcome for LIVE-R11-010's fixture — a CAMS statement with a closing-balance line (200 units) and ZERO transaction rows for that scheme. Hand-traced `determineHistoryCompleteness`: `hasAnyTransactionHistory=false`, `hasClosingHoldingSnapshot=true` → falls through the first three branches to `if (input.hasClosingHoldingSnapshot) return 'holdings_only'`. Separately confirmed by reading `documentProcessing.ts` end-to-end that no code path in the R2/R11 ingestion pipeline ever writes to `ii_tax_lots` at all (that table is populated exclusively by R6's separate tax-lot engine, which itself only derives lots from already-evidenced `ii_transactions` rows — it has no mechanism to synthesize a lot for a holdings-only position). Expected: `history_completeness='holdings_only'`, 0 tax-lot rows. Compared against actual live result: exact match (`history_completeness: "holdings_only"`, `taxLots: 0`) — confirms "tax basis incomplete" is signalled correctly and nothing is fabricated. (One assumption corrected during this trace: `certification.status` reaches `'certified_with_warnings'` for a holdings-only position — a deliberate R2 design choice treating incomplete-but-present evidence as a disclosed warning rather than a hard block — which in turn upgrades `ii_holding_snapshots.quality_status` to `'certified'`; this does not contradict `history_completeness` still correctly reading `'holdings_only'` for any downstream consumer, e.g. R6.)
18. **MR18 Professional permission matrix**: given a frozen permission set (relationship `status='active'`, not expired, professional `is_active=true`, `VIEW_INVESTMENTS`+`VIEW_REPORTS` granted and live, `VIEW_TAX_SUMMARY` never granted), manually hand-traced `checkProfessionalAccess` (read in full this round) branch-by-branch for four requests: `VIEW_INVESTMENTS` → all relationship gates pass → `grantsForScope` finds a live grant → **ALLOW**. `VIEW_REPORTS` → identical reasoning → **ALLOW**. `VIEW_TAX_SUMMARY` → relationship gates pass but `grantsForScope.length===0` → **DENY** (`SCOPE_NOT_GRANTED`). Raw-document access → `isRawDocumentScopeSupported()` returns `false` unconditionally and no such string exists in `PROFESSIONAL_SCOPES` at all, so the request is not even expressible as a scope check → **DENY**, structurally. Cross-checked against `r11ProfessionalPermissions.test.ts`'s existing PA-06..PA-10 scope-gating matrix, which independently exercises this same function on equivalent inputs and reaches the identical ALLOW/DENY pattern.
19. **MR19 Revocation, same-session semantics**: hand-traced the BEFORE/AFTER-revocation lifecycle against `access.ts` (read in full this round). BEFORE: `checkAccessLive` → `fetchAccessContext` reads the relationship row fresh → `status='active'` → passes to the scope check → **ALLOW** (given a live grant). Revocation itself (`revokeRelationship`) is a service-role write, since `professional_relationships` carries no authenticated-role UPDATE policy (independently confirmed live in `r11_rls_certification.mjs` Section 5/6 this round). AFTER: the SAME session/token calls the SAME endpoint again; `fetchAccessContext` re-reads the relationship row FRESH (confirmed zero caching exists anywhere in `access.ts` — no in-memory map, no JWT-claim shortcut) → sees `status='revoked'` → `checkProfessionalAccess`'s revoked-check fires before the scope check is even reached → **DENY** (`NOT_ACTIVE`). This traces the exact mechanism (statelessness, not a revocation-list lookup) that makes "same pre-revocation session/token, immediately denied" true, and is cross-checked against the RLS cert's independent DB-trigger backstop (Section 6: even the service role cannot un-revoke).
20. **MR20 Cross-client security, real valid IDs**: given real User A and real User B (genuine Supabase Auth accounts, never malformed/invalid UUIDs) and Professional P1 authorised only for A, hand-traced two distinct attack shapes against `fetchAccessContext`/`checkProfessionalAccess`. Attack 1 (P1 requests B's data, no relationship exists for (B,P1) at all): the `.eq('client_user_id', B).eq('professional_user_id', P1)` query returns no row → `relationship=null` → the very first check (`if (!relationship) return {allow:false, code:'NO_RELATIONSHIP'}`) fires → **DENY**. Attack 2 (P1 reuses the real (A,P1) relationship id while asserting `clientUserId=B`): `relationship.clientUserId !== requestedClientUserId` → the second check (`WRONG_CLIENT`) fires → **DENY**. Both are independently blocked at the application layer by hand-trace, and cross-checked against `r11_rls_certification.mjs` Section 3's "MANDATORY cross-client attack: P2 cannot read P1's client relationship" (DB/RLS-layer proof of the same invariant) — application-layer and DB-layer backstops agree.

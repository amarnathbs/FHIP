## 1. What was implemented

- Three additive migrations (`0039`-`0041`): parser-run lineage (`ii_document_parse_runs`), multi-source transaction lineage (`ii_transaction_source_links`), deterministic transaction-fingerprint dedup (`ii_transactions.transaction_fingerprint` + unique index), the controlled scheme-alias mapping table (`ii_scheme_alias_map`), mutual-fund variant columns on `ii_instruments` (`plan_type`/`option_type`/`amc_name`), the Portfolio Truth entity (`ii_portfolio_truth_status`), the reconciliation-case structural extension (named `discrepancy_type` enum + severity/evidence/resolution columns), the versioned reconciliation-tolerance reference table (`ii_reconciliation_config`), and additive check-constraint widenings on `ii_audit_events.event_type`, `ii_source_documents.status`, and `ii_transactions.transaction_type`.
- A real, dependency-free exact-decimal module (`decimal.ts`) — no such module existed in this codebase before (checked: `lib/engines/money.ts` uses plain `number`, acceptable there but not for authoritative parsing of statement text).
- A CAS date-normalisation module (`dateNormalisation.ts`) supporting exactly the DD-MMM-YYYY/DD/MM/YYYY formats the golden fixtures use, DD-first always, with real calendar validation.
- Safe, local, server-side PDF text extraction (`pdfExtraction.ts`) via a new dependency, `pdf-parse` (pure TypeScript, `pdf.js`-based, no network call when given raw bytes) — the only new npm dependency this release adds.
- The parser architecture: `parsers/types.ts` (the `InvestmentDocumentParser` interface), `parsers/camsParser.ts` and `parsers/kfintechParser.ts` (two genuinely independent provider adapters, no shared provider-specific logic), `parsers/registry.ts` (detection + orchestration + the documented parser-confidence formula), `parsers/textUtils.ts` (shared provider-neutral helpers including the PAN-redaction fix).
- Canonical transaction-type classification (`transactionTypeMapping.ts`) — a 20-value ordered rule table.
- Deterministic, priority-ordered scheme/instrument resolution (`schemeResolution.ts`) — pure logic, DB-backed wiring in the orchestrator.
- Deterministic transaction fingerprinting (`fingerprint.ts`).
- The reconciliation engine (`reconciliation.ts`) and the certification-rules engine (`certification.ts`) — both pure functions, both exhaustively unit-tested.
- The transparent data-quality component model (`dataQuality.ts`) — deliberately no single opaque score.
- The versioned reconciliation-tolerance config (`reconciliationConfig.ts`) with a DB-backed loader and a hardcoded, value-matched fallback.
- The full DB-touching orchestrator (`documentProcessing.ts`) wiring everything above into the real pipeline: extraction → detection → parsing → account/instrument resolution → transaction normalisation+dedup → holding snapshots → per-position reconciliation+certification → audit.
- The account-resolution extension (`accountResolution.ts`) — normalised-folio matching so repeated statements for the same folio resolve to the same account.
- 5 new API routes (process, status, summary, reconciliation-cases list, portfolio-truth list+certify) plus 1 extended route (reconciliation-cases resolve), all `requireUser()`-gated, none exposing unrestricted CRUD.
- A minimal upload/review UI (`app/(app)/investment-intelligence/page.tsx` + `InvestmentIntelligenceClient.tsx`) implementing spec section 31's 8-step flow, with a new nav entry.
- 30 golden CAS fixtures (15 CAMS + 15 KFintech), independently-authored expected values, generated by a from-scratch fixture generator (`scripts/investment-intelligence/`).
- 195 new unit tests across 13 files (364 total with the R1 baseline), including a genuine binary-level PDF-extraction test pack, a harness self-check (proves the fixture comparison can detect a broken parser), negative/edge and dedup/reconciliation test packs.

## 2. What was deliberately NOT implemented (R2 non-goals, honoured)

No XIRR/CAGR/TWRR/rolling-returns calculation anywhere. No benchmark comparison, blended benchmark, alpha/beta/volatility/Sharpe/Sortino. No SIP performance analytics. No stock look-through/fund-overlap/sector-concentration analytics. No tax/STCG/LTCG/exit-load calculation. No regular-to-direct switch recommendation, no investment recommendations, no portfolio optimisation, no Monte Carlo, no goal forecasting integration. **No FHIP publication of any R2-produced canonical data** — `publishPositionStructural()` (R1) is never called from any R2 code path; `ii_fhip_publications` remains exactly as R1 left it (structural only, `published_row_id` always null). No Dashboard/net-worth integration. No automated AMFI NAV valuation engine (statement-provided NAV only, `source_nav`, never "current" NAV). No adviser workflows. No broker transaction ingestion. No Australian parser. Confirmed by direct code review — no R2 file imports `publishing.ts`, and `computeDashboard()`/`reportSections.ts`/every forecast calculator are byte-identical to their pre-R2 state (`git diff df6c221..HEAD -- lib/services/dashboard.ts lib/engines` returns no changes to any of those files, since R2 never touched them).

## 7. Known limitations (honestly disclosed, not hidden)

- Golden fixtures are synthetic, structurally-faithful text — not a byte-exact reverse-engineering of a real production CAMS/KFintech PDF (no licensed sample was available). See `R2_SUPPORTED_CAS_FORMATS.md` section 4.
- Genuine RC4/AES PDF-encryption decryption is not independently re-proven — the classification logic around a real `PasswordException` type is fully tested; the upstream library's own decryption correctness is trusted, not re-verified. See `R2_TESTING_AND_VERIFICATION.md` section 3.
- Every claim requiring the new migrations applied to a live Postgres instance is BLOCKED in this sandbox, exactly as R1's precedent — see `R2_SECURITY_VERIFICATION.md` and `R2_TESTING_AND_VERIFICATION.md` for the exhaustive, explicit list of what is and is not proven live.
- `DUPLICATE_SUSPECTED` reconciliation-case detection (the heuristic that would flag a near-duplicate transaction that doesn't fingerprint-match exactly) is not implemented as a distinct detection pass in R2 — the discrepancy-type enum value exists for future use; R2's actual duplicate handling relies entirely on the deterministic fingerprint mechanism (exact match → linked, no match → new canonical row), which is simpler, fully deterministic, and covers every golden-fixture dedup scenario tested, but does not attempt fuzzy/near-duplicate detection.
- The minimal UI is deliberately minimal (spec section 31's own instruction) — no polished design pass, no loading skeletons beyond a plain "Loading…" state, no pagination for a large statement/case list. Sufficient to exercise and observe the full R2 workflow, not a production-polish UI.

## 8. Exact prerequisites for R3

1. Migrations `0039`-`0041` applied to DEV, then the full SEC-*/DB-*/PROV-*/IN-* security and RLS test pack re-run live against the new tables (methodology already proven correct on the R1 tables).
2. A real CAMS and/or KFintech sample statement (de-identified or synthetic-but-licensed) to validate the parser regexes against actual production layout variation, beyond the synthetic fixtures.
3. Activation of the real `assets`/`investments`/`retirement_accounts` cross-register write inside `publishPositionStructural()` — R2 deliberately leaves this untouched; R3 is the first release permitted to wire it, per spec section 32's explicit R2/R3 boundary.
4. XIRR/CAGR/TWRR and benchmark-comparison analytics, built ON TOP OF the transaction/holding data R2 now proves — R2's `history_completeness` status must be read and respected by that engine (never computing "since inception" performance on anything less than `complete_from_inception`), per spec section 46.
5. Reconciliation UX beyond the minimal review-and-resolve flow (bulk actions, admin curation UI for `ii_scheme_alias_map`/`ii_sources`, which R2 populates only via service-role code, not a UI).

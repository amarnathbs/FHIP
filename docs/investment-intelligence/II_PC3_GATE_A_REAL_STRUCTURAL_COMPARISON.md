# II-PC3 — Gate A: Real CAMS Statement Structural Comparison

Status: DISCOVERY / DOCUMENT-INSPECTION ONLY — no fixtures, no test files, no product code touched in this pass.
Branch: `feature/ii-pc3-real-cams-qualification-pack`, on top of `85e2adf` (Gate B), off the certified `721417e` base.

## 0. Scope and method

A genuine, password-protected CAMS Consolidated Account Statement PDF was supplied for structural comparison ONLY, per the task that authorised this pass. The file was decrypted locally, in-memory, using a one-off inspection script; the script and the password used to run it were never committed, and no decrypted PDF, extracted text, or excerpt of any real value (name, PAN, address, folio number, account number, amount, unit count, NAV, balance, bank/advisor code, email, phone) was ever written to disk or is reproduced anywhere in this document. Every property below was captured as an abstract structural fact (a boolean, a count, a redacted "shape", or a genuinely non-sensitive template/label string) — never a real value.

**Methodology caveat, disclosed up front:** this inspection used Python's `pypdf` library for text extraction, not the project's actual `pdf-parse` (Node/pdf.js-based) library used by `pdfExtraction.ts`. The two extraction engines can, in principle, reconstruct whitespace and multi-column ordering differently for the same PDF content stream. Every finding below that concerns column/field *ordering* should be read as "this is what the real PDF's structure most plausibly is," corroborated by the parser's own actual regex failing to match it — not as a byte-for-byte guarantee of what `pdf-parse` would emit. This does not weaken the conclusion below, because the mismatches found are large and multi-axis (label vocabulary that doesn't exist at all, not just re-ordered whitespace).

Reference material read before this comparison: `docs/investment-intelligence/II_PC3_CAMS_STRUCTURAL_FINGERPRINT.md` (the existing privacy-safe fingerprint the synthetic fixtures were built against), `scripts/investment-intelligence/pc3/pc3FixturePack.ts` (Q01–Q10 fixture generator), and `lib/services/investment-intelligence/parsers/camsParser.ts` (the actual parser logic, traced line-by-line against every finding below).

## 2. Why this is not merely a fixture gap

Tracing the findings above directly against `camsParser.ts`'s actual control flow (not by running the file through the pipeline, per the task's own restriction):

1. **Source detection is at serious risk of failing outright.** `canHandle()` scores `TITLE_RE` (+0.55, row 1: does not match this document) and counts exact-line matches of `REGISTRAR_RE` (`^Registrar\s*:\s*CAMS\s*$`, capped contribution `min(0.44, 0.2 + n*0.05)`). Because the real statement's registrar mentions are overwhelmingly folded into the combined scheme-heading line (row 5) rather than standing alone on their own line, only a minority of the real "Registrar" occurrences take the exact standalone shape `REGISTRAR_RE` requires. With the title contributing nothing, total confidence is well short of the `>= 0.5` threshold `registry.ts`'s `detectSource` requires to assign `sourceKey: 'cams'` at all — meaning this real document plausibly never even reaches the CAMS parser.
2. **Even granting detection, no scheme is ever established.** `parseTransactions()`/`parseHoldings()` both gate all transaction/holding capture behind `currentScheme` being non-null, which is set only by `extractLabelledField(line, 'Scheme Name')` finding a line that begins with the literal label `Scheme Name:` (row 5: this document has no such line anywhere). `currentScheme` therefore stays `null` for the entire document, and `if (inTable && line.length > 0 && currentScheme)` / `if (m && currentScheme)` never fire — zero transactions and zero holdings would be extracted, independent of whether any individual row's regex happens to match.
3. **Even granting a scheme were somehow set, the transaction-row and closing-balance regexes independently fail to match this statement's real grammar** (rows 6 and 9) — every one of the 193 date-prefixed candidate lines in the document, and all 17 closing-balance-looking lines, fail their respective certified regex.
4. **`AMC Name:` never populates**, so even a best-case partial parse would carry an empty institution name for every instrument (row 3) — reproducing, for real-world input, the same class of live defect the code's own comments describe having found and fixed once before (the R11-FINAL finding), except this time the root cause is that the label doesn't exist in this statement's grammar at all, not that it was mis-gated.

These are independent, compounding failures across source detection, scheme establishment, transaction parsing, and holdings parsing — not a single narrow edge case a fixture update could close.

## 3. Outcome: REAL PARSER INCOMPATIBILITY

**`camsParser.ts` as currently written would not correctly parse this real CAMS statement.** The synthetic Q01–Q10 fixture pack is faithful to the CAMS grammar `II_PC3_CAMS_STRUCTURAL_FINGERPRINT.md` documented — which that document itself flagged, up front, as reverse-engineered from the pre-existing R2 parser/fixtures rather than from any real sample, capping PC3 at CONDITIONAL PASS at best. This real statement now proves that flagged gap was real: the actual production CAMS layout (at least for the registrar-generation era/template this file represents) uses a materially different label vocabulary and line grammar than the one certified in this codebase, on at least four independent structural axes (title line, investor labels, AMC/scheme heading composition, and closing-balance grammar).

This is not something to fix in this pass — per the task's scope, no fixture, test, or product file has been modified. This finding should block any claim of production-readiness for real CAMS ingestion until the parser (and its fixture pack) are rebuilt against this statement's actual grammar, or against a broader real-sample survey if this statement's era/template is not the only one in use.

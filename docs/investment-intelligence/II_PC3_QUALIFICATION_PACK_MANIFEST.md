## Finding #1 (the single most important finding) — caught live by the Q09 fixture: a real PARSER_DEFECT — FIXED

**Classification: PARSER_DEFECT** (CAMS transaction-table state machine, `camsParser.ts`).

Running the pack for real (not just designing it) caught a genuine, previously-unproven bug exactly where Phase 1's structural fingerprint flagged an "unverified risk": `inTable` was reset by a `Folio No:` line, a `Scheme Name:` line, or a `Closing Unit Balance` line — but **not** by an `AMC Name:` line. Every scheme block begins with `AMC Name:` before its own `Scheme Name:` line (the parser's own documented layout). So whenever a preceding scheme's transaction table had not yet been closed by a `Closing Unit Balance` line when the next scheme's `AMC Name:` line was reached — exactly what Q09's real 2-page-object PDF does (page break falls mid-table, header block reprinted on page 2 before the eventual closing line) — the `AMC Name:` line itself was fed to `TXN_ROW_RE`, always failed it, and raised a false `unparseable_transaction_row` error against a perfectly valid document. The same gap would also misfire on a single-page statement whose scheme has no closing-balance line printed at all (e.g. some RTAs omit it for a fully-redeemed zero-balance scheme) immediately followed by the next scheme's `AMC Name:` line — not exclusively a page-break scenario.

**Fix applied** (`lib/services/investment-intelligence/parsers/camsParser.ts`, `parseTransactions`): an `AMC Name:` line now resets `inTable = false` and `continue`s, exactly mirroring the existing `Folio No:`/`Scheme Name:` pattern. `parseHoldings` was checked and needs no equivalent fix — it has no "else, try to match this line as a data row" branch; it only ever matches `CLOSING_RE` explicitly, so it was never exposed to this defect.

**Verification**: reproduced the failure first (`tests/unit/iiPc3QualificationPack.test.ts`'s Q09 test failed with exactly the predicted `unparseable_transaction_row` on the reprinted `AMC Name:` line, `lineHint` pointing at it), applied the fix, re-ran — all 12 Q09 transactions now parse with zero errors, in the correct order, no loss, no duplication. Re-ran the full R2 CAMS golden-fixture suite (`iiR2ParserFixtures.test.ts`) afterward — all still pass, confirming the fix does not regress any existing certified CAMS behaviour (none of R2's fixtures happen to exercise a scheme block without a closing line immediately followed by a new `AMC Name:` line, which is exactly why this was never caught before).

## Finding #2 — a real, narrow, in-scope RECONCILIATION_DEFECT — FIXED

**Classification: RECONCILIATION_DEFECT** (certification-gating gap, not a parser or schema defect).

`lib/services/investment-intelligence/certification.ts` has always defined and documented a `parser_fatal_error` blocking reason (spec sections 27/29's own "likely blockers" list). But `documentProcessing.ts`'s one call site feeding `evaluateCertification` hardcoded `parserFatalError: false` **unconditionally** — the real, already-computed `parsed.errors` signal (populated whenever a transaction row fails the CAMS/KFintech grammar, e.g. Q10's corrupted Amount field) was silently never wired through. The only backstop was reconciliation math happening to disagree with the statement's printed closing balance, which is not guaranteed (an economically-neutral dropped row, or a coincidental balance, would sail through undetected).

**Fix applied** (`lib/services/investment-intelligence/documentProcessing.ts`): the per-position certification loop in `processSourceDocument()` now computes `parserHasFatalError = parsed.errors.length > 0` and threads it into `evaluatePositionAndCertify()`, which passes it through to `evaluateCertification({ parserFatalError: parserHasFatalError, ... })`. The separate manual `recertifyPosition()` re-evaluation path (which has no fresh `ParsedDocumentOutput` to inspect) is deliberately left unchanged/out of scope, to keep the fix narrow to the one call site that actually has the signal.

**Verification**: `tests/unit/iiPc3QualificationPack.test.ts`'s Q10 test proves the exact wiring; `tests/unit/iiR2Certification.test.ts` (the pre-existing generic unit test for `evaluateCertification` itself) was confirmed to assert only the pure function's happy-path input shape and is unaffected by this change (no test anywhere asserted the old, buggy hardcoded-`false` behavior — confirmed by grep across `tests/unit` and `tests/live-dev` before making the change). The full pre-existing baseline regression suite (136/136, 10 files, covering CAMS/KFintech parsing, F1 FIFO account-scope, F2 current-result selection, account identity) was re-run clean both before this change was made and is re-run again in Phase 5 to confirm it remains clean after.

No migration was needed (no schema change — `ii_portfolio_truth_status.blocking_reasons` already accepts arbitrary JSON reason codes, and `parser_fatal_error` was already a documented, valid code certification.ts could emit).

# R0 — Net Worth Deduplication Contract

Status: FINAL (R0) — this is the critical R0 deliverable per spec Section 9.
Depends on: `R0_CURRENT_STATE_DISCOVERY.md` (sections 8, 11 — the exact net-worth formula and confirmed overlap risk), `R0_CANONICAL_DATA_CONTRACT.md`, `R0_FHIP_PUBLISHING_CONTRACT.md`

## 1. The mechanism (least-disruptive option chosen, and why)

`computeDashboard()` sums `investments`/`assets`/`retirement_accounts` rows directly, with **no existing concept of "exclude this row"** (`R0_CURRENT_STATE_DISCOVERY.md` section 8). The spec offers candidate concepts (`canonical_position_id`, `publication_id`, `economic_asset_id`, `source_system`, `publication_target`, `include_in_net_worth`, `canonical_owner_module`) but instructs not to adopt them blindly.

**Decision**: adopt exactly two of the seven candidates, both already present in `R0_CANONICAL_DATA_CONTRACT.md`'s `ii_fhip_publications` entity — `publication_target` and `include_in_net_worth` — and reject the rest as unnecessary for R0/R1:

- `canonical_position_id` — **rejected as a new concept**; already covered by `ii_fhip_publications.canonical_position_id`, which is the entity's own field, not a new column needed anywhere else.
- `publication_id` — **rejected**; `ii_fhip_publications.id` already serves this role.
- `economic_asset_id` — **rejected**; would duplicate `(account_id, instrument_id)`, the stable position identity already frozen in `R0_CANONICAL_IDENTIFIER_STRATEGY.md`. Introducing a second "economic asset" identity alongside it would itself become a dedup risk.
- `source_system` — **rejected as a new column on existing FHIP tables**; the existing tables need no such column because dedup is enforced by *never creating a second row* for an already-published position (see mechanism below), not by tagging rows post-hoc and filtering at read time.
- `canonical_owner_module` — **rejected**; ownership of the calculation stays exactly where it is today (`computeDashboard()` for net worth, Forecasting for household projections — design principles 10/11); no row needs to declare which module "owns" it because only one module (Dashboard) ever sums these tables, unchanged.

**The chosen mechanism**, concretely:

1. Investment Intelligence never inserts a second row into `investments`/`assets`/`retirement_accounts` for a position it has already published. Publishing an update to an existing position **updates the same `investments.id` row** (via `ii_fhip_publications.published_row_id`, frozen in section 2 of `R0_CANONICAL_DATA_CONTRACT.md`) rather than inserting a new one. This alone prevents the "two rows in one register" half of double counting.
2. Cross-register duplication (the same economic holding entered once as an `assets` row and once as an `investments` row — the concrete, already-live risk confirmed in `R0_CURRENT_STATE_DISCOVERY.md` section 11) is prevented by **routing every Investment Intelligence publication through exactly one target register per position**, decided once at publish time by `publication_target` (`assets|investments|retirement_accounts`) based on the instrument's classification (an NPS/PPF/EPF-classified instrument always targets `retirement_accounts`; a mutual-fund/share/ETF-classified instrument always targets `investments`), and by **never publishing the same `ii_holding_snapshots` position to more than one target**. `ii_fhip_publications` has a `unique(canonical_position_id)` constraint (an R1 implementation detail, frozen here as a requirement) enforcing this at the database level, not merely by convention.
3. `include_in_net_worth` (on `ii_fhip_publications`) is the explicit, auditable off-switch for the rare legitimate case where a position must be tracked in Investment Intelligence but must **not** count toward household net worth (e.g. scenario 8 below — an employer-restricted holding the household doesn't consider "their" net worth yet, or a position being actively reconciled and not yet certified). This does not filter `computeDashboard()` (which has no knowledge of Investment Intelligence at all, preserving its zero-coupling design) — instead, when `include_in_net_worth = false`, publishing simply does not push a value into `investments.current_value` at all (or archives the previously-published row via the existing `is_active = false` soft-delete already used by `registry.ts.archive()`), so the exclusion happens **before** the row reaches `computeDashboard()`, not as a filter inside it.
4. The pre-existing double-counting prevention for **goals** (`goal_funding_sources`' allocation-percentage cap, `R0_CURRENT_STATE_DISCOVERY.md` section 6) is reused as-is via `ii_goal_allocations` keeping it in sync (`R0_GOAL_INTEGRATION_CONTRACT.md`) — no second allocation-limit mechanism is introduced.

This is deliberately the **least disruptive** option: `computeDashboard()`, `reportSections.ts`, and every forecast calculator require **zero code changes** — they keep summing `investments`/`assets`/`retirement_accounts` exactly as today (`R0_CURRENT_STATE_DISCOVERY.md` section 8, 12). All the new dedup logic lives entirely inside Investment Intelligence's own publishing step, upstream of the existing, unmodified calculation path.

## 2. Scenario matrix

For each scenario: canonical record, display location, net-worth treatment, reporting treatment, conflict handling, migration handling.

### 1. Manual share entered in existing Assets
**Canonical record**: the `assets` row itself — no Investment Intelligence involvement (no `ii_fhip_publications` row references it). **Display**: Assets grid. **Net worth**: counted once, via `totalAssets`. **Reporting**: as today. **Conflict handling**: none — this is today's behaviour, unmodified. **Migration**: no migration needed; R1 does not touch pre-existing manual rows.

### 2. Manual share entered in Investments
**Canonical record**: the `investments` row itself, no `ii_fhip_publications` reference. **Display**: Investments grid. **Net worth**: counted once, via `totalInvestments`. **Reporting**: as today. **Conflict handling**: none. **Migration**: none.

### 3. Same share later imported from a broker
**Canonical record**: Investment Intelligence creates an `ii_instruments`/`ii_accounts`/`ii_holding_snapshots` chain for the imported share. Before first publish, a **reconciliation check** (not built in R0/R1, architecture only — flagged as an R1+ UX requirement) should detect that a manually-entered `investments` row already exists for what appears to be the same instrument/owner and prompt the user to link rather than duplicate. **Display**: once linked, the *existing* `investments.id` row is what `ii_fhip_publications.published_row_id` points at — publishing updates it in place rather than creating a second row. **Net worth**: counted once (the same row, now Investment-Intelligence-managed going forward). **Reporting**: as today, now with a "Last reconciled" badge (`R0_FHIP_PUBLISHING_CONTRACT.md`). **Conflict handling**: if the manual value and the imported value disagree, an `ii_reconciliation_cases` row is opened rather than silently overwriting; the user resolves which value is certified. **Migration**: no schema migration; this is a runtime reconciliation-UX flow, out of scope to build in R0/R1.

### 4. Mutual fund imported from CAS
**Canonical record**: `ii_source_documents` (the CAS) → `ii_transactions` → `ii_holding_snapshots` → one `ii_fhip_publications` row → one `investments` row (`master_item_key='managed_funds'`, per `R0_FHIP_PUBLISHING_CONTRACT.md` ITEM mapping). **Display**: Investments grid, exactly one row. **Net worth**: counted once. **Reporting**: as today. **Conflict handling**: n/a (first-time import, no prior manual row). **Migration**: none (net-new row via the standard `registry.ts`-shaped INSERT, since `ii_fhip_publications` didn't exist for this position before).

### 5. Existing manual managed-fund row plus imported CAS holding for the same fund
**Canonical record**: identical to scenario 3's pattern — the manual `investments` row is the target of `ii_fhip_publications.published_row_id`, not a second insert. **Display**: one row. **Net worth**: counted once. **Reporting**: as today. **Conflict handling**: `ii_reconciliation_cases` if manual cost base / value materially disagrees with the CAS-derived figures. **Migration**: the existing manual row's `master_item_key`/`institution` values may need reconciling against the CAS-derived instrument classification before linking — a data-quality step, not a schema migration.

### 6. Indian NPS later published to Retirement
**Canonical record**: `ii_instruments.instrument_class` classifies NPS as a retirement-type instrument, so `publication_target='retirement_accounts'` (never `investments`) — this routing decision, frozen in section 1 above, is exactly what prevents the NPS-in-two-registers risk flagged in `R0_CURRENT_STATE_DISCOVERY.md` section 11. **Display**: Retirement grid, `account_type` mapped via the equivalent of the Investments ITEM mapping (`master_item_key` in the `retirement` category — `nps_goal`/similar catalogue entries already exist per `R0_CURRENT_STATE_DISCOVERY.md` section 6's `goal_types` seed, and `retirement_accounts` has its own `master_item_key` column, `R0_CURRENT_STATE_DISCOVERY.md` section 5). **Net worth**: counted once via `totalRetirement`. **Reporting**: as today. **Conflict handling**: if a user had manually entered an NPS row under Investments (mis-classified) before Investment Intelligence existed, this is a genuine pre-existing data-quality issue Investment Intelligence surfaces (via reconciliation) but does not silently "fix" by moving the user's data between registers without confirmation. **Migration**: none required for R0/R1 (no auto-migration of existing rows between registers is in scope — flagged in `R0_ACCEPTANCE_REPORT.md` as a manual-remediation-only concern, not a blocking R1 architectural issue).

### 7. Term deposit appearing as Asset vs Investment
**Canonical record**: `ii_instruments.instrument_class` for a fixed/term deposit is deliberately classified consistently (`cash`-bucketed, matching `MASTER_ASSET_ITEM_TO_BUCKET`'s existing `term_deposits: 'cash'` mapping AND `MASTER_INVESTMENT_ITEM_TO_BUCKET`'s equally-existing `term_deposits: 'cash'` mapping — both already agree on the bucket even though today either register can hold it, `R0_CURRENT_STATE_DISCOVERY.md` section 8). **Decision**: Investment Intelligence always routes term deposits to `publication_target='assets'` (matching the more common existing manual-entry pattern for this item), never split across both. **Net worth**: counted once regardless of which register a *manual* entry chose historically, because Investment Intelligence's own publish is single-target by construction (section 1). **Conflict handling**: reconciliation if a manual `investments`-register term deposit already exists when Investment Intelligence would otherwise publish to `assets` — same linking flow as scenario 3, generalised across registers. **Migration**: none.

### 8. Gold investment vs personal gold asset
**Canonical record**: the spec principle here is intent, not instrument type — physical gold jewellery/coins held as a personal asset is genuinely a different economic concept from investment-grade gold (ETF/SGB/digital gold) even though `master_item_key='gold'` exists in both the `asset` and `investment` catalogues today (`R0_CURRENT_STATE_DISCOVERY.md` section 3, section 8). Investment Intelligence's CAS/broker-derived import can only ever produce investment-grade gold instruments (an SGB or Gold ETF has a demat/folio trail; jewellery does not) — so this scenario **cannot actually arise from an Investment-Intelligence-sourced publication**: there is no import path that would produce a personal-asset gold row. A user's existing manual "gold" entry in either register is left untouched by Investment Intelligence entirely (no publication ever targets it) unless the user separately imports a Gold ETF/SGB position, which follows the standard scenario-3/5 reconciliation flow if a same-labelled manual row already exists. **Net worth**: counted once (Investment Intelligence never creates a second gold row without going through reconciliation). **Migration**: none.

### 9. Indian investment shown in AUD household net worth
**Canonical record**: `ii_holding_snapshots.currency_code='INR'` is preserved unchanged; the published `investments.currency_code='INR'`, `country_code='IN'` row is summed by `computeDashboard()`'s existing `reportingValue()` FX conversion (`R0_CURRENT_STATE_DISCOVERY.md` section 8) exactly as any manually-entered INR investment row already is today — **no new FX logic is needed**, because `computeDashboard()` already handles per-row currency conversion for the household's reporting currency. **Net worth**: counted once, in AUD-equivalent terms in the household total, while the underlying `ii_holding_snapshots`/`investments.current_value` stays in INR. **Reporting**: cross-border sections (`assetsByCountry`, `investmentByCountry`) already show the INR figure "as recorded" per-country (confirmed in `dashboard.ts`, `R0_CURRENT_STATE_DISCOVERY.md` section 8) — unchanged. See `R0_CROSS_BORDER_CONTRACT.md` for the full treatment.

### 10. Archived/unlinked imported investment
**Canonical record**: user archives the published `investments` row via the existing `registry.ts.archive()` path (`is_active=false`). **Display**: removed from the active grid (existing behaviour, `registry.list()` filters `is_active=true`). **Net worth**: excluded — `computeDashboard()` already only ever receives active rows (the service layer queries `is_active=true`), so this requires no new logic. **Investment Intelligence's own record**: `ii_fhip_publications.status` transitions to `unpublished`; the underlying `ii_holding_snapshots`/`ii_transactions` history is **not deleted** (design principle 6 — corrections never destroy source evidence) so republishing later (the user un-archives, or a fresh statement arrives) can resume from full history rather than starting cold. **Conflict handling**: n/a. **Migration**: none.

### 11. Source document refreshed with newer holdings
**Canonical record**: a new `ii_source_documents` row (never overwriting the prior one — `superseded_by_document_id` chain, `R0_CANONICAL_DATA_CONTRACT.md`) produces new `ii_transactions`/`ii_holding_snapshots` rows. **Display**: unchanged row (same `investments.id`), now showing the newer value once republished (`ii_fhip_publications.last_republished_at` updates, `published_row_id` stays the same). **Net worth**: still counted exactly once — this is precisely why `ii_fhip_publications.unique(canonical_position_id)` matters: a refresh is an UPDATE to the existing publication row's linkage, never a second publication. **Reporting**: "Last reconciled/valued" badge date advances. **Conflict handling**: if the newer statement's closing balance for a still-open position materially disagrees with the prior certified snapshot in a way not explained by the transactions in between (a genuine data-quality anomaly, not routine growth/contribution), an `ii_reconciliation_cases` row is opened before the discrepant value is certified and republished. **Migration**: none — this is the designed steady-state operation, not a migration event.

### 12. User correction to an imported position
**Canonical record**: the user edits the published `investments` row directly through the existing grid UI (still permitted — `R0_FHIP_PUBLISHING_CONTRACT.md` section 3). This is recorded as a correction **layered on top of** the certified canonical record (`R0_SOURCE_PROVENANCE_CONTRACT.md`'s layering: original evidence → parsed interpretation → reconciliation adjustment → certified record → FHIP publication), not written back into `ii_holding_snapshots`/`ii_transactions` as if it were newly-parsed source data. **Display**: the edited value shows immediately (same row, same mechanism as any manual edit today). **Net worth**: counted once, using the user's corrected value, until the next republish. **Conflict handling**: the next republish (scenario 11) must not silently discard the user's correction — an R1 UX decision (last-write-wins-with-warning vs. merge-prompt) is flagged as an open item, not resolved by R0 architecture alone, in `R0_ACCEPTANCE_REPORT.md`. **Migration**: none.

## 3. Design-test verdict

Every scenario above resolves to **exactly one household economic value** contributing to `computeDashboard()`'s net worth, with the mechanism in section 1 (single-target-per-position publishing + unique-canonical-position constraint + existing soft-delete-excludes-from-sum behaviour) sufficient to guarantee it without any change to `computeDashboard()`, `reportSections.ts`, or any forecast calculator. See `R0_TESTING_AND_VERIFICATION.md` section C for the corresponding design-test record.

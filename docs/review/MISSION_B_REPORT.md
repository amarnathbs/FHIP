## 2. F3: create only on Save, delete drafts, cleanup

Decision stated: **no autosave anywhere** (Article, Guide, FHIP Explainer, Money Update and Template, Glossary, Video editors). The PO asked to save only when Save is pressed; the FAQ editor and CTA form were already explicit-save. Work is protected by the unsaved-changes guard and the "Unsaved changes" label.

What changed:
- Create Article/Guide/Explainer, Money Update/Template and Glossary now open the editor on an in-memory blank post (`lib/resources/editor/blankPost.ts`, `lib/resources/money-update/blankPost.ts`). The chooser pages are links, not buttons that POST. The record is created by the first Save, with the author's own title, through the existing POST routes, which now **refuse a request without a real title (422)** and return `updated_at` for the follow-up PATCH. The editor shows "Not saved yet / Nothing is saved yet" and hides Preview, Delete, workflow and slug-check until the record exists.
- Video: the record is created by the explicit "Add Video" button with a YouTube URL (it cannot exist without one). Autosave removed from the video editor.
- Delete: one shared server function `deleteNeverPublishedDraft` (`lib/resources/editor/deleteDraft.ts`), `DELETE /api/admin/resources/content/[id]`, a shared `DeleteDraftButton` with a confirmation dialog, shown in All Content and Drafts lists (desktop table and mobile cards), the read-only detail page ("next screen after View") and every editor. Only status idea/draft with `published_at` null; a draft that ever reached published or scheduled in workflow history is refused as published content; the DELETE statement repeats the status predicate so a publish between check and delete cannot be deleted. Related rows go through the existing ON DELETE CASCADE (versions, categories, tags, related, context, sources, FAQ links, workflow history, video row); counts are written into the audit event `RESOURCE_DRAFT_DELETED` (`resource_audit_log`, before state included). Published, scheduled, in review, approved and archived items are never deleted (409 with the workflow message).
- Capability (Admin Standard s2): new separately named `canDeleteDraftResource` = Super Admin or Resource Administrator, mirroring the database's own "managers delete posts" policy; the page props, the route (401/403/404/409) and the database policy enforce it independently. Author and Editor must ask a Resource Administrator.
- No migration was needed.

Standard clauses and tests (`tests/unit/resourcesF3DraftDeleteAndCreateOnSave.test.ts`, 20 tests): s2 capability matrix (six roles); s4 direct-API 401/403/404/409/200; s13 a delete that matches no row is refused, not reported as success. Negative control demonstrated: removing the status/published predicate and the draft check from `deleteDraft.ts` made 3 named tests fail (published row deleted, race row deleted, 409 became 200); restored.

DEV-browser-verified (fixture user, Super Admin, temporary and restored): opening `new?type=article` and waiting longer than the old 2.5 s autosave window left the count of "Untitled Article" rows unchanged (27 before, 27 after); typing a title for 4.5 s created 0 rows; pressing Save created exactly 1 draft; Delete in the editor showed the confirmation, removed the row and wrote 1 audit row.

Existing "Untitled" drafts on DEV (read-only dry run `scripts/resources/f3-untitled-draft-cleanup.ts`, dry-run by default, `--apply` deletes only pristine ones, refuses any host but DEV): 42 placeholder-titled rows. **35 are pristine empty placeholders** (24 Article, 4 Guide, 6 FHIP Explainer, 1 Glossary Term). 7 are never auto-deleted: 3 Articles that have saved versions and 4 "Untitled Video" rows that have a real video row. I did **not** run `--apply` (the PO decides). Production: hand-over `docs/resources/po_apply_f3_cleanup/` (`01_look_first.sql` read-only, `02_remove.sql` one statement that deletes only never-edited placeholders and audits each, plain-language README). PGlite-verified (`resourcesF3CleanupSqlPglite.test.ts`, 7 tests, includes two demonstrated negative controls and the editor-safe SQL lint). The SQL was not run on any real database.

## 6. F12: link a video to content, and the broken video record

Link: "Link to content" on the video edit page, in the Videos list rows, and offered after "Add Video"; a "Linked videos" panel on the content detail page and the Article/Guide editor page, with remove and confirmation. It reuses the existing `resource_related_content` table with relationship type `related` (the CHECK allows it, so **no migration and no constraint change**); direction content to video; duplicates and video-to-video are refused; unlink only removes a link that belongs to that video; audit events `video_linked_to_content` and removal. Capability: listing is Resources staff, linking is `canManageDiscovery` (Resource Admin, Editor, Super Admin), 403 otherwise (tested for Author, Publisher, Compliance Reviewer, Analyst).

The failure (record `a7fc6f61-6dc5-4635-9e52-10c55c59dd85`): it is **VID-008 "Compounding Explained Visually"**, one of the 20 planned video scripts (VID-001 to VID-020) that the R1.7/R1.7C content import created as video-typed posts with **no `resource_videos` row**, because the source workbook has no YouTube IDs and the table's `youtube_video_id`/`youtube_url` are NOT NULL (an invented ID would have been fabricated data). The editor then met a video post with no video row and dead-ended. **DEV data, confirmed:** 30 video posts, 10 with a row, **20 orphans = exactly VID-001 to VID-020, and the PO's record exists on DEV**. **Production inference (no production read):** the same import payload was deployed to production as Draft content, so the same 20 records almost certainly exist there and the PO's screenshot is one of them.
Fix: the dead end is replaced by a repair form (enter the YouTube URL or ID; validated; creates the missing row for that existing post; refuses if a row already exists even with the same ID, so a healthy record can never be swapped; atomic and idempotent because the table is unique on the post; audited as `video_details_repaired`; capability = those who may add a video). DEV-browser-verified that the PO's record now shows the repair form plus the linked-content panel and no dead-end message (screenshot `f12_repair_form.png`). The repair was **not executed** on any record (that needs the real YouTube URLs from the PO). A second, smaller root cause was also fixed in `createVideoDraft`: its compensating delete ran under RLS where only managers may delete, so an Author's failed second insert silently left an "Untitled Video"; it now retries once, verifies the delete, and cleans up through a tightly scoped service-role delete, or tells the caller honestly. Tests: repair (creates, refuses twice, refuses healthy record, bad URL, non-video), routes (401/403/200/409), link/unlink, orphan clean-up; demonstrated control: removing the already-has-video check made 3 named tests fail.
